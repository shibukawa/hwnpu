# 変換したモデルを AMD の NPU で動かす: 設計

作成: 2026-11-03。**状態 (2026-11-04): 段階 A1〜A4 を実装し、Gemma 4 E2B が `hwnpu-chat -iron` と `hwnpu-agent -iron` (今は `hwnpu-chat -m DIR` と `hwnpu-chat agent -m DIR`) で動いた (design.md 16.47〜16.51)。Windows 向けの XRT 経由のバックエンド (16.56) と、NPU1 向けの「1 ステップごとの xclbin」(16.57) も実装した。どちらも同じ経路をこの機械 (NPU2、Linux) で実機検証したが、Windows と NPU1 の実機では未検証。** 対象は `hwnpu-chat` と `hwnpu-chat agent` を AMD Ryzen AI の NPU (XDNA2、Strix Point 以降) で動かすこと。根拠は design.md 16.44 (実機での最初の確認) と 16.45 (GEMV と切り替えの測定)、それとこの文書の 2 節の測定。

## 1. 現状

| 層 | 今の状態 | AMD で足りないもの |
|---|---|---|
| ドライバの呼び出し (`internal/xdna`、`internal/backend/amd`) | xclbin と命令列の実行 (ERT_START_CU) が Ryzen AI 9 365 で動く | **full ELF** の実行 (3 節) |
| 演算の実装 | なし。AMD には公開されたグラフ用コンパイラがない | カーネルとその並べ方。自分では書かない (2.3) |

## 2. 測定から決まったこと

### 2.1 速さと電力 (design.md 16.45)

- NPU が重みを読む速さは約 50 GB/s (bf16 の GEMV、8 列)。CPU が読むだけなら 55〜79 GB/s
- 電力 (パッケージ全体): NPU の GEMV はアイドルより約 5〜8 W 増。CPU は読むだけで 13〜24 W 増。同じ量の重みを読む電力量は NPU が半分以下で、待つ間 CPU は空く
- **ハードウェアコンテキストの切り替えは 1 回約 0.46 ms**。演算ごとに xclbin を投入する方式は、1 トークンに 100 演算なら切り替えだけで 46 ms になり使えない
- ハードウェアの上限 (IRON のサンプルで 2026-11-02〜03 に測定、[amd-xdna2-bench.md](amd-xdna2-bench.md)): DMA は読みだけで 55〜57 GB/s、書きだけで 48 GB/s、読み書き同時で計 64 GB/s (8 本で頭打ち、1 本 14 GB/s)。1 回の実行の固定費は最小 0.06 ms。4096³ の行列積は int8 7.3〜7.6 TOPS、bf16 2.7〜3.0 TFLOPS (bfp16 で代用すると 5.6) で、ピークの 1〜4 割 (コア内の計算が律速)。4 ビットの GEMV は 16 コア以上で読みの帯域に届く

### 2.2 IRON の実績 (amd/IRON の CI、Krackan = NPU2、2026-11-02)

| モデル | 形式 | デコード | 1024 トークンのプロンプトの初回 |
|---|---|---|---|
| Llama 3.2 1B | bf16、full ELF | 14.5 トークン/秒 | 0.47 秒 |
| Llama 3.2 1B | bf16、演算ごとに投入 | 5.4 トークン/秒 | 0.76 秒 |
| Llama 3.2 3B | bf16、full ELF | 6.4 トークン/秒 | 1.6 秒 |
| Gemma 4 E2B | bf16、full ELF | 5.6 トークン/秒 | — |
| Gemma 4 E2B | q4nx (FastFlowLM のエンジン) | 28 トークン/秒 | — |

full ELF と演算ごとの投入の差 (2.7 倍) は、2.1 の切り替え費用とおおむね合う。プロンプトの処理は 2000 トークン/秒前後で、M3 の Neural Engine (OpenCode の 7.4K トークンに 13〜17 秒) より 1 桁速い。デコードは bf16 だと遅く、4 ビットの重みで 5 倍になる。

### 2.3 方針の選択

| 案 | 内容 | 判断 |
|---|---|---|
| A | MIL のプログラムを AIE 向けに下ろす変換器とカーネルを自分で書く | しない。AIE の配置、DMA、カーネルは IRON と mlir-aie が何年もかけて作っている部分で、追いつけない |
| B | 演算ごとに xclbin を作り、Go から順に投入する | しない。切り替え費用 (2.1) |
| C | ONNX Runtime と Vitis AI | しない。Windows が中心、依存が大きく、Linux の NPU 単体では動かない |
| **D** | **IRON をビルド時のコンパイラとして使い、hwnpu は Go の実行器になる** | **採る** |

案 D の考え方は MODEL_ARCHITECTURE.md の「開発者が一度だけ変換し、NPU ごとの成果物を配る」と同じ。ただし AMD の成果物を作るのは Go ではなく IRON (Python) になる。利用者の機械には Python も XRT も要らない。これは「変換は Go だけで」という原則の例外で、AMD に公開されたグラフ用コンパイラがない以上ほかに道がない。IRON (Apache-2.0) は、AMD がモデル単位で精度と速さを毎晩確かめているので、移植の検証の手本にもなる。

## 3. full ELF の実行 (hwnpu 側)

IRON は NPU2 で、モデルの 1 回の呼び出し (デコードの 1 ステップ、またはプロンプトの 1 塊) を **1 つの ELF** にまとめる (`Graph.compile(full_elf=None)`)。全演算の PDI (タイルの構成) と制御コードが 1 つのハードウェアコンテキストに入り、1 つのコマンドで流れる。

### 3.1 投入の手順 (実機で XRT 2.21 の ioctl を記録して確かめた)

`LD_PRELOAD` で ioctl を横取りする道具 (`xtrace.so`) を挟み、IRON の 2 演算のグラフ (ReLU → AXPY) を pyxrt で動かして記録した。Linux 7.0 の標準ドライバ、ファームウェア 1.1.2.64。

1. デバイスヒープ (`BO_DEV_HEAP`、64 MiB) を作ってマップする (xclbin の流れと同じ)
2. 入出力の BO (`BO_SHARE`) を作ってマップする
3. `CREATE_HWCTX`: `num_tiles` = 列 × コア行 (8 × 4 = 32)。列の数は ELF の注記 `.note.xrt.configuration` (種類 6、値 8)。QoS は全て 0、`max_opc` 0。**`CONFIG_HWCTX` (CU の設定) は呼ばない**
4. カーネルのインスタンスの制御コード (`.ctrltext.N`) と、それが参照する PDI (`.pdi.N`) を、それぞれヒープ上の `BO_DEV` に写す。PDI の BO のデバイスアドレスは制御コードに書き込む (3.2 の種類 8)
5. 実行ごとに、引数の BO のアドレスを制御コードに書き込み (種類 5)、`SYNC_BO`
6. コマンドの BO (`BO_CMD`): 頭の語 `0x3b00d001` (状態 NEW、語数 13、opcode 22 = `ERT_START_NPU_PREEMPT_ELF`)。続けて CU マスク 1 語 (0)、`amdxdna_cmd_preempt_data` {inst_buf = 制御コードのデバイスアドレス、save_buf 0、restore_buf 0、inst_size、save_size 0、restore_size 0、inst_prop_cnt 0}、最後に 2 語 (最初の引数の BO のアドレス。ドライバは読まない)
7. `EXEC_CMD`: `args` は引数の BO のハンドル (制御コードと PDI の BO は含めない)。完了待ちは xclbin の流れと同じ syncobj

ドライバ側の裏付け: Linux 7.0 は `force_cmdlist` (既定 true) の経路で `aie2_cmdlist_fill_npu_elf` を通り、`EXEC_NPU_TYPE_ELF` のスロットを作る。npu4 のファームウェアの機能表で、メールボックスのプロトコルの主版 7 なら `AIE2_NPU_COMMAND` と `AIE2_PREEMPT` が有効 (`npu_7.sbin`)。

### 3.2 ELF の読み方

ELF32 (OS/ABI 0x45、ABI 版 0x21)。IRON のカーネル名 `main:sequence` は「カーネル `main` のインスタンス `sequence`」。

| 部分 | 意味 |
|---|---|
| `.symtab` の FUNC 記号 | カーネル。`_Z4mainPcPcPc` = `main(char*, char*, char*)` で、引数の数は名前から読む |
| `.symtab` の OBJECT 記号 | インスタンス (`sequence`、`aiecc_empty`)。`st_shndx` はカーネルの記号の番号 |
| COMDAT グループ (`.group.N`) | 署名がインスタンスの記号で、中身が `.ctrltext.N` |
| `.dynsym` | 名前が `"0"`、`"1"`… の記号は引数の番号、`.pdi.N` は PDI。`st_shndx` は書き込み先の `.ctrltext` |
| `.rela.dyn` | `r_offset` は記号の節の中の位置 |

再配置の種類 (XRT 2.21.75 の `xrt_module.cpp` の `patcher::patch_*` を読み、5 と 8 は記録した書き換え後の制御コードと突き合わせて確かめた。`w[i]` は `r_offset` からの i 語目、`A` は書き込むアドレス):

| 種類 | 名前 | 書き方 |
|---|---|---|
| 5 | shim_dma_48 | DMA のバッファ記述子 (TXN の BLOCKWRITE の BD) への 48 ビットのアドレス。`b = ((w[2] & 0xFFFF) << 32 \| w[1]) + A + addend + 0x80000000` (DDR の窓のずれ)、`w[1] = b & 0xFFFFFFFC`、`w[2] = w[2] & 0xFFFF0000 \| b >> 32` |
| 8 | address_64 | `w[0] = lo(A)`、`w[1] = hi(A)`。addend も窓のずれも足さない。PDI の BO のアドレスを TXN の LOADPDI に書く |
| 4 | control_packet_48 | 5 と同じ計算を `w[2]`、`w[3]` (`(w[3] & 0xFFF) << 32`) に |
| 3 | scalar_32 | `mask = st_size`、`w[0] = w[0] &^ mask \| v & mask` |

- ABI 版が 1 の ELF だけは、種類を `addend & 0xF`、addend を `addend >> 4` から読む。IRON の ELF は 0x21 (主版 2) で、種類は `ELF32_R_TYPE`
- `.dynsym` の特別な記号: `scratch-pad-ctrl` (制御コードが読むスクラッチパッドの BO。大きさは `st_size`)、`control-packet` (`.ctrldata`)、`ctrlpkt-pm-*`、`scratch-pad-mem` (プリエンプションの退避)。今回の 2 演算の ELF にはどれもない
- XRT は書き換え前の語を最初に覚えておき、引数が変わるたびにそこから書き直す。引数が変わらなければ、2 回目からの投入はコマンドの頭を書いて `EXEC_CMD` するだけ
- PDI の BO は XRT 2.21.75 ではモジュールごと (全ての run で共有)、XRT の master では run ごと。`BO_DEV` は 32 KiB 境界に置かれる
- コマンドの頭の語は XRT が書いたものを記録すると `0x3b00d001` (上位 4 ビットの種類欄が 3)。ドライバは opcode と語数だけを読む

未確認で、実装の中で確かめるもの:

- ctrl scratchpad (呼び出しごとの値)。IRON の `ParameterScratchpad` は `scratch-pad-ctrl` の BO に位置などを書く。LLM の ELF で、この記号と、制御コードへのアドレスの書き込み (種類 5 か 8) を確かめる
- 1 つの ELF に複数のコマンドがある場合 (`Plan.commands`。ホストの処理を挟むときや、スクラッチパッドの語数が 32 を超えるとき)
- 各 BD の BLOCKWRITE の後ろに TXN の DDR_PATCH (0x81、`arg_idx`、`arg_plus`) が残っている。ELF の流れでファームウェアがこれをどう扱うかはソースからは読めない。XRT と同じものを送るので、同じに振る舞うはず
- 知らない種類の再配置は必ずエラーにする

### 3.3 API

`ProgramSource.ELF` (design.md 5.4 で予約済み) と、インスタンス名つきのカーネル名を受け付ける。

```go
prog, err := kr.Load(ctx, hwnpu.ProgramSource{Path: "decode.elf"}) // 拡張子か ELF の頭で判別
k, err := prog.Kernel("main:sequence")
run, _ := k.NewRun()
run.SetBuffer(0, input).SetBuffer(1, output).SetBuffer(2, scratch)
```

- 引数の BO が変わったときだけ制御コードを書き換える (書き換えの位置は読み込み時に表にしておく)
- 複数の `Program` が 1 つのヒープを分け合う。ヒープは npu4 なら 512 MiB まで広げられる。制御コードは数 MB になりうる (Llama のデコードの全演算)
- 偽のドライバ (`xdnasim`) に ELF のコマンドを足し、制御コードの書き換えを検査する

## 4. 何を IRON の外から渡すか

IRON の `CompiledGraph` が実行時に使うものを、全てファイルに書き出す。

| もの | IRON での出どころ | hwnpu での使い道 |
|---|---|---|
| ELF (版ごと) | `compiled.artifacts.image` (`design.elf`) | 3 節で読み込む |
| 版の一覧 | `Model.shapes()`: デコードのステップ (入力なし) とプロンプトの塊 (`ids` の長さ) | 実行器が呼び分ける |
| 引数の割り当て | `FullELFCallable._argument_index`: `input`、`output`、`feedback`、scratch の bank | BO を作って番号どおりに渡す |
| バッファの配置 | `sequence.layout`: 名前 → (種類、オフセット、バイト数)。scratch は `BANK` (3.5 GiB) ごとの bank | 重み、KV キャッシュ、入出力の場所 |
| 重み | `recording.weights`: 名前 → (配列、handle)。読み込み時に `_copy_in` で配置どおりに写すだけ | 下の重みの像をそのまま bank に読み込む |
| 呼び出しごとの値 | `artifacts.parameter_table` (スクラッチパッドの語) と `Carried` (デバイスで引き継ぐ値) | 位置、行数、開始位置を書く |
| 出力 | `recording.returned` の handle の配置 | ロジット (またはデバイスで引いたトークン) を読む |

重みは「デバイス上の並びのまま」の像として書き出す。IRON は読み込み時に重みを変形する (RoPE の表、並べ替え) が、hwnpu はそれを移植せず、変形後のバイト列を bank ごとのファイルにする。実行時は読み込んで BO に写すだけになる (mmap からの写しで、16.38 の prompt store と同じ扱い)。

## 5. 成果物と変換の道具

```
gemma-4-E2B-it.amd-npu2/
  manifest.json      版、引数、配置、パラメータの表、出力、IRON と mlir-aie の版、元の重みのハッシュ
  decode.elf         デコードの 1 ステップ
  prompt-256.elf     256 トークンのプロンプトの塊 (塊の大きさは版ごと)
  bank0.bin ...      デバイスの並びの重み (bf16)。KV キャッシュなどの状態は含めない (実行時に 0 で作る)
```

- 道具: `tools/amd/iron_export.py` (開発者の機械で一度だけ)。IRON のアプリケーション (`iron.applications.gemma4` など) を、NPU のない機械でも `set_current_device(from_name("npu2", n_cols=8))` でコンパイルし、上の全てを書く。IRON と mlir-aie の版を固定し、manifest に記録する
- 装置ごと: NPU2 (8 列、Strix、Strix Halo、Krackan) は full ELF。NPU1 (Phoenix、Hawk Point、4 列) は full ELF がないので、IRON と同じく「1 ステップごとの xclbin」で書き出す (`--device npu1 --cols 4`、design.md 16.57)。呼び出しごとの値は、mlir-aie が生成する命令列の C++ を命令列プログラムに直して持つ
- `hwnpu-dev convert` には `-backend amd` を足さない (Go では作れないため)。`hwnpu-chat` のカタログに AMD の成果物の置き場所 (URL とハッシュ) を持つ

## 6. 実行側

### 6.1 IRON の像の実行器 (`internal/llm/iron`)

- `Open(dir)`: manifest を読み、bank と入出力の BO を作り、重みの像を読み込み、版ごとの ELF を読み込む (ハードウェアコンテキストは版ごとに 1 つ。プロンプトとデコードの切り替えは 1 回 0.46 ms で、トークンごとではないので許せる)
- `Prompt(ids, start)` / `Step(id, pos)`: 呼び出しごとの値を書き、1 コマンド (または manifest の数) を投入し、ロジットを読む
- KV キャッシュは IRON の配置どおり bank の中にあり、ホストから読み書きできる BO_SHARE なので、`ExportRows` / `ImportRows` (16.38 の prompt store) はバイト列の写しで実装できる。巻き戻し (`Rewind`) は位置を戻すだけで済む (IRON のキャッシュは位置で書く)

### 6.2 IRON の版の作り方 (エクスポート時に決める)

hwnpu のエンジンは、ロジットを受け取ってホストで標本を引く (温度、思考の上限 16.32、投機的デコード 16.33)。IRON の既定のモデルはデバイスでトークンを引いて次の呼び出しに引き継ぐ (`Sample` と `Carried`) ので、エクスポートでは次の版を作る:

- デコード: 1 トークンを入れて **ロジット** を返す
- 投機的デコードの確認: k トークンを入れて k 行のロジットを返す (プロンプトの塊を全行のロジットを返す形にしたもの)。**測った結果、プロンプトの版の流用では行数によらずデコード 4.5〜8 ステップ分かかり得にならない (design.md 16.54)。デコードと同じ演算で k 行を処理する版が IRON 側に要る**
- プロンプト: 塊を入れて最後の行のロジットを返す。Gemma 4 は KV を共有する層 (E2B の後ろ 20 層、E4B の 18 層) を最後の行だけに通す (`tools/amd/iron_gemma4.py`、design.md 16.80)。キャッシュは IRON のままと同じで、4K のプロンプトは E2B (bf16、q4 とも) で 2.3 倍速く電力量 −56 %、E4B で 1.7 倍、−40 %。IRON のままの版は `iron_export_lm.py gemma4full` (`gemma4mmfull`)

デバイスでのサンプリング (ロジットをホストに読まない分速い) は、まず測ってから。ロジットは Gemma 4 なら 262144 × bf16 = 512 KiB で、50 GB/s の DRAM では読み出しは問題にならない。

### 6.3 `chat.Engine` との境目

`chat.Engine` が `decode.Session` に求めているもの (`Q`、`Qs`、`Cache`、`Pos`、`Reset`、`Mark`、`Save`、`Rewind`、`Step`、`Speculate`、`RowBytes`、`ExportRows`、`ImportRows`、`Resume`、`Migrate`) を interface にし、`decode.Session` と IRON の実行器の両方が満たす形にする。違い:

- IRON は埋め込みをデバイスで引くので、入力は埋め込みではなくトークン ID。interface の入力をトークン ID にし、Core ML 側は今までどおりホストで埋め込みを引く
- KV キャッシュの段階 (16.20、16.37) は IRON にはない (`max_seq_len` で 1 つ)。`Migrate` は何もしない
- 画像と音声: Gemma 4 E2B の塔は IRON の多モーダルのモデル (`gemma4mm`) で書き出して動く (design.md 16.55)。1 回のプロンプトに画像 1 枚と音声 1 本まで

### 6.4 バックエンドの選択

`WithBackend("coreml")` の 6 か所 (`chat/engine.go`、`chat/embed.go`、`systemone/model.go`、`speech/speech.go`、`hwnpu-dev generate`、`hwnpu-dev powerbench`) を、モデルの成果物の種類 (Core ML のパッケージ、OpenVINO IR、AMD の manifest) から決める。Intel の設計 (intel-npu-models.md 7.1) と同じ作業なので共通にする。

## 7. モデルの順番

1. **Gemma 4 E2B (テキスト部、bf16)**: IRON の既存のアプリケーション。AMD が毎晩精度を確かめていて、hwnpu も Apple で対応済み (チャットの型、トークナイザー)。実行器と full ELF の正しさを、移植の誤りと切り分けて確かめられる。重みは Hugging Face から認証なしで取れる。見込み 5〜6 トークン/秒
2. **LFM3-1.7B (bf16)** (2026-11-04 済み、[design.md](design.md) の 16.66。hwnpu の `tools/amd/iron_lfm3.py`、8.7 トークン/秒): IRON のアプリケーションを書く (Python)。部品は IRON に揃っている (RMSNorm、GEMV/GEMM、RoPE の部分回転、スライディング窓の注意、depthwise の 1 次元畳み込み、SwiGLU)。`port-architecture` スキルと同じく Hugging Face のロジットと照合する。重み 3.4 GB/トークンで 50 GB/s なら上限 14 トークン/秒、実際は 8〜10 と見込む
3. **4 ビットの重み** (2026-11-05、Gemma 4 で済み、13 節): q4nx (FastFlowLM の形式、32 個ごとの scale と min) の GEMV を hwnpu 側に書き (`tools/amd/iron_q4.py`、`kernels/q4_mv.cc`)、プロンプトは IRON の `flm.DequantBFP` で bfp16 に戻して GEMM

## 11. 画像生成: Anima (`hwnpu-image`)

2026-11-05。Anima (circlestone-labs/Anima) を AMD の NPU だけで動かす。ComfyUI や Diffusers が担う「モデルの実行」の部分を hwnpu が受け持ち、UI やワークフローは持たない。

### 11.1 構成

| 部品 | 中身 | グラフ (`tools/amd/iron_anima.py`) |
|---|---|---|
| テキスト | Qwen3-0.6B (28 層、因果) の最終層の隠れ状態、その後 LLM アダプタ (6 層。T5 のトークンの埋め込みが自分自身と Qwen3 の隠れ状態に注意する) | `text` (1 つ、5 コマンド)。プロンプトは 512 トークンまで |
| DiT | Cosmos-Predict2 2B (28 ブロック、hidden 2048、16 ヘッド)。adaLN-zero の自己注意 (3 軸の RoPE)、テキストへの交差注意、GELU の MLP | `dit_in` (パッチの埋め込みと時刻の埋め込み)、`dit_blocks` (4 ブロック。1 つの ELF に重みのバンクが 7 組。ブロックの射影は 8 ビット (q8)、13 節)、`dit_out` |
| VAE | Qwen-Image の VAE (Wan 2.1 のもの) の復号器を 1 フレームで。因果 3D 畳み込みは時間方向の最後のタップだけ、時間方向の拡大は通らない | `vae/s0`〜`s9` (段ごとに 1 つ) |

ホスト (`internal/imagegen/anima`) がするのは、テンソルの計算でないもの: トークン化 (Qwen3 の BPE と T5 の Unigram、どちらも Go)、埋め込みの行の取り出し、時刻の正弦波、2 × 2 のパッチの並べ替え、flow matching の Euler のステップ (`x += (σ' − σ) v`)、ノイズ、PNG。Anima-Turbo は CFG 1 なので、負のプロンプトも 2 回目の DiT もない。

### 11.2 決めたこと

- **汎用のグラフの書き出し** (`tools/amd/iron_graph.py`、Go の `iron.Graph`): 言語モデルの版 (decode、prompt) を持たない、入力から出力への IRON のグラフ。manifest は `iron_export_lm.py` の版の形をそのまま使う。`variants` で、同じ ELF に別の重みのバンクを持てる (DiT の 7 組。コンパイルは 1 回)。バンクの像は末尾のゼロを切って書く (VAE で 8 GB → 0.2 GB、読み込み 10 秒 → 4 秒)
- **コマンドの大きさ**: 1 コマンドの制御コードはデバイスのヒープ (64 MiB) に、時間は amdxdna の 2 秒に収める。テキストは 7 層ごとに空のホストステップ (`iron.on_host`) でコマンドを分けた (80 MB の ELF が 5 コマンドに)。DiT では同じ分け方で最初のコマンドが `ERT_CMD_STATE_TIMEOUT` で止まった (原因は未調査) ので、4 ブロック (制御コード 20 MB、1.0 秒) を 1 コマンドにし、グループごとにグラフを呼ぶ。VAE は段ごとに別のグラフ
- **交差注意**: IRON の MHA はクエリより短いキーを取らない (クエリがキーの最後の行という前提)。4096 個のパッチを 512 行ずつに分け、それぞれ 512 個のテキストのキーに注意する
- **アダプタのマスク**: 注意のキーを有効な行に切る (`k[:n]`)。出力の有効でない行はホストがゼロにする (アダプタのマスクと 512 行への埋めと同じ)
- **VAE の畳み込み**: チャネルを最後に置いた、ゼロで囲んだ格子 (各行 W + 16 画素、上下に 1 行) にし、3 × 3 の畳み込みは Copy で近傍 9 画素を集めた im2col の行列と GEMM 1 回にする。結果の内側だけを次の格子に Copy で書き戻すので、囲みはずっとゼロのまま (RMS 正規化と SiLU はゼロをゼロのままにする)。行数は 256 の倍数に揃える (GEMM のタイルと、格子全体の写しが奇数の長さに分かれないため)。中段の注意は 1 ヘッド 384 次元で、MHA は `d=384` を取る (16384 行で 423 ms)
- **精度**: IRON の行列積の `MEDIUM` は A と B を bfp16 に丸める。DiT の射影で `HIGH` の 6.5 倍速い (4096 × 2048 × 2048 で 2.1 対 13.3 ms)。テキストは 1 枚に 1 回なので `HIGHEST` にした (時間は同じ 0.5 秒)。DiT と VAE は `MEDIUM` (`--dit-precision high` で選べる)

### 11.4 書き出しの手順

## 12. メモリ: 固定されるバッファを減らす (2026-11-05)

IRON の arena (bank) とグラフのバッファは amdxdna の BO_SHARE (shmem) で、作ったときから全ページが固定される。プロセスの RSS には出ず (Gemma 4 E2B で 0.43 GB)、`/proc/meminfo` の `Shmem` と `Unevictable` が増え、`MemAvailable` がその分減る (E2B で 9.3 GB)。スワップにも出ない。測るときは `Unevictable` の増え方を見る。

中身 (manifest の配置から):

| Gemma 4 E2B | 9.0 GB | 層ごとの埋め込みの表 (PLE) 4.4 GB、MLP 2.9 GB、embed_tokens (出力の行列と共有) 0.75 GB、KV キャッシュ 72 MB |
| Gemma 4 E4B | 14.3 GB | PLE 5.25 GB、MLP 6.2 GB、embed 1.25 GB |
| LFM3-1.7B | 3.7 GB | ほぼ重み。KV キャッシュ (12288) 264 MB。`--q4` で 1.64 GiB (13 節) |

したこと:

- **Anima: 段ごとに読み込む** (`internal/imagegen/anima`): テキスト、DiT、VAE の 10 段は同時には走らないので、走るときに読み込み、終わったら放す。最大は DiT の 5.0 GiB (DiT の重みを q8 にして 3.4 GiB、13 節)。絵はビット単位で同じ。読み込みはページキャッシュから 1 枚あたり数秒 (VAE の段は特徴マップが大半で、像のファイルは 0.16 GB)

  - Go 側はヒープが足りないとき (`ENOSPC`) デコードのランを放してやり直す (IRON と同じ)

## 13. 4 ビットと 8 ビットの重み (q4nx、q8) (2026-11-05)

`iron_export_lm.py gemma4 ... --q4` で、Gemma 4 の MLP (gate、up、down) と出力の行列を 4 ビット (q4nx)、注意の射影 (q、k、v、o) を 8 ビット (q8) にする。`--attn q4|bf16` で注意を 4 ビットか bf16 にもできる。

形式 (どちらもブロックは出力 32 × 入力 256、並びは `flm.DequantBFP` が読む順で、出力 64 ずつの列ブロックが連続。デコードとプロンプトは同じバイト列を読む):

- **q4nx**: FastFlowLM の Gemma 4 の形式 (mlir-aie の `flm_gemma4/q4nx.h`、IRON の `iron.operators.flm.q4nx`)。入力 32 個ごとに bf16 の scale と min、重みは `min + scale × code` (code は 0〜15)。1 重み 5 ビット (bf16 の 31 %)
- **q8**: hwnpu の形式。入力 32 個ごとに bf16 の scale、重みは `scale × code` (code は -127〜127、int8)。並びは q4nx と同じ (16 行の帯ごとに列優先)。1 重み 8.5 ビット (bf16 の 53 %)

演算 (`tools/amd/iron_q4.py`、カーネルは `tools/amd/kernels/q4_mv.cc` と `q8_mv.cc`):

- **デコード** (1 行): `QGEMV`。1 列に 2 コア。メモリタイルが列ブロックの 2 ブロック (出力 0〜31 と 32〜63) を 2 コアに分け、x を両方に配り、出力をつなぐ。q4nx は FastFlowLM の `q4nx_accumulate` (32 列の部分和を bf16 にしてから scale を掛け、min は x の 32 個ごとの和との積 1 回)。q8 は同じ形だが、部分和を bf16 1 つに丸めると 8 ビットの精度が消える (コサイン 0.9998) ので、上位と残りの 2 つの bf16 に分けて scale を掛ける (0.999992)
- **プロンプト** (複数行): q4nx は IRON の `flm.DequantBFP` でデバイス上で bfp16 に戻し、`flm.ProjectionGEMM` (bfp16 の B)。Gemma 4 はもともと `Precision.MEDIUM` (bfp16) で掛けているので、計算の精度は量子化の分だけ変わる。q8 は `QDequant` (hwnpu の演算。int8 を bf16 にして scale を掛け、16 行 × 8 列ずつ転置して書く) で bf16 の (N, K) に戻し、IRON の `F.linear` に渡す。`QDequant` は q4nx も戻せる (`iron_q4.PREFILL["q4"] = "bf16"`、Anima の DiT。下の「コアの丸めの向き」)
- **量子化** (q4nx): 32 個ごとに、[min, max] を少し縮めた候補 9 つから、code を決めたあと scale と min を最小 2 乗で合わせ直し、誤差の最も小さいものを選ぶ (llama.cpp の make_qkx と同じ考え)。単純な min-max より重みの誤差が 1 割小さい (E2B の 3 層目の gate_proj で 8.2 % → 7.3 %)。q8 は 32 個の最大の絶対値 / 127
- **トークンの埋め込み**: 出力の行列と共有 (tied) なので、出力側を 4 ビットにすると bf16 の行がなくなる。PLE と同じくホストの表 (`embed.bin`、12 節) にし、デバイスには塊の行数分 (3 MB) だけ置く
- IRON への手当て (hwnpu 側で、IRON は変えない): `F.linear` を差し替え、量子化した重みなら `q_linear` へ。`Operand.fits` が bfp16 の型で落ちる (bfp16 の B に呼び出しごとの行数があるとき) ので、バイトの並びで判定する。プロンプトの版の入力 `ids` は表を引かなくなっても読まれている必要があり、全体を 1 回写す (4 KiB)

単体 (`python tools/amd/iron_q4.py check OUT --fmt q4|q8 --n N --k K [--rows R] [--cores 1|2]`、`go run ./tools/amd/irongraph OUT`): NPU の出力と、量子化した重みでの float64 の積のコサインが q4nx で 0.99994 以上、q8 で 0.99999 (プロンプトの経路は bfp16 の GEMM で 0.99995)。速さ (1 行):

### コアの丸めの向き (2026-11-06)

AIE のコアは丸めのモードが切り捨て (負の無限大へ) のまま始まる。float から bf16 や bfp16 に狭めるたびに値が少しずつ下に寄り、入力 K 個にわたって足されると、入力に平均があるとき (Anima の DiT の活性) 出力の 1 割近い偏りになる。平均 0 の乱数の単体の試験では打ち消し合って見えない。IRON の `flm.DequantBFP` の README にも切り捨てとある。

- hwnpu のカーネル (`q4_mv.cc`、`q8_mv.cc`) は呼ばれるたびに最初に最近接偶数 (`aie::set_rounding(conv_even)`) にする。1 命令で、速さは変わらない
- q4nx をプロンプトで bf16 に戻す `q4_dequant` (`QDequant` の q4nx 版) を足した。IRON の `DequantBFP` は変えない。量子化した DiT も `--check` の参照 (IRON の `F.linear` に戻した重み) と比べられる (512 × 512 の 4 ブロック、q8 でコサイン 0.999987)
- 単体 (`iron_q4.py check --x-mean 1`、2048 × 2048、4096 行): `DequantBFP` の経路はコサイン 0.968、`QDequant` (bf16) の経路は 0.99994、q8 は 0.99996
- Anima の DiT (diffusers の fp32 とのステップ 0 の速度の相対誤差): NPU の q8 は 0.088 → 0.031、q4nx は 0.244 → 0.087。NPU の bf16 は 0.025、CPU で量子化だけなら q8 0.007、q4nx 0.092 で、直したあとの差は量子化と NPU の bf16 の計算の分だけ。絵は上の表のとおり
- 言語モデル (正規化した、平均がほぼ 0 の入力) では差がほとんど見えない: 書き出し直した Gemma 4 E2B の q4 の NPU の bf16 との KL は 0.097 → 0.093 (最上位の一致 90.0 %、同じ)、LFM3-1.7B は 0.0364 → 0.0362 (92.0 → 93.0 %)。プロンプトの q4nx も `QDequant` (bf16) にすると KL は同じ (0.094、0.0368) で塊が 5〜9 % 遅くなる (LFM3 の 2048 で 628 → 684 ms、E2B の 1024 で 940 → 988 ms) ので、言語モデルの q4nx は `DequantBFP` のまま (`PREFILL["q4"] = "bfp16"` が既定)。デコード (`QGEMV`) は丸めだけが変わり、速さは同じ (LFM3 88 ms、E2B 128 ms)。今ある書き出しはそのまま動き、書き出し直すと丸めが直る

ほかのビット数: AMD の NPU (AIE2P) がそのまま掛けられるのは bf16、bfp16 (8 値で指数 1 つ、約 9 ビット)、int8 など。4 ビット、6 ビット、8 ビットのブロック形式は、コアの中で bf16 に戻しながら掛ける (q4nx、q8 と同じ) ので、形式ごとに GEMV のカーネルと、プロンプト用に bf16 か bfp16 へ戻す演算が要る。q8 は q4nx の形を元にしたので、6 ビットも同じ並びで足せる。

### GPTQ: 4 ビットの符号を活性を見て選ぶ (`tools/amd/q4_gptq.py`、2026-11-06)

`iron_q4.quantize` は重みを 1 つずつ群の 16 段の最も近いものに丸める (RTN)。重みの誤差は小さいが、層の出力の誤差が最小になるわけではない。GPTQ は層の入力の H = E[x xᵀ] を校正の文で集め、入力の列を順に量子化して、その誤差をまだ量子化していない列に H で重みを付けて送る。出力の誤差を最小にする選び方で、形式は同じ (32 個ごとの bf16 の scale と min は、GPTQ がその群に着いたときに `iron_q4._fit` で合わせ直す)。変わるのは符号と scale、min の値だけで、NPU の演算、速さ、メモリは変わらない。

```
python tools/amd/iron_export_lm.py gemma4 ~/models/gemma-4-E2B-it EXPORT --q4 --q4-codes OUT/codes
```

### 6 ビットの重み (q6、2026-11-08)

q8 と同じブロックと並びで符号を 6 ビット (−31〜31) にした形式 (`iron_q4.quantize6`、`kernels/q6_mv.cc`)。符号の下位 4 ビットを q4nx と同じニブルに、上位 2 ビットを 128 個ごとに 32 バイトに置く。6.5 ビット/重み。GEMV は q8 とほぼ同じ時間 (8192 × 2048 で 0.42〜0.47 ms、q8 0.43〜0.50 ms、q4 0.30〜0.35 ms: 上位ビットの取り出しで律速) なので、得るのはメモリと精度 (重みの相対 RMS 誤差 q4 0.071、q6 0.022、q8 0.005)。

- 小さい Qwen3.5 (0.8B、2B) の MLP と出力の行列: q4 では GPL の KL が 0.34 / 0.16 に崩れる (GPTQ でも 0.30) が、q6 で 0.044 / 0.019 (`iron_export_lm.py qwen35 --q4 --mlp q6 --head q6`、design.md の 16.104)。`--verify 3` も足すと下書きを確かめる版がつく (下の節)
- Anima の DiT: `iron_anima.py --dit-attn q6 --dit-mlp q6` (上)
- GPTQ と CPU の見積もり: `q4_gptq.py --fmt-q4 q6 --head q6`

### 下書きを確かめる版 (`--verify`、2026-11-08)

`iron_export_lm.py ... --verify 3` は、3 トークン (次のトークンと下書き 2 つ) を 1 回で確かめる版 (`verify.elf`) を足す。全部の行のロジットを返し、各行の鍵と値と、行ごとの GDN の状態を書く。AMD の NPU の hwnpu-chat はこの版があればプロンプトからの下書きを確かめ、採用しなかった行の状態はホストが戻す (`iron.Model.Keep`)。ロジットはデコードのステップとビット単位で同じなので、temp 0 の文は変わらない。Qwen3.5-0.8B q6 で 1 回 1.27 ステップ、生成 82 → 62〜72 ms/トークン (design.md の 16.117)。今は Qwen3.5 (密)、q8 と q6 の射影だけ (q4 の数行の GEMV と、Gemma 4 / PLaMo 3 / LFM3 はまだ)。`HWNPU_IRON_DRAFTS=0` で使わない。

#### Qwen3.6-35B-A3B (`tools/amd/qwen36_gptq.py`、2026-11-08)

`q4_gptq.py` はモデル全体を fp32 で持つので、36 B パラメータ (fp32 で 140 GB) の Qwen3.6 は入らない。`qwen36_gptq.py` は 1 層ずつ重みを safetensors から読み (meta デバイスのモデルに差し込む)、校正の文のその層の前の隠れ状態だけを持って進める。層の 4 ビットの重みを GPTQ で選び、量子化した重みで次の層への入力を作る。

## 14. 画像生成: Sana と Sana-Sprint (`hwnpu-image`、2026-11-09)

### 14.2 決めたこと

- **割り算のない線形注意**: IRON に要素ごとの割り算がない。ヘッドの出力は `N / D` (`N = relu(q)(relu(K)ᵀV)`、`D = relu(q)·Σrelu(K)`)。値の行をヘッドあたり 64 行に並べ (値 32 行、定数 c の行、0)、1 回の行列積で各ヘッドの行 `[N, cD, 0…]` を作る。その 64 の行を RMS 正規化すると cD が支配して `8N/(cD)`、重み c/8 で `N/D` (誤差は `(N/D)²/c²` の割合。c = 4096)。D = 0 のヘッドは 0 になり、参照の eps と同じ。`relu(K)ᵀ` は重みを左に置いた行列積 (`F.linear(W, h)`) で作り、q と k の正規化がある Sana-Sprint は単位行列との HIGHEST の積で転置する。線形注意の 2 つの積は HIGHEST
- **ヘッドの埋め**: 重みを左に置く積 (MEDIUM、flm.ProjectionGEMM) は行が 256 の倍数。値の 64H 行と、正規化のないモデルの鍵の 32H 行がそうなるようにヘッドを 0 で足す (Sana 600M は 36 → 40、1.6B は 70 → 72)
- **深さ方向の畳み込み**: 行列積にしない。トークンの格子を 0 で囲んだ状態に写し (各行の後に 0 の画素)、9 個のタップのそれぞれが帯の連続した行の範囲になるので、行ごとの重みの積と和 (要素ごと) で計算する。VAE の 5 × 5 も同じ
- **交差注意**: MHA は `d` が 64 の倍数なので、ヘッド (72、112) を 128 に 0 で埋める。キーは有効な行 (`k[:nk]`)。**鍵から先頭の行の鍵を引く** (softmax はクエリごとの定数を消すので答えは同じ): Sana 600M のスコアは q と k の正規化がなく、絶対値が約 1750 で行の中の差は数単位しかない。MHA はスコアを bf16 で持つので刻みが 8 になり、条件つきの出力だけがずれ、CFG で 4.5 倍に広がって 20 ステップで絵が崩れた (潜在のコサイン 0.79)。引くと 0.960 (CPU の bf16 の 0.962 と同じ)
- **MHA のスケール**: MHA は scale × log₂e を bf16 に丸める (最大 0.4 %、温度のずれ)。scale を ln 2 (積がちょうど 1) にして、本来のスケールはクエリの重みに float32 で掛けておく。Gemma 2 も同じ。この絵では効果は見えなかった
- **Gemma 2 の softcap**: 注意のロジットの softcap (50) は入れない。CPU で外しても残す行のコサインは 0.99999、画像の PSNR 47 dB
- **Gemma 2 の q8**: 固定メモリを 4.0 → 2.3 GiB。q8 のブロックは入力 512 単位なので、入力 2304 列は 0 で 2560 列に写してから積む。精度は HIGHEST のまま (QDequant で bf16 に戻してから)。HF との行のコサイン 0.9998〜0.99999 (bf16 は 0.9999)。2026-11-10 から既定は q6 (14.6)
- **VAE の近道**: conv_in の入力チャネルの繰り返しと、拡大ブロックの近道 (チャネルを画素に並べ替え) は 3 × 3 の中央のタップに足す。チャネルを半分にする拡大は出力の行の偶奇で使う入力チャネルが変わるので、偶数行と奇数行を別の重みで積む。im2col はチャネル 1024 で DMA の次元の上限 (1023 語) を超えるので、縦のタップごとに 3 回に分けて写す

### 14.4 書き出しの手順

Efficient-Large-Model の diffusers のリポジトリをそのまま置く (`transformer/`、`vae/`、`text_encoder/`、`tokenizer/`、`scheduler/`)。Gemma 2 (`text_encoder/`、`tokenizer/`) はどのリポジトリも同じファイルなので、1 つを落としてほかはシンボリックリンクでよい。

```bash
python tools/amd/iron_sana.py ~/models/Sana_Sprint_0.6B_1024px ~/models/sana-sprint-0.6b-1024.amd-npu2
go run ./cmd/hwnpu-image generate --model ~/models/sana-sprint-0.6b-1024.amd-npu2 "..." --seed 1 -o out.png
```

`--only` で部品を選べる (`text caption dit_in dit_blocks dit_out vae`)。`--text-format q8` / `bf16` は Gemma 2 を q8 (固定 2.3 GiB) / bf16 (4.6 GiB) に、`--no-prefix` は指示文も毎回計算する前の形 (512 行) に (14.6)、`--dit-precision high` は DiT の射影を HIGH に (Sana 600M で絵は同じ、2.5 倍遅い)。確かめ方は Anima と同じ: `--check` と `go run ./tools/amd/irongraph DIR`、全体は `tools/ref/ref_sana.py` の `noise` を raw の float32 にして `--noise` に (Sana-Sprint はステップ + 1 個)、`--latents` で最後の潜在、`--dump DIR` で各ステップの DiT の出力とキャプション。

### 14.6 Gemma 2: 指示文を書き出しに持ち、続きだけを計算する (2026-11-10)

Sana はプロンプトの前に毎回同じ指示文 (diffusers の complex_human_instruction、`<bos>` を含めて 208 トークン) を付ける。Gemma 2 は因果的な注意なので、指示文の行のキーと値と出力は、後に何が続いても同じ。前の形は 512 行を毎回計算していた (このプロンプトの 216 トークンのうち、6 割は空回り)。

- **書き出し** (`iron_sana.Prefix`): 指示文を `tokenizers` で区切り、Gemma 2 を numpy の float32 で通す (transformers と同じ計算。注意の softcap も入れる。15 秒)。各層のキー (RoPE の後) と値の先頭 192 行 (塊の倍数) をグラフの定数に、208 行の最後の隠れ状態を `prefix_out.bin` に、トークン列を manifest の `prefix` に書く
- **グラフ**: 64 行の塊で、呼び出しごとの値は `start` (64 の倍数) だけ。各層で定数のキーと値をキャッシュ (512 行) の先頭に写し、塊の行のキーと値を `start` から書き、`start + 64` 行のキーに因果的に注意する (MHA の `kv_len` 512、パイプライン 1 本)。塊の中のプロンプトより後の行は 0 で、因果的な注意なので前の行に影響しない
- **Go** (`sana.textStart`): プロンプトのトークン列が指示文と先頭から一致する長さを、持っている 192 行と塊の倍数に切り捨てて `start` にする。最後の指示文のトークンはプロンプトの最初の語とつながることがあるので、一致はたいてい 207。否定のプロンプトは `<bos>` だけが一致し、`start` 0 から計算する (定数を写した後に塊の行で上書きする)。長いプロンプトは塊を続けて呼ぶ (キャッシュはグラフを開いている間残る)。`start` より前の行の出力は `prefix_out.bin` から
- **呼び出しごとの行の数で縛る形はやめた**: IRON の `x[:rows]` で縛ると、8 コアに分ける RMSNorm の呼び出しごとの回数が `ceil(rows / 8)` になり、Go が計算できる一次式で表せない (`words without a form`)。IRON の lm と同じく、固定の塊と `start` だけにした。`start + rows` のような 2 つの値の和も表せない

### 14.7 VAE: タップごとの行列積と、同じ形の段をまとめる (2026-11-10)

1 枚 20 秒のうち VAE が 13 秒だった。段 9 (1024² × 128 チャネルの ResBlock 1 つ、1.15 秒) を、演算ごとにコマンドを分けた計測用の書き出し (`IRON_SANA_PROFILE=1`、`HWNPU_IRON_TIMING=1`) で分けると、im2col の写しが 63 % (733 ms)、行列積 21 %、後処理 8 %、格子への写し 8 %。写しは連続する長さが 3C (768 バイト) の細かい DMA で、6.8 GB/s しか出ていなかった。

- **タップごとの行列積** (`--vae-conv taps`、既定): 格子は「チャネルが最後、行に Wp 画素」なので、3 × 3 の各タップの入力は格子の連続した行の範囲になる。タップごとに行列積 (K = C) をして 9 個を足す。im2col の写し (格子の 9 倍) がなくなる。64 行ずつで、塊ごとにコマンドを分ける (制御コードをデバイスのヒープ 64 MiB に)。段 9 は 1.15 → 0.76 秒。行列積に足し込む出口処理はない (活性化だけ) ので、足し算 8 回が残る (塊あたり約 7 ms)。偶奇で重みを変える拡大 (チャネルを半分にする 3 つ) は im2col のまま。im2col の上限を 64 → 256 MiB にするだけでは 9 % しか速くならない (演算の切り替えの回数は主ではない)
- **同じ形の段をまとめる**: 段 9〜11 (ResBlock 3 つ) と段 3〜4 (EfficientViT 2 つ) を 1 つの段に (13 → 10 段)。パイプラインの中では、次の段の読み込み (重みと大きな格子の確保) が重なって実行が 0.76 → 1.1 秒に遅くなっていたので、読み込みが減るぶん効く。ブロックの間でコマンドを分ける。格子の状態は使い終わったら返して同じ形の次の格子に使い (`free_grid`)、2 つ目以降の ResBlock は入力の格子に上書きする (2 つ目の畳み込みは x を近道の足し算で同じ行しか読まない)。上書きしないと格子 1 枚 (260 MiB) 分だけ固定の最大が増えた (2409 → 2670 MiB)
- **段を閉じる処理を裏に** (`sana.VAE.Decode`): 前の段を閉じる (50〜136 ms) のを次の段の実行と重ね、次の次の段を読む前に待つ (載るのは 2 段まで)。単独では差がほとんど見えなかった
- **拡大を低い解像度の 4 つの位相で** (`--vae-up phase`、既定): 最近傍の 2 倍の後の 3 × 3 は、出力の画素 (2y + py, 2x + px) ごとに低い解像度の 2 × 2 の畳み込みになる。縦は、py = 0 なら低い行 y − 1 に核の上の行、y に中と下の行の和、py = 1 なら y に上と中の和、y + 1 に下の行 (横も同じ)。位相ごとの 4 タップの重みを書き出しのときに作り (`_up_phases`)、各位相は低い解像度の格子の行の範囲に 4 回の行列積の和で、出力の格子の 2 行おき 2 画素おきに写す。偶奇で重みを変える拡大も py ごとの重みで同じ形になる。積は 4/9、拡大した格子 (1024² × 256 で 545 MB) が要らない
- **格子を行列積が直接読む** (`iron_gridgemm.GridGEMM`、`--vae-conv grid`、既定): IRON の `flm.ProjectionGEMM` (bfp16) を継承し、A を読む DMA の並び (runtime sequence の `TensorAccessPattern`) だけを差し替える。im2col の行列 (M, 9C) の 1 行は「縦のタップごとに、格子の連続した 3C 要素」なので、論理上の行は C 要素ずつ重なり、K のタイル (3C) は Wp·C 要素ずつ離れている。次元の数は密な A の読み方と同じで、刻み幅だけが違う。C ≤ 170 (3C ≤ 512) は 9 タップを 1 回の行列積に、それより大きい C は縦のタップごとの 3 回 (K = 3C、連続) と足し算 2 回。写しもタップの足し算もない。拡大の位相 (2 × 2) も同じく、横の 2 タップが隣り合う 2 画素 (2C 連続) なので 1 回の行列積 (K = 4C) か、縦のタップごとに 2 回。1024² の ResBlock 3 つの段 2.7 → 1.4 秒、head 0.50 → 0.38 秒。確認用の参照 (`reference`、`tolerance`) は、論理上の A を組み立てて計算する
- **VAE の線形注意を MEDIUM に** (`--vae-attn-precision`、既定 medium): bfp16 は K の方向の 8 要素で指数を共有するだけなので、定数 c (4096) の行が値の行と指数を共有しない。絵は HIGHEST と 51.6 dB で、CPU との PSNR も同じ。VAE 6.6 → 6.2 秒
- 結果 (Sana-Sprint 0.6B、1024²): VAE 12.3 → **6.3 秒**、1 枚 20 → **12 秒** (テキストの変更 14.6 を含む)。Sana 600M 1 枚 67〜70 → 59 秒。画素は前の VAE と 50〜54 dB で、CPU の参照 8 枚との PSNR は変わらない。**固定の最大 2409 → 1936 MiB** (位相の拡大で。プロセスを足して 2.27 GB)。1152 × 896 も同じ

### 14.8 残り

- VAE は約 6.3 秒 (1 枚の時間の半分、14.7)。低い解像度の EfficientViT の段 (0〜3) が計 2.1 秒、1024² の ResBlock 3 つが 1.4 秒。EfficientViT の線形注意は、ヘッドごとのブロック対角の積を、全部のヘッドの密な行列積とマスクで計算していて、要る計算の H 倍 (64² で 32 倍) をしている。深さ方向の畳み込みは要素ごとの掛け算と足し算 (5 × 5 で 49 回) で、IRON の `axpy` は係数がスカラーだけなので 1 回にできない
- 書き出しは 1 つの大きさ。大きさごとに書き出す (`hwnpu-image generate --model` はその書き出しの大きさで描く)
- Mac は 4 つの Sana を Core ML で (design.md 16.143)。Intel (OpenVINO) は未対応
- Sana 1600M (1.0) は Sana 600M と同じ VAE 1.0、1.6B の DiT で、同じ手順で書き出せるはず (確かめていない)

## 15. 深度推定: Depth Anything 3 (`hwnpu-image depth`、2026-11-09)

Depth Anything 3 (Apache-2.0) を AMD の NPU だけで動かす。4 つの版に対応する。

| 書き出し | 中身 | 出力 |
|---|---|---|
| `da3mono-large` (DA3MONO-LARGE) | DINOv2 ViT-L/14 (24 ブロック) と DPT | 相対の深度 (大きいほど遠い) と空 |
| `da3metric-large` (DA3METRIC-LARGE) | 同じ構造 | 深度 × 焦点距離 (画素) ÷ 300 = メートル (`--focal` か `--fov`) と空 |
| `da3-small` / `da3-base` (DA3-SMALL / BASE) | ViT-S / B、複数視点用の注意 (1 枚として)、DualDPT の深度の側 | 相対の深度と確信度 |

### 15.1 構成

| 部品 | 中身 | グラフ (`tools/amd/iron_da3.py`) |
|---|---|---|
| ViT | パッチの埋め込み (14 × 14 × 3 = 588 値を 640 列に) とブロック。4 つの層を最後の LayerNorm に通して出す。位置埋め込みは書き出しの大きさに双三次で補間しておく (DINOv2 の `interpolate_offset` まで同じ、CPU とのコサイン 1.000000)。layer scale は出力の射影に掛けておく | `vit` (6 ブロックごとに 1 コマンド) |
| ヘッド | 4 つの特徴を 1 × 1 で射影し、4 倍と 2 倍は転置畳み込み (カーネル = ストライド。GEMM 1 回と、カーネルの位置ごとの列を画素に写す Copy)、1/2 倍はストライド 2 の 3 × 3、各解像度の 3 × 3、上から順の融合 (残差の畳み込み 2 つと双線形の拡大)、3 × 3、画像の大きさへの双線形、小さなヘッド (DPT は深度と空を並べて 1 回の 3 × 3 と 1 × 1、DualDPT は深度と確信度) | `head` (1 コマンド) |

書き出しは縦横比ごとの大きさ (長辺 504: 504 × 504、504 × 378、378 × 504、504 × 280、280 × 504) のフォルダを持ち、`model.json` が並べる。ホスト (`internal/vision/depth`) は、画像に最も近い縦横比 (比の対数の差) を選び、その大きさに引き伸ばし (PIL と同じ双三次。公式は OpenCV で縦横比を保って長辺 504)、正規化し、パッチを切る。深度の出力の exp、空 (0.3 以上) を残りの深度の 99 パーセンタイルにする (公式は 10 万点を抜き出す)、確信度は exp + 1、元の大きさへの双線形の戻し、PNG を受け持つ。大きさを変えるときはその大きさのグラフを読み込み、前のものは放す。

### 15.2 決めたこと

- **格子**: Sana の VAE と同じ 0 で囲んだ格子の im2col と GEMM だが、パッチの格子 36 や 27 は 16 で割り切れないので、行を 16 の倍数まで 0 で足し (読むだけ)、1 行の画素数 Wp も 16 の倍数にした (`Grid`)。ストライド 2 の出力は切り上げ (27 → 14)
- **チャネル**: ヘッドの全チャネル (DA3-SMALL の 48、96、32 など) を 0 で 64 の倍数に埋める
- **双線形 (align_corners)**: 補間の行列 (行と列を 64 の倍数に 0 で埋める) を左に置いた GEMM 2 回 (`GEMM.step(A, X, b_col_maj=False)`)。列の向きは画素を (W, H·C) に転置する Copy をはさむ。融合ブロックの 1 × 1 は拡大の前にした (どちらも画素ごとに線形で入れ替えられる。4 倍軽い)
- **行の数**: 射影の GEMM (MEDIUM) は行が 256 の倍数なので、特徴はクラストークンの行ごと積み、画素へ写すときに 1 行ずらす
- **複数視点のモデルを 1 枚で**: 視点をまたぐ注意 (alt_start からの奇数のブロック) は 1 枚なら同じトークンの注意で、違いは RoPE の位置 (パッチがすべて (1, 1)) だけ。カメラトークンは alt_start でクラストークンの行を置き換える (行のマスクと定数の行)。2 次元の RoPE (行で前半 32 次元、列で後半) は、q と k の次元を並べ替えて (重みの行で) IRON の RoPE (j と j + 32) に載せる。ヘッドごとの q と k の LayerNorm も並べ替えた重みで。特徴は「最後の局所のブロックの出力」と「正規化した出力」を並べた 2 倍の幅 (`cat_token`)。DualDPT の UV の位置埋め込みは定数として足す。光線 (カメラ姿勢) の補助ヘッドは作らない

### 15.6 複数の画像 (`iron_da3.py --views N`、2026-11-09)

DA3-SMALL / BASE を N 枚の同じ場面の画像に同時に使う: 深度は全部で 1 つの尺度、カメラ (世界からカメラへの [R | t] と内部パラメータ) も出す。`hwnpu-image depth --model <--views の書き出し> a.jpg b.jpg c.jpg` が `cameras.json` と各画像の深度を書き、`--ply` で全部の画素を参照の視点の座標で 1 つの点群にする。

- ViT は視点のトークンを詰めて並べる (視点 i の行は i × 973 から、`Config.tall`)。視点の中の注意は各視点の先頭からの窓 (1024 行、鍵は `k[s : s + 1024][:973]`。窓の後ろの行は次の視点が上書きする)、視点をまたぐ注意は全部の行 (`k[:N × 973]`)。埋めた行が視点の間に入らないので、マスクは要らない
- グラフはブロック 3 の前で 2 つに分ける (`vit_a`、`vit_b`): 公式はそこでクラストークンから参照する視点を選び (`saddle_balanced`、3 枚以上) 先頭に並べ替える。選択と並べ替えはホスト (`depth.SaddleBalanced`、公式の値と一致するテスト)。カメラトークンは参照の視点とほかの視点で別。ヘッドは 1 枚のものを視点ごとに
- カメラ: 最後の層のカメラトークン (局所の出力と全体の出力を並べた 768) に cam_dec (小さな MLP) をホストで掛け、四元数と画角から [R | t] と焦点距離にする (公式の `pose_encoding_to_extri_intri`、`affine_inverse`)
- 3 枚 (504 × 378、DA3-SMALL): 1.1 秒 (ViT 0.39 秒、ヘッド 3 回 0.47 秒)。参照する視点をそろえると公式と深度のコサイン 0.9998、相対誤差 1.2 %、回転の差 0.0016 以下、焦点距離の差 1 % 前後
- 注意: ほぼ同じ画像どうしでは参照する視点の選択が同点に近く (類似度の差 3 × 10⁻⁵)、NPU の bf16 の差で公式と違う視点を選ぶことがある (`--ref` で指定できる)
- 書き出しは視点の数と大きさを固定 (`--views 3 --sizes 504x378`)

- 複数の画像は書き出しごとに枚数が決まる。光線の補助ヘッド (`use_ray_pose`) と、カメラを与える使い方 (`cam_enc`) は未対応

## 16. 深度と形: MoGe-2 (`hwnpu-image depth`、2026-11-09)

MoGe-2 (Ruicheng/moge-2-vit{s,b,l}-normal、MIT) を AMD の NPU で動かす。1 枚の画像から、焦点距離を知らなくてもメートル単位の深度、点群、法線、有効な画素のマスクを出す (焦点距離は点群から解く)。`hwnpu-image depth --model ~/models/moge-2-vits.amd-npu2` で使い、`--normal` で法線、`--sky` でマスク、`--raw` で深度と点群の float32。

### 16.1 構成

| 部品 | 中身 | グラフ (`tools/amd/iron_moge.py`) |
|---|---|---|
| ViT | DINOv2 (ViT-S / B / L、DA3 と同じ VitBlock)。中間の層を最後の LayerNorm に通し、層ごとの 1 × 1 を足し合わせる。クラストークンに尺度の MLP | `vit` |
| neck | ConvStack: パッチの格子の 1、2、4、8、16 倍。最初は特徴と視野平面の UV (定数) の 1 × 1、ほかは UV の 1 × 1 (定数) を足し、残差ブロック (ReLU、3 × 3、ReLU、3 × 3、足す。MoGe-2 は正規化なし)、次の倍率へ 2 × 2 の転置畳み込みか双線形 2 倍と 3 × 3 | `neck` (5 つの倍率の出力) |
| ヘッド | 点、法線、マスクの ConvStack (neck の各倍率を 1 × 1 で受ける)。16 倍の出力を 1 × 1 で 3、3、1 チャネルに | `heads` (1 つのプログラムに重みのバンクが 3 組) |

3 × 3 はすべて端の画素を複製して詰める (`padding_mode="replicate"`)。格子の各行の両側と上下の行に端の画素を写す (`Grid(rep=True)`、`fill_pads`)。畳み込みの部品は DA3 のヘッドと共通 (`iron_da3.ConvOps`)。`model.pt` は torch なしで読む (`TorchZip`: zip の pickle から辞書とテンソルの組み立てだけを許す)。

ホスト (`internal/vision/moge`) は、近い縦横比の大きさに双線形 (antialias) で引き伸ばし、パッチを切る。後処理は公式の `infer` と同じ順: ヘッドの出力を画像の大きさへ双線形 (align_corners=False)、点の z の exp (xy に掛ける)、マスクの sigmoid、法線の正規化、64 × 64 に間引いた点群で z のずれと焦点距離を解く (1 変数の Levenberg–Marquardt。公式は scipy の least_squares)、深度 = (z + ずれ) × exp(尺度)、点群は深度と内部パラメータから作り直す。

書き出しは `--tokens` (既定 2500。公式の num_tokens、1200〜3600) と縦横比 (1:1、4:3、3:4、16:9、9:16) ごとの大きさ (例: 50 × 50 パッチの 700 × 700、58 × 43 の 812 × 602) を持つ。

### 16.2 測定 (Ryzen AI 9 365、812 × 602)

公式の CPU (fp32、`tools/ref/ref_moge.py`) と同じ画像で:

| | ViT | neck | ヘッド (3 つ) | 合計 | 深度のコサイン | 相対誤差の平均 | マスクの一致 |
|---|---|---|---|---|---|---|---|
| vits | 0.30 秒 | 0.55 秒 | 1.80 秒 | 約 2.7 秒 | 0.99987 | 1.2 % | 99.95 % |
| vitb | 0.45 秒 | 0.55 秒 | 1.79 秒 | 約 2.8 秒 | 0.99993 | 0.8 % | 99.96 % |
| vitl | 1.04 秒 | 0.72 秒 | 1.78 秒 | 約 3.6 秒 | 0.99992 | 0.7 % | 99.98 % |

- 固定されるメモリの最大: vits 1.94 GiB、vitb 2.11 GiB、vitl 2.64 GiB (ヘッドの作業領域 773 MiB は 1 組。3 組とも載せると vits で 3.9 GiB)。書き出し (5 つの大きさ) は 1.4 / 2.0 / 4.3 GB、3〜5 分
- 尺度のロジットの差は 0.005〜0.01 (メートルで 0.5〜1 %)。画角は公式と 1° 以内
- IRON の参照 (CPU) と公式: ヘッドの出力のコサイン 0.99991〜0.99999
- 時間の大半は 16 倍の解像度 (800 × 800 前後、32 チャネル) のヘッド

### 16.3 残り

- ヘッドが重い (16 倍の解像度の 3 × 3 と、3 つのヘッドが同じ neck の出力を別々に処理する)
- マスクで点群を消す以外の後処理 (深度の段差の検出など) は未対応。画角を与えて解く `fov_x` は `hwnpu-image depth --fov` (焦点距離は与えたもので、z のずれだけを解く)

## 17. 顔の検出: YuNet (`hwnpu-image face-detect`、2026-11-10)

OpenCV Zoo の YuNet (`face_detection_yunet_2023mar.onnx`、MIT、5.3 万パラメータ、Hugging Face では opencv/face_detection_yunet) を `tools/amd/iron_yunet.py` で 1 つのグラフにします。ONNX を読み、層の並び (3 × 3 の stride 2、1 × 1 と深さ方向 3 × 3 の組、2 × 2 の max pool、最近傍の 2 倍と足し算、3 つの stride の頭) をそのまま組みます。

### 17.1 構成

- 1 × 1 と深さ方向の 3 × 3 の組は、1 つの 3 × 3 の畳み込みにまとめる (重み d[o, ky, kx] w1[o, i])。1 × 1 のバイアスは、ゼロ埋めの外側では 0 なので、画像の内側で 1 になる「1 のチャンネル」(テンソルの最後のチャンネル。実チャンネルが 64 の段は幅 128) に乗せる。深さ方向のバイアスは、その中央のタップに乗せる。これで、バイアスの足し算の演算が 1 つもなくなる
- ReLU は GEMM に入れる。flm.ProjectionGEMM のエピローグには、呼び出しごとの値で clamp の下限と上限があり (既定は恒等)、下限を 0 にした `ReluGEMM` が ReLU になる。畳み込み 1 つは、im2col のコピー、GEMM、次のグリッドへのコピーの 3 演算
- NPU2 の GEMM は A を bfp16 (8 列で指数を共有) で受ける。入力の画素 (0〜255) とバイアスの 1 が同じ 8 列に入ると、1 が丸めで消えた (cos 0.69)。画素を 255 で割り (最初の重みに 255 を掛ける)、1 を im2col の最後の 8 列に離した
- max pool は max(a, b) = b + ReLU(a − b) を 2 段 (4 つの見え方を 2 つの束にして)
- ホスト (internal/vision/face) は、画像を縮めずに入る大きさを選び、左上に置き、BGR / 255 と 1 を渡す。sigmoid、枠と点の復号、NMS は OpenCV の FaceDetectorYN と同じ。グラフは `iron.GraphOptions.KeepRuns` で開く (下記)

### 17.2 測定 (Ryzen AI 9 365、パッケージ電力 PPT からアイドル 4.55 W を引く)

| | 1 枚 | 正味の電力 | 1 枚のエネルギー | ホストの CPU |
|---|---|---|---|---|
| NPU、320 × 256 | 29.2 ms | 4.34 W | 127 mJ | 0.73〜1.1 ms |
| NPU、640 × 480 | 77 ms | | | 2.7 ms |
| CPU、onnxruntime 1 スレッド、320 × 256 | 2.73 ms | 2.81 W | 7.7 mJ | 2.73 ms |
| CPU、onnxruntime 4 スレッド、320 × 256 | 1.02 ms | 3.07 W | 3.1 mJ | 約 4 ms |

- 出力は参照と cos 0.9997。selfie の写真 (2048 × 1150 を 640 × 359 に) で、OpenCV と同じ 3 つの顔、枠の差は元の画素で 1〜2、スコアの差は 0.003 以内
- NPU は CPU を空けるが、エネルギーでは 16〜40 倍悪い。時間は計算ではなく演算の切り替えで決まる: 同じ演算を続けると 1 つ 5〜30 µs、GEMM と他の演算を交互にすると 1 回約 250 µs (`irongraph` で測定)。YuNet は約 70 演算で、切り替え 1 回が約 1 mJ。バイアスと ReLU を GEMM に入れても 32 → 29.5 ms で、残りは 1/2 の段の im2col (26 MB、5.8 ms) とコピー
- 待ちはカーネルの syncobj で眠る (ポーリングではない)。ホストの CPU は、実行のたびに作っていた run (制御コードの確保、コピー、キャッシュのフラッシュ) が半分だった: `KeepRuns` で 1.6 → 1.1 ms。残りは提出と待ちのシステムコール、Go のスレッドの切り替え (1 回に約 60)
- `irongraph` に `-keep` (KeepRuns)、`-cpuprofile`、1 回あたりのホストの CPU 時間を足した

### 17.3 置き場所: models.yaml の device

測定を受けて、置き場所をモデルごと・NPU のベンダーごとに書けるようにした (`device: {amd: cpu}`、書かないベンダーは npu。コマンドの `--device` と `HWNPU_DEVICE` で上書き)。Apple と Intel は、グラフ全体をまとめて投入するので AMD とは事情が違うはずで、まだ測っていないので npu のままにしている。CPU の実行系は ONNX Runtime の共有ライブラリを purego で呼ぶ (`internal/onnxrt`)。YuNet の 2023mar 版は形が 640 × 640 に固定されているので、入出力の形と value_info を外して (`onnxrt.FreeShapes`) どの大きさでも動かす (2026may 版と差 0)。

`hwnpu-image face-detect --repeat 301` (selfie を 320 × 180 にした画像、320 × 256 で実行、Go のコマンド全体):

| | 1 枚 | 正味の電力 | 1 枚のエネルギー | ホストの CPU |
|---|---|---|---|---|
| CPU (ONNX Runtime 1.31、1 スレッド、スピンなし) | 3.96 ms | 2.57 W | 10 mJ | 約 5 ms |
| NPU | 30.5 ms | 4.5 W | 137 mJ | 約 2.5 ms |

- 前処理が最初は 1 枚 11 ms だった (lfm3vl.Resize が画素ごとに color.Convert し、同じ大きさでもフィルタを 2 回かけていた)。RGB の取り出しに NRGBA、RGBA、YCbCr の速い道を足し、同じ大きさは素通しにした
- CPU の結果は OpenCV と一致 (スコア 0.916 / 0.917)

### 17.4 残り

- 速くするなら: GEMM の出力を次のグリッドの band 行へ直接書く (状態の連続した部分には書ける。パッドの列を 0 にする工夫が要る)、1/2 の段を幅 32 に、演算の数を一桁減らす。小さなモデルで CPU に勝つには、演算ごとに配列を組み直すいまの方式ではなく、モデル全体を 1 つの構成で流す設計が要る
- MediaPipe Face Landmarker (478 点、虹彩) は、同じ理由で NPU では得にならない見込み
- 入力の縮小は 2048 × 1150 から 640 × 359 で 190 ms (float64 の 2 回のフィルタ)。カメラの RGB をそのまま受ける道を作る
- Mac (Core ML、CPU と Neural Engine) と Intel (OpenVINO の NPU) で同じ 320 × 256 を測り、device の既定を決める
