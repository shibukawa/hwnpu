# 引き継ぎ: M2 (16 GB) での gpt-oss-20b の専門家を速く

作成: 2026-11-20、整理: 2026-11-21。前の版の「やること」と「M2 で最初に測ること」は 4 節で済んだので外した。残りは 4.10。M3 (16 GB) で作った gpt-oss-20b の Core AI の経路 (注意と出力層は Neural Engine、専門家は CPU で MXFP4 のまま) と、専門家ごとの固定 (`experts.Placement`) を、M2 の MacBook Air (16 GB、macOS 27.2.1) で速くするためのメモ。設計と M3 での記録は [docs/design/apple-coreai.md](design/apple-coreai.md)の gpt-oss の行、[docs/design/cli.md](design/cli.md) (`hwnpu status`)。

## 1. ここまでの状態

- ブランチ: `t3/gpt-oss-20b` (PR #243)
- 専門家は CPU で、チェックポイントを写像したまま (`safetensors.File.Map`、10.2 GB、コピーしない) `internal/mxfp4` の NEON のカーネル (e2m1 を表で引く、行は 32 個ごとに int8、SMMLA / SDOT) で計算する。`internal/llm/experts/host.go`
- 専門家の固定 (`internal/llm/experts/placement.go`): メモリの半分に収まらないとき (16 GB の機械) は、芯 (models.yaml の `experts_core`、141 個 1.9 GB) を先に、次にアプリの使用統計 (`~/Library/Caches/hwnpu/models/gpt-oss-20b/experts-usage/<キー>.bin`) の順に、予算 (既定はメモリの 1/4 = 4.3 GB、空きメモリに合わせて上下 (2026-11-20 に 3/8 = 6.4 GB から下げた)) まで専門家ごとに mlock する。30 秒ごと (初回は 5 秒後) に使われ方で入れ替え、`--idle` (5 分) 使わなければ芯以外を外す
- `HWNPU_MOE_WIRE`: `0` 固定しない、`1` 全部、`6GB` のような大きさは予算
- `HWNPU_DEV` の `moe.` の項目。`moe.time` で専門家の時間、固定の様子、固定した専門家に当たった割合。`usage=FILE` で使用回数をファイルにも、`prefault=0|wait`
- 使用統計の道具: `tools/moeusage/` (`prompts.tsv` 19 分野 約 25 言語 110 個、`collect.sh`、`analyze.py`)

## 3. 気をつけること

- Neural Engine のロックはほかのセッションが長く持つことがある。迂回しない (CPU だけのカーネルの試験、`go test ./internal/mxfp4` はロックが要らない)
- Core AI のコンパイル済みのキャッシュ (`~/Library/Caches/<プロセス>/com.apple.e5rt.e5bundlecache`) が消えると最初に 40 秒ほどコンパイルし直し、その回の速さは比べられない。速さは 2 回目から
- ディスク: 最初の取得はチェックポイント 13 GB と変換、`HWNPU_CACHE_MIN_FREE` (10 GB) の空きも要る
- `hwnpu status` の NPU% は推定 (PMP の ANE の読み出しの帯域の分布で、いちばん下の区分の外にいた時間)。M2 では確かめていない (チャンネルの名前が違うかもしれない)。電力は macOS 27 では root でないと 0 しか読めないので「読めない」と出す
- 速くなったら: [docs/design/performance.md](design/performance.md) (と .ja.md) の gpt-oss の行、MODEL.md、models.yaml の `memory`

## 4. M2 で測った結果 (2026-11-20、MacBook Air M2 16 GB、0c459eb の先読み入り)

まとめ: **M2 のカーネルは遅くない。遅さは熱と、メモリの取り合いと、層の間で眠ったコア**。先読みがあれば予算 3〜6 GB はどれも 12.4〜12.6 tok/s。

### 4.1 測り方 (これをしないと設定の差が揺れに埋もれる)

- ファンのない Air は 1〜2 回続けて回すと `hwnpu status` の `thermal pressure` が heavy になり (nominal に戻るまで約 60 s)、同じ設定が 12.8 → 8.7 tok/s と落ちる。毎回 nominal に戻ってから 45〜60 s 待つ
- `vm_stat` の Pageins を前後で取る。Safari (WebKit 多数) を開いたままだと、生成中もシステム全体で 100〜450 MB/s 読み、1 回 7〜36 GB
- 使ったスクリプト (3 つの固定を同じ状態で交互に回し、冷ますのと page-ins を足した):

```sh
therm(){ ./hwnpu status 2>&1 | grep -oE "thermal pressure [a-z]+"; }
cool(){ until [ "$(therm)" = "thermal pressure nominal" ]; do sleep 10; done; sleep 45; }
pi(){ vm_stat | awk '/Pageins/{gsub("\\.","",$2);print $2}'; }
run(){ cool; echo "== $*"; a=$(pi); env "$@" ./hwnpu-chat chat -m gpt-oss-20b -n 600 --seed 1 --prompt-cache off \
  "Explain how a CPU cache works, with examples." 2>&1 >/dev/null | grep -E "^experts:|\[prompt|chain: experts"; b=$(pi); echo "pageins $(( (b-a)*16/1024 )) MB; end: $(therm)"; }
for r in 1 2 3; do for w in 6GB 4GB; do for p in 4 0; do run HWNPU_MOE_WIRE=$w HWNPU_DEV=moe.time,moe.prefetch=$p; done; done; done
```

### 4.2 カーネル: 詰める余地は小さい

- `internal/mxfp4` の `BenchmarkGenLayer` (1 層の生成: 4 専門家の gate_up と down、1 ベクトル、53 MB、318 MB を回してキャッシュの外): **1.05 ms (約 50 GB/s)**、M3 の 0.9 ms とほぼ同じ。`GOMAXPROCS` 8、6、4 で差なし (1.01〜1.10 ms)
- 同じ機械で 8 スレッドの単純な読み出しは約 61 GB/s。カーネルはその 83 %: 命令を詰めても上がるのは最大 15 % ほど。生成は 1 行なので `dotNEON` (SDOT) で、SMMLA は関係しない
- 実機のチェックポイントでの `TestHostTokenTime` はページの読み込みで 8.8〜23 ms/層になり、カーネルの比較には使えない (メモリが空いていないと)
- 層の間の間: `HWNPU_TEST_GPTOSS_GAP=1ms` で 1.09 ms (変わらない)、`4ms` で 1.5〜2.2 ms (コアが眠る)。worker を回し続けると (`HWNPU_MXFP4_SPINNERS=2`、後にコードごと消した: performance.md) 4 ms の間でも 1.0〜1.07 ms に戻る
- ところが hwnpu-chat の中では spinners は効かない: 4 GB・先読みありで spinners 0 は 12.5 / 12.4 / 12.4 tok/s、2 は 11.3 / 12.5 / 11.6。既定 (0) のまま
- 「M2 の専門家は M3 の 1.85 倍」(2 節) は、カーネルではなく、ページの読み込みと眠ったコアと熱だった。chat の中の専門家は今も 1.64〜1.76 ms/層 (合成の 1.05 ms との差が残り)

### 4.3 先読みと予算

先読みが入る前 (d12b662、冷まして 2 回ずつ、ほかのアプリはふだんどおり):

| `HWNPU_MOE_WIRE` | tok/s | page-ins / 回 |
|---|---|---|
| 0 | 12.4 / 11.0 | 8.6 / 12.2 GB |
| 4GB | 7.5 / 11.4 | 36.6 / 12.6 GB |
| 6GB | 9.4 / 9.7 / 12.8 | 22.1 / 19.3 GB / — |
| 8GB | 11.3 / 11.0 | 12.9 / 14.5 GB |
| 1 (全部、9.1〜9.4 of 10.2 GB で EAGAIN) | 11.0 / 9.9 | 17.3 / 18.9 GB |

遅い回は、30 秒ごとの入れ替えで 1.2 GB を読み直したとき、またはメモリの状態が悪いとき。全部固定しても、Neural Engine の 1.44 GiB と合わせてほかのアプリに残らず、page-ins は減らない。

先読みあり (0c459eb、どの回も終わりまで nominal、3 回ずつ交互):

| 予算 | 先読み | tok/s | 専門家 ms/層 | 固定に当たった | 外れのうち先に読めた |
|---|---|---|---|---|---|
| 6GB | 4 (既定) | 12.2 / 12.5 / 12.5 | 2.11 / 1.68 / 1.69 | 82〜87 % | 75〜77 % |
| 6GB | 0 | 12.1 / 12.3 / 12.1 | 1.79 / 1.74 / 1.79 | 85〜86 % | — |

| 3GB | 4 | 12.4 / 12.6 / 12.4 | 1.65〜1.74 | 57〜58 % | 77 % |

- 予測は上位 4 個に 87.3 %、上位 8 個に 97.7 % (M3 と同じ)
- 先読みで 6 GB +2 %、4 GB +4 %。**先読みがあれば 3 GB でも 6 GB と同じ速さ** (M3 でも 3 GB の先読みありが 6 GB の先読みなしより速かった)。先読みは外れの予測のぶん page-ins を 1 回 2〜3 GB 増やす
- 提案 (まだ変えていない): M2 では既定の予算 (メモリの 3/8 = 6.4 GB) を下げても速さは落ちず、ほかのアプリに 3 GB ほど返せる。M3 の 3 GB (14.7〜15.0) と 6 GB (15.1〜15.2) の差は小さいので、既定を 4 GB 前後 (メモリの 1/4) にするか、両方の機械で決める → 2026-11-20 に 1/4 にした (M3 でも 3 GB と 6 GB の差は 2〜4 %)

### 4.4 chat の中の 1.7 ms と合成の 1.05 ms の差の内訳

`HWNPU_DEV=moe.time` に、生成の 1 層ごとの専門家の時間を、選んだ専門家が「全部固定」「固定していないものは先読み済み」「先読みしていないものがある」に分けた分布 (`experts: a row's layer, …`) と、次の層の予測の時間を足した。4 GB (メモリの状態が悪めの回、10.0〜10.7 tok/s、page-ins 12〜27 GB):

| 1 層の専門家 | 割合 | 中央値 | p90 | p99 | 時間の割合 |
|---|---|---|---|---|---|
| 全部固定 | 28 % | 1.32〜1.37 ms | 1.42〜1.70 | 2.1〜3.6 | 17 % |
| 固定していないものは先読み済み | 49 % | 1.39〜1.40 | 2.5〜3.6 | 14〜16 | 45 % |
| 先読みしていないものがある | 23 % | 1.46 | 13〜16 | 27 | 38 % |

- **差のほとんどは外れ**: 中央値はどれもほぼ同じで、固定していない層がときどき SSD を待って 14〜27 ms かかる。その裾が時間の 8 割以上。先読み済みでも p99 は 14〜16 ms (読み終わる前に使われたか、追い出された)。メモリが苦しい回は先読みが page-ins を 2 倍にし (12 → 27 GB)、速さは変わらなかった (10.0 / 10.5 と 10.7 / 10.3)
- **次の層の予測 0.12〜0.13 ms/層**: 専門家の前に同期して回っていた (`prefetch=0` でも)。goroutine に移した (`prefetcher.guessLoop`。遅れた予測は数えて捨てる、`guesses too late`): 全部固定の層の中央値 1.35 → 1.23〜1.25 ms、4 GB で 10.6〜10.8 → 10.8〜11.6 tok/s (3 回ずつ交互)。遅れた予測は 0
- **残り約 0.2 ms** (1.25 と 1.05): 全部固定でも残る。眠ったコアの起き上がりと活性化 (spinners では縮まなかった)

### 4.5 先読みの読み方

メモリに無い専門家 1 つ (13.3 MB) を読む速さ (`TestColdRead`、`mincore` でメモリに無いものを選ぶ):

| 読み方 | GB/s | 1 専門家 |
|---|---|---|
| ページに触れる (1 goroutine、16 KB ずつの割り込み) | 0.5〜0.6 | 20〜27 ms |
| `madvise(WILLNEED)` してから触れる (それまでの先読み) | 1.7〜1.8 | 7.1〜8.1 ms |
| 同じく 4 goroutine で触れる、1 MB ずつ WILLNEED | 1.7〜1.9 | 7.0〜7.8 ms |
| ファイルを `pread` (1 MB ずつ、4〜8 スレッド) | 2.7〜2.8 | 4.7〜4.8 ms |

先読みを、1 MB ずつに分けて 4 goroutine で、メモリに無いもの (`mincore`) だけ `pread` してから触れる形に替えた (メモリにあるものを pread すると写すぶん帯域を使う)。4 GB、3 回ずつ交互 (メモリが苦しめの回、page-ins 22〜30 GB): 9.6〜9.8 → 9.8〜10.2 tok/s。先読み済みの層の平均 2.37〜2.46 → 1.93〜1.98 ms、p99 17〜18 → 10 ms。全部固定の層の中央値は 1.27〜1.30 → 1.34〜1.36 ms (読み手が帯域を使う)

それでも 1 専門家 4.8 ms は Neural Engine の部品の間 (約 1.5 ms) より長い。SSD から読むかぎり先読みで外れは隠しきれない

### 4.6 使う直前にメモリに無い専門家を読む (main の a017fb2 の上、既定の予算 4.3 GB)

`HWNPU_DEV=moe.time` の分け方を「使う時点でメモリにあったか」(`Host.cold`: 範囲に散らした 8 ページの `mincore`、1 専門家 4 µs。全ページは 0.2 ms かかる) に替えると、遅さの正体が出た。メモリが苦しい状態 (空き 25 % 前後、page-ins 1 回 23〜58 GB) の 600 トークン:

| プロンプト | tok/s | 固定に当たった | 予測せずメモリに無い専門家に当たった層 | その 1 回 | 専門家の時間に占める割合 |
|---|---|---|---|---|---|
| 英語 (統計と同じ文) | 9.7 / 9.9 | 71 % | 4.6〜4.8 % | 14〜15 ms (中央値 [amd](design/amd.md)) | 30〜32 % |
| 日本語 (江戸時代の経済) | 12.2 / 12.2 | 75 % | 1.4 % | 14 ms | 13 % |
| コード (Go の LRU) | 8.4 / 7.7 | 61 % | 7.2〜7.8 % | 15〜17 ms | 40〜42 % |

速さはほぼこの「メモリに無い専門家」の数で決まる。写像からそのまま計算すると、カーネルが触れるたびの割り込みで 16 KB ずつ読むので 0.6 GB/s しか出ない (4.5 節の表のいちばん上)。

`reader.need`: 行 (プロンプトの塊も) の専門家を回す前に、固定していないものを 8 ページで確かめ、無いものを 1 MB ずつ 4 つの読み手と呼び出し側が `pread` して触れる。先読みの読み手 (4.5) と同じ goroutine で、行の要求を先に取る (`internal/llm/experts/fetch.go`)。`HWNPU_DEV=moe.need=0` と交互:

| | `need=0` | 既定 | メモリに無い専門家に当たった層 |
|---|---|---|---|
| 英語 | 9.3 tok/s | 10.1 | 18.5 → 8.6 ms |
| コード | 7.9 | 8.8 | 19.2 → 8.9 ms |
| コード (予算が 1.9 GB に落ちた回) | 6.7 | 7.8 | 21.1 → 9.6 ms |
| プロンプト 77〜89 トークン | 4.8〜6.8 s | 2.3〜3.3 s | |

- 先読み 8 個 (`prefetch=8`) は 7.1〜7.2 tok/s (4 個は 9.7〜9.9)、page-ins 60〜65 GB (23〜24 GB): 間違った予測の読み込みが要るページを追い出す
- 2 層前からの予測は上位 4 個に 80〜85 %、8 個に 94〜97 % (1 層前は 86〜90 %、97〜99 %)。早く読めるが、読む量を増やす害の方が大きいので使っていない
- `need` が入ると、メモリが苦しい状態では先読みの差が見えなくなった (英語 あり 10.1 / なし 10.0、コード 8.4 / 8.9)。余裕がある状態 (4.3) の +2〜4 % は測り直していない。既定は変えていない

### 4.7 予算の振動 (PR #246 の空きメモリへの追従)

空き 24〜26 % の M2 で、固定と警告が追いかけ合った: 4.3 GB 固定 → システムの警告 (逼迫度 2) → 芯の 1.9 GB (2.4 GB を外す) → 空き 40 % → 次の入れ替えで 4.3 GB、を 30 秒ごと。その回は 6.7〜7.8 tok/s。

直し (`placer.warned`、`placer.rise`): 芯より多く固定しているときに警告が出たら、そのとき固定していた量より 1 段 (予算の芯より上の 1/4、16 GB で 0.6 GB) 下を上限にして 10 分保ち、その後 1 段ずつ戻す。直した後: 4.3 → 1.9 → 3.7 GB で止まる (ある回は 3.7 でもう 1 度警告が出て 3.1)。上限はプロセスの中だけなので、起動のたびに 1 度は予算いっぱいを固定する。

### 4.8 固定の入れ替えの方式 (変えていない)

`HWNPU_DEV=moe.trace=FILE` で行ごとの専門家を記録し、`tools/moeusage/place.py` で方式を比べた (324 個固定、統計は英語の文の繰り返し)。生成の専門家が固定に当たった割合 (括弧は入れ替えで新しく固定した専門家の数):

| 方式 | 英語 (統計と同じ文) | 日本語 | コード | 平均 |
|---|---|---|---|---|
| 最初の固定のまま | 84.6 % | 59.9 % | 52.2 % | 65.5 |
| 今の方式 (点数を半分にして直近の割合を足す) | 76.1 % (142) | 81.4 % (162) | 60.8 % (156) | 72.7 |
| 直近の標本を回数で重み付け (1000 回で 1) | 81.9 % (70) | 78.4 % (124) | 61.2 % (108) | 73.8 |
| 統計を 500 回分として回数で混ぜる | 80.4 % (105) | 80.7 % (138) | 61.3 % (124) | 74.1 |

入れ替えは新しい分野で効く (+9〜21 ポイント)。統計と同じ文では 5 秒後の入れ替えが当たりを下げるが、方式を替えても平均は 72〜74 % の中で、新しい分野での当たりと引き換えになる。3 つの文だけの比較なので、今の方式のままにした。

これまでの計測は `--experts-key off` を付けずに同じ文を繰り返したので、`experts-usage/chat.bin` がその文に偏っている (英語の文の当たりは実際より良く出ている)。測るときは `--experts-key off` か別のキーを使う。

### 4.9 1 ステップの内訳と、残りの改善点を試した結果

`HWNPU_PROFILE=1` (メモリが苦しい回、1 ステップ 96 ms): 専門家 24 × 2.39 = 57 ms、Neural Engine の呼び出し 37 回 約 32 ms (1 回 約 0.85 ms)、ホストの注意 12 × 0.53 = 6.4 ms。余裕がある回 (80 ms) は専門家が 41 ms。

**ワーカーの起こし方 (効果なし、コードは戻した)**。`Host.Run` は 1 層にワーカーを 3 回起こし (gate と up、活性化、down)、Go のスケジューラは眠ったワーカーを 1 つずつ順に起こす (`HWNPU_DEV=mxfp4.bench=wake go test ./internal/mxfp4 -run TestWake`: 4 個目 60 µs、8 個目 180 µs、悪いときは数 ms)。合成の重みでの `Host.Run` (`HWNPU_TEST_GPTOSS_GAP=2ms go test ./internal/llm/experts -run TestHostRunGap`):

| | 続けて (`BenchmarkHostRun`) | 1 ms 空けて | 2 ms 空けて (平均 / 中央値 / p90) |

**Neural Engine の 37 回 (変更なし)**。37 個の部品が 1 トークンに読む重みは 1.09 GB (出力層 436 MB、注意 1 層 12〜27 MB)。32 ms は約 34 GB/s で、呼び出しの固定費 (M1 で空の呼び出し 0.21 ms、[docs/design/performance.md](design/performance.md) の行) より重みの読み出しが大半。切れ目は専門家 24 とホストの注意 12 で決まり、M3 と同じ形 (3.3)。

**上限の持ち越し (入れた)**。4.7 の上限と、戻すまでの時間を `experts-usage/ceiling` (「バイト数 時刻 保つ秒数」) に残し、次の起動が引き継ぐ (`Placement.Ceiling`、`placer.keepCeiling`、`readCeiling`)。保つ時間ごとに 1 段戻り、戻りきるとファイルを消す。持ち越すと、10 分ごとに 4.3 GB に戻っては警告で 1.9 GB まで外す繰り返しが見えたので、戻した後その保つ時間のうちに警告が出たら保つ時間を倍にする (最長 80 分)。確認: 警告の後の起動は 3.7 GB (その後 3.1 GB) から始まり、戻した直後の警告で「for 20m0s」になった。

**先読みの数をメモリの状態で (入れた)**。`--experts-key off`、既定の予算、メモリが苦しい状態で 2 回ずつ:

| 先読み | 英語 | コード | page-ins (英語 / コード) |
|---|---|---|---|
| 0 | 10.7 / 10.2 tok/s | 9.0 / 9.0 | 25 / 34〜35 GB |
| 2 | 10.4 / 10.3 | 9.3 / 9.4 | 25 / 34〜36 GB |
| 4 | 9.9 / 10.0 | 8.8 / 8.9 (どちらも途中で警告) | 32〜34 / 43〜45 GB |

行がメモリに無い専門家を読んだ (`reader.need` が pread した) 後の 10 秒は「苦しい」とみなし、上位 2 個だけ先読みする (`prefetcher.auto`、`reader.short`)。そうでなければ 4 個 (M3 の余裕がある状態で 4 個が 3〜6 %)。`HWNPU_DEV=moe.prefetch=N` は数を固定する。入れた後の確認 (固定 3.1 GB、2 回目): 英語 既定 9.7 / 4 個 9.5 tok/s、コード 8.7 / 8.8、page-ins は 31 / 36 GB と 41 / 45 GB。速さの差は揺れの範囲 (0〜4 %) で、確かなのは SSD から読む量が 1〜2 割減ること。**M3 の「ほかのアプリが忙しいとき」(先読み 4 個で +7 %、`need` が入る前の値) は測り直していない**: そこで 2 個に切り替わって遅くなるなら `fewWhenShort` を 4 に戻す。

警告のたびに芯 (1.9 GB) まで外して次の入れ替えで上限まで戻すので、警告が出た回は遅い (コード 7.6 tok/s、page-ins 54 GB。出なかった回 8.7、41 GB)。警告では上限まで 1 段ずつ下げる形 (芯までは逼迫度 4 か空き 10 % 以下だけ) にすれば読み直しは減るが、ほかのアプリにメモリを返すのが遅くなるので変えていない。
