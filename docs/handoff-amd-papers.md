# 引き継ぎ: 論文から拾った AMD の NPU の最適化の候補

作成: 2026-11-20。arXiv の「NPU」の検索 (505 件) と、AMD XDNA、端末の LLM の論文の調査から、hwnpu の AMD の経路 (IRON、`internal/llm/iron`、`internal/backend/amd`) に入れられそうなものを選んだ。全体の一覧 (`docs/npu-optimization-papers.md`: MoE 以外、`docs/moe-papers.md`: MoE) は、このリポジトリにはまだ入っていない。

対象の機械は Ryzen AI 9 365 (XDNA2、NPU4 系)。書いてあるのは仮説と、それを確かめる手順。

**論文の確かめた度合い**
- ✓: 本文 (HTML) を調べた
- (a): 要旨だけで見た
- †: 一般に知られた手法で、本文を読んでいない

2026 年のものは査読前のプレプリントが多い。数字を設計の根拠にする前に本文を読む。

## 1. 演算子の切り替えの上乗せを減らす (優先: 高) — 確かめた、16.266

**出典**
- HeteroMosaic 2607.12839 ✓: データパスの再設定 (PDI の読み直し) は高く、DMA の設定の切り替えはほぼ無料。xclbin ごとに操作をまとめ、NPU を扱うスレッドを 1 本にする
- 2606.07586 ✓ (XDNA2 で Llama-3.2-1B のデコード 10.8 tok/s): XRT のコンテキストを使い回し、層ごとの BO をゼロコピーで回す

**仮説**: 16.75 の「違う種類の演算子で 1 個 約 80 µs、同じものが続くと 20 µs 未満」は、full ELF の制御コードがコアのプログラム (PDI) を読み直す費用ではないか。

**結果** (16.266): 仮説どおり。演算子が変わるたびに `load_pdi` と配列の設定 (コアのプログラムメモリを含む) が制御コードに入り、1 回 85〜100 µs (設定の大きさ 6〜35 KB でほぼ変わらない)。

- gpt-oss-20b のデコードは常駐の 1 演算で、1 層 1 回だけ。層のコマンド 1.80 ms は別の理由
- LFM3-1.7B のデコードは 1 トークン 614 回 (約 60 ms / 89 ms)、Gemma 4 E2B は 1016 回 (約 100 ms / 127 ms)、Qwen3.6 は 484 回 (約 48 ms / 172 ms)
- 並べ替えで消せるのは Qwen3.6 で 1 トークン 40 回まで (依存を無視した上限)。密なモデルは同じ設定が層ごとに出て、層の間には依存がある

**残作業**
- (a) 静かな NPU で測り直す: 済み (16.266 の「静かな NPU で測り直す」)。費用は設定の大きさで増える (40 µs + 2.3 µs/KB)
- (b) 実機のデコードで確かめる: 済み。LFM3-1.7B 92.6 ms に対して見積もり 98 ms、Gemma 4 E2B 137 ms に対して 138 ms、Qwen3.6 はコマンドごとの時間で 1 トークン約 90 ms / 122 ms が設定
- (c) 1 層の演算をまとめる: LFM3-1.7B で済み (16.268、`ShortConvStep`、`SandwichAdd`、`QGEMVGlu` で 11.2 → 15.6 トークン/秒、KL は同じ)。Gemma 4 E2B も済み (16.269、7.7 → 9.3 トークン/秒、KL は同じ)。LFM3-VL・Audio・Omni は 11.3 → 15.6、Gemma 4 E4B は 5.5 → 6.4 (16.272)。QGEMV を 1 列 1 コアに、sandwich を GEMV の中で (16.277、LFM3 15.6 → 17.2)。LFM3 の ShortConvStep が状態の置き場を直接読み書き (16.278、+2 %)。プロンプトの短い畳み込みを 1 演算子に (16.278、LFM3 16 トークン −13 %、Qwen3.5-0.8B −25 %)。残りの大きな費用は、デコードでは層の中の演算の切り替え (1 配列の形が要る)、Qwen3.6 では GDN の演算子の設定 374 KB × 30 層、プロンプトでは IRON の GEMM が行に関係なく重みを全部の行の単位に流すこと
- (d) 済み (16.272): ローカルのブランチ t3/qwen36-integrate が GDN の演算子に状態の枠を直接読み書きさせていた (`gdn_operator(slots=)`)。取り込んだ。今の main から作った Qwen3.6 が遅かった原因もこのブランチが main に入っていなかったこと
- (e) GDN の 0 の塊: 済み (16.267)。Qwen3.5-0.8B で 13.2 → 14.1 トークン/秒 (ロジットはビット単位で同じ)、t3/qwen36-integrate と合わせて Qwen3.5-0.8B 13.8 → 18.7、Qwen3.6 8.5 → 8.9 (16.272、どちらもビット単位で同じ)
- (f) `--load-pdi-to-ctrl-pkt`: aiecc が「operand #0 does not dominate this use」で止まる (`--ctrlpkt-adaptive-overlay=false`、teardown なしでも)。上流 (Xilinx/mlir-aie #3928 の計画、#3934・#3935 はマージ済み) にこの不具合の報告はない。複数列の設計は #3488 (実機で止まる、open) にも当たりうる

**次の手**: 1 層の演算の数を減らす。gpt-oss の `GptOssStep` (iron_gptoss_layer.py) と同じ常駐の形を、密なモデル (まず LFM3-1.7B か Qwen3.5) に作る。比べる基準は `elfconfigs` の数と、デコードの 1 トークンの時間。合格条件はロジットのコサインが変わらないこと (`ironlm` の閾値)。

## 2. 要らない同期を外す (優先: 高、小さい) — IRON の経路はすでに済み

**出典**: 2606.07586 ✓。NPU だけが読み書きするバッファは、ホストとの同期を省く。

**調べた結果**: IRON の経路 (`internal/llm/iron/moe.go` の `readRegion`/`writeRegion`/`writeCopies`、`rows.go`、`graph.go` のホストの手順) は、すでに使う範囲だけを同期している。`moe_route`、`moe_combine`、`moeHostRouteMX4` もそう。バッファ全体の同期が残っているのは読み込みのときと、IRON でない経路 (`internal/llm/chain/moe.go` と `chain.go` の専門家の 1 行と注意の塊。Intel と Apple でも使う) だけ。

**注意**: ホストが読む領域は、IRON の割り当てで使用に数えられず、あとの演算に上書きされることがある (16.93、16.179、16.110 の落とし穴)。同期を減らすときに、読む位置を変えない

## 3. 多次元の DMA の番地で、1023 語の制限と事前の並べ替えを避ける (優先: 中)

**出典**: 2512.13282 ✓ (Ryzen AI の 2 世代の GEMM、XDNA2 で int8 38 TOPS、bf16 14.7 TOPS)。XDNA2 では bf16 を bfp16 のデータパスに通す。多次元の DMA の番地で並べ替え、ホストで重みを前もってタイルにしない。shim あたり 16 を超える BD は、同期してから使い回す。

**hwnpu で困っていること**: 「DMA の 1 次元の大きさは 1023 語まで: 重みを消費順に並べ替える 4 次元の TAP は通らないので、表の順のまま流す」(16.93、16.179)。そのため次のことが起きている。
- 専門家の表を「[組][k ブロック][gate/up][コア]」の並びに作り直している
- プロンプトの MoE で x をホストが 2 回、4 回と並べ直している

**やること**
- 2512.13282 の本文の DMA の書き方 (次元ごとの大きさと stride の割り方) を読み、1023 語を超える 1 次元を、2 つの次元に割って同じ並びを作れるかを、`iron_moep.py` の小さな形 (32 専門家、16 トークン) で試す
- 通れば、ホストでの x の並べ直し (`moe_route`) の時間を減らせる

## 4. タイルを入力と出力で違う大きさで持つ (優先: 中、画像と長いプロンプト)

**出典**
- 2511.16041 (a): Asymmetric Tile Buffering。XDNA2 の BFP16-BF16 の GEMM で 24.6 TFLOPS、4.54×
- 2512.13282 ✓: 出力の転送が償却できるとき、C のバッファを 1 つに (+13〜18%)

**対象**
- 画像の DiT の GEMM (Anima、FLUX.2/3 klein、Chroma の bfp16 の MLP と注意。16.200、16.207)
- gpt-oss のプロンプトの専門家 (`MX4GroupGateUp`、bf16 の `mac_4x8_8x8`)

**やること**: 本文を読んで、今の `iron_gridgemm.py` と DiT の GEMM のタイルの大きさ、L1 と L2 の二重バッファの数と比べる。1 つの形 (Anima の DiT の MLP) で試し、1 ステップの時間を比べる

## 5. 注意の融合と、因果の三角を均す配置 (優先: 中)

**出典**
- 2609.21264 ✓: IRON と MLIR-AIR で FlashAttention、128K まで。融合版は XDNA2 で 3.62 TFLOP/s
  - QKᵀ のスコアをコアのメモリに置き、cascade の配線で集める
  - 融合は XDNA2 で効き、XDNA1 (ridge point が低い) ではほとんど効かない
  - メモリの段 (shim、MemTile、コア) ごとに、命令から数えた天井で roofline を描く
- STEEL 2607.09385 (a): XDNA の FlashAttention を公開。因果マスクの疎を考えて、パイプラインの段を置く
- Zen-Attention 2508.17593 (a): 注意を畳み、タイルを決めて DRAM の帯域を減らす。注意 最大 4×、端から端まで 最大 32%

**対象**
- プロンプトの塊の因果な注意 (16.58、16.84)。三角の後ろの行ほど仕事が多いので、列ごとの仕事が偏っていないかを先に測る
- DiT の注意 (16.147 の 64 キーの塊、QKᵀ を bfp16)

**やること**: 2609.21264 は IRON で書いているので、コードが公開されていれば今の `iron_mha.py` と同じ形で比べるのが早い。融合は設定のし直しの回数も減らす (16.266)

## 6. q4nx の前に回転 (アダマール) で外れ値をならす (優先: 中、精度)

**出典**: MR-GPTQ 2509.23202 (a, MXFP4 とブロックのアダマール変換)、QuaRot / SpinQuant †

**動機**
- Qwen3.6 の 40 層の q4 は、HF とのコサインが 0.986〜0.996 で、差の大半は q4 (16.91)
- gpt-oss の専門家は q4nx に丸め直すと重みの誤差 6.6%。KL は README 0.052 → 0.135 (16.179)

**やること**
1. `tools/amd/iron_q4.py` で量子化する前に、残差の次元を回す。RMSNorm の重みを次の射影に畳み込み、W を W·Hᵀ に書き換える。実行時の演算は増えない
2. CPU の KL の掃引 (`ref_gptoss.py sweep`、`qwen36_gptq.py` の評価) で、回転なしの q4 と GPTQ の q4 と比べる
3. 効けば、GPTQ と組み合わせる (先に回して、それから GPTQ)

**注意**
- RMSNorm の重みが `1 +` の形 (Qwen3.5 系、`RMSNorm.plus_one`) と、そうでない形 (gpt-oss) の両方がある
- 回転は残差の流れ全体にかかる。埋め込み、出力層、共有の専門家、router のすべてに同じ H を入れる

## 7. bfp16 の精度を測り直す (優先: 低、確認だけ)

**出典**: TileFuse 2606.11357 ✓ (XDNA2 の W4A16/W8A16 の融合カーネル)。「BFP16 のカーネルは LLM の端から端までには精度が足りない」と書いている。

**対象**: hwnpu は bfp16 を DiT の注意と MLP (16.200)、gpt-oss の専門家のプロンプト (16.179) に使っている。DiT は潜在のコサインで確かめ済みで、gpt-oss は KL を測っている。新しい LLM で bfp16 を使うときは、16.179 と同じ KL の掃引を通す。

## 8. 重みの可逆圧縮でデコードの帯域を稼ぐ (優先: 低、研究寄り)

**出典**: ENEC 2604.03298 (a, Ascend)。長さ固定のブロックの符号と分岐なしの復号で転送の律速を外す。端から端まで最大 6.3×。

**前提を先に測る**: q4nx の符号 (4 ビット) とスケールのエントロピー。2.5 ビット/符号を切らないなら、復号の費用に見合わない見込み。`tools/amd` に小さなスクリプトを書いて、Qwen3.6 と gpt-oss の表で測るだけでよい。16.266 のとおり密なモデルのデコードは帯域より設定のし直しで決まっているので、効くのはそれを減らした後。

## 9. MoE

MoE の論文と順位つきの候補は別の資料 (`docs/moe-papers.md`、未収録)。AMD に直接関係する上位 3 つ:

1. 専門家の常駐を、校正した頻度で決める。層ごとに活性の約 2 倍 (2505.16056、NPUMoE、Fate)。[handoff-amd-moe.md](handoff-amd-moe.md) と同じ方向
2. `MoERoute` がスクラッチパッドに書く「表の中の位置」を「arena の枠の位置」に読み替える (EStream 2609.06551)。今の形 (16.89) はこの論文の「専門家の仮想化」と同じ考え方
3. 層をまたいだゲートの先読み (Fate、Pre-gated)

## 10. 気をつけること (前の作業の落とし穴)

- **shim のチャネルのタスクキューは 4 段**: 待たずに積むと止まる (`ERT_CMD_STATE_TIMEOUT`)。続けて 2 回止めると SMU が戻らず、再起動が要る (16.89)。DMA の形を変える試し (3 と 4) では、チャネルごとに 3 本までにする
- **IRON のコンパイルのキャッシュは演算子の引数で引く**: build の中を変えても古い設計が動く。形を変えたら、形の引数を足す (16.179 の `sink_form`)
- **ホストが読む領域**は、ホストの手順の直前の演算の出力か、状態に写したものだけ (16.93)
- **書き出しは重い**: Qwen3.6 で 29 分、最大 RSS 50 GB。他の重い仕事と並べない (16.91)
- **NPU を他のセッションと分け合う**: 2026-11-20 は別のセッションが gpt-oss-120b の hwnpu-chat を続けて回していて、小さな試しの時間が 2〜5 倍に揺れた。比べるものは同じ回の中で交互に回し、`/dev/accel/accel0` を開いているプロセスを先に見る
- 結果は design.md の 16 章に新しい節として書く (既存の節の流儀: 測った表、採らなかったもの、試し方)
