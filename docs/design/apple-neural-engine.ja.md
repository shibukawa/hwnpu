# Apple の Neural Engine

[English](apple-neural-engine.md)

どのバックエンドで動かしても当てはまる、Apple の Neural Engine (ANE) の事実: 上限、数値の落とし穴、プロンプトのプログラム、プロセスどうしのロック、ANE のメモリ。バックエンドは [Core AI](apple-coreai.ja.md) (macOS 27 でコマンドが使う) と [Core ML](apple-coreml.ja.md) (ベストエフォート: ライブラリの既定と開発用の道具)。

## 上限

| 上限 | 値 | hwnpu のすること |
|---|---|---|
| 1 本のプログラムの重み | Core ML: 0.99 GiB は ANE で動き、1.02 GiB は CPU に落ちる (M1〜M3。M4 は 2 GB)。Core AI 自身の上限は [Core AI](apple-coreai.ja.md) | 層ごとに分ける ([Core ML](apple-coreml.ja.md))、または注意で分ける ([LLM のエンジン](llm-engine.ja.md)) |
| テンソルのどの次元も | 16384 は収まる。16385 では演算が CPU に置かれる (M3)。出力に名前をつけるだけの恒等でも | `llm.NeuralEngineMaxDim`。KV キャッシュは 16384 ずつの塊 (`CacheChunks`)。幅の広い出力、入力、連結は分ける |
| 重みの表 (lut) | 16 行に 1 つの表だけ | 行を 16 の倍数に詰めて切り戻す (`blocks.LinearPadded`)。[量子化](quantization.ja.md) |
| `gather` | CPU で動く | one-hot の行列積。埋め込みの行はホストで引く |
| ANE のコンパイルのキャッシュ (システム、`aned`) | バイト数で約 4 GiB の LRU (3.2〜4.8 GiB、実効は約 3.5)。sudo なしでは見えない。外れると読み込み時に `ANECompilerService` がやり直し、1 本に数十秒〜数分 | `-prefill auto` は 2 本で `compileCacheBytes` (3.5 GiB) を超えるなら 1 本にする。毎ステップ動くものを一番小さく。2 回目**と 3 回目**の起動が数秒なら良い |
| 部分を順に回す (M1 だけ) | 2.86 GiB まで全速。2.97 GiB からは呼び出しがどれも約 12 倍遅い (1 トークン 828 対 72 ms)。M2 は 3.65 GiB、M3 は 3.96、M4 は 3.62 まで全速 | `Apple M1` では `neuralEngineHold` = 2.8 GiB: 2 本と横のプログラム (MTP、塔) で超えるなら `-prefill auto` は 1 本にし、1 本で超えるなら警告する |
| 1 プロセスのプログラムの数 | 112 (M2、Core AI): 113 本目の読み込みは失敗し (`no ANE resources`)、Core AI は黙って GPU で動かす | `coreai` は ANE に載ったプログラムを数え、上限が近いと警告する。gpt-oss-20b は約 84 |
| 呼び出しの下限 | 1 回約 160〜175 µs (M2、Core AI)。112 本の間で切り替えの費用は見えない | 大きな呼び出しを少なく |
| 要素ごとの演算 | 16〜20 GB/s (3 つのテンソルの和)。2 MB を超えても崖はない (M2) | |
| 1×1 の畳み込み | 出力 256 チャンネルまで時間は平ら、その先で増える (1024: 500 µs、4.3 TFLOP/s) | 広い畳み込みを分ける理由はない |
| 実行時の重み (入力の配列) | 定数の重みの半分の速さ (26 対 50〜52 GB/s、M2) | [MoE](moe.ja.md) |
| 注意のスコア | スコアのテンソルが約 64〜68 MiB を超えると、q kᵀ と softmax がスコアあたり 2〜3 倍遅い (Core ML) | 問い合わせを塊に (`mil.DitQChunk`)。ただし先に測る: Whisper の 90 MB は塊にしても速くならなかった |

### 重みの形式ごとの速さ (M2、Core AI、定数の 4096×4096、lut の表は 16 行ごと)

| 形式 | 1 行 | 64 行 | 重みの要素/秒 (1 行) |
|---|---|---|---|
| fp16 | 742 µs | 808 µs | 22.6 G (45 GB/s) |
| int8 (行ごと) | 466 | 506 | 36.0 G |
| lut8 | 449 | 515 | 37.4 G |
| lut6 | 387 | 477 | 43.4 G |
| int4 (行ごと) | 329 | 379 | 51.0 G |
| lut4 | 351 | 382 | 47.9 G |

160 µs の下限を引くと、fp16 は約 58 GB/s、int8 と lut8 は約 55 GB/s (バイト数で決まる)、lut4 は約 90 G 要素/秒で頭打ち。lut8 は fp16 の 0.6 倍の時間、lut4 は lut8 の 1.3〜1.4 倍速い。

## ANE が動かさない演算と代わりの形

Core ML の計算の計画で見たもの (Core AI 自身の落とし穴は [Core AI](apple-coreai.ja.md))。代わりの形はどちらのバックエンドのグラフにも入っている。

| 演算や形 | どこから | 代わり |
|---|---|---|
| `sin`、`cos`、`floor`、`round`、`ceil`、`mod`、`sign`、`cast` | いつも | 丸めは 1536 を入力にした `(v + 1536) − 1536` (定数だとたたまれる)。範囲を縮めてから級数 |
| `gather` | いつも | one-hot の行列積 |
| 指数の `reduce_sum` | コンパイルごとに変わる | 1 との行列積で和 |
| K/V を `tile` で写す注意 | いつも | `SDPAGrouped` (演算の順だけで配置が変わる) |
| 語彙 262144 の `reshape`、最後の部分の `transpose` | その演算 | ホストで並べ替え (PLaMo 3、Gemma 4 の softcap をホストで) |
| `conv_transpose` (M1) | 歩幅 5 と 7。8、4、3 は動くがずれる | ポリフェーズの畳み込み |
| 膨張つき畳み込み、`max_pool` (M1) | 膨張 17〜48。窓 9 と 13 | ずらした写しと 1×1 の畳み込み。窓 5 の連鎖 |
| 深さ方向の畳み込み (M1) | 4096 チャンネルを超える | 4096 以下の塊 |
| 8×8 と 8×8 の行列積 (Qwen3.5 の GDN の塊) | いつも | (8×8)·(8×128) の積 7 つ |
| (3, 39) の畳み込みと ReLU (Basic Pitch) | いつも | 解決していない |

## 数値の落とし穴

配置の報告は値の誤りを示さない。同じプログラムを ANE と CPU で動かして比べる。

### ハードウェアの決まり (M2、Core AI、`aicheck rules`。Core AI の CPU にはどれもない)

| 決まり | 詳細 | hwnpu のすること |
|---|---|---|
| 線形や畳み込みの和は 2^15 未満に | 32768 で Inf (32256 は正しい)。**途中の和も** (1024 入力の +1/−1 の半分ずつ: 和は 0 でも Inf)。`reduce_sum` は 51200 まで正しい | 値の範囲を抑える (MaxScaled、残差の倍率)。下の行ごとの int8 のあふれはこの決まりだろう |
| 最後の軸の切り出しの始まりが 32 で割って 1〜14 | 4094 を超える値が Inf になる。始まり 0 と 15〜31 は正しい。ほかの軸は影響なし | `aicheck lint`、`HWNPU_DEV=ailower.notes=1`。27 の書き出しで当たるのは LFM2-8B-A1B の上位 4 つの経路の重み (≤ 1) だけで、害はない |
| log(1 + exp(x)) にまとめた softplus | x > 10.4 で 0 | `relu(x) + log(1 + exp(−|x|))` |
| 行列積の中の小さな積 | 約 2^-16 より小さいと捨てる (注意のデータで当てはめた。1e-6 の積を 512 足すと 0)。要素ごとの積は保つ。値の小さい注意の `matmul(e, v)` で、重みの小さい多くの鍵が消えた (o が最大 79 % ずれる、[LLM のエンジン](llm-engine.ja.md)) | 大きくしてから後で割る: 注意で分けた形の注意は積の前に e に 1024/l を掛ける |
| 内側の次元が 1 の行列積 | (1,8,M,1)·(1,8,1,128): M = 1 で相対誤差 0.28、M = 64 は正しい | 積 (外積) で書く |
| 33 点の折れ線の活性 | sigmoid、silu、tanh、gelu の最大相対誤差 0.0009〜0.0016 | 下を参照 |
| 定数での割り算 | 積なら問題ない | `x × (1/c)` に下げる |

### 活性

- ANE の `silu` は 1.4 % ずれ、小さい裾の値ほど悪い。`x · sigmoid(x)` も同じ値。どこでも `blocks.SiLU` (`x / (1 + exp(−x))`) と `builder.softplus` を使う。PyTorch fp32 との KL (英語 / 日本語、M3): LFM3-1.7B lut8 0.058 / 0.012 → **0.022 / 0.0048**、PLaMo 3 Translate 2B lut8 0.0067 / 0.0069 → **0.0053 / 0.0042**、Qwen3.5 (silu と softplus) 0.33〜0.76 → 0.005〜0.007。費用: 3790 トークンのプロンプトで +9 %、生成の 1 回で +3 %。
- 深い CNN を通る `sigmoid` はずれる (RTMDet-s、SiLU 80 個: 箱が 98 px ずれる、CPU では 7.5)。exp で書く (`onnx.Program.ExpSigmoid`)。
- tanh の `gelu` は問題ない (Gemma 4: 書き直しても変わらない)。

### 値

- **行ごとの int8 は大きな出力であふれる**: ANE は int8 の符号どうしを掛けてから行の倍率をかけるので、13000 の出力 (Qwen3-VL-8B の注意の sink) が NaN になった。lut8 は先に fp16 に戻すので正しい。
- fp16 の上限に近い値 (SANA 1.5 の `<bos>` の行 38 000、SpectroStream は 1.2e7 まで) は ANE だけで NaN になる。後ろに norm があるなら線形を 1/64 に、なければ 2 のべき乗の倍率で。
- 線形の隣の定数の倍率は重みにたたみ込まれ、積が fp16 の正規の範囲を下回ることがある (T5 の外れ値の行: コサイン 0.36)。射影の出力に掛ける。
- 詰め物の行は本物のトークンで埋める (fp16 で eps 0 が NaN になった)。
- 後のすべての層が読む 1 行の計算 (時刻の埋め込み) は最大 1 % ずれた。ホストの float32 で計算する。

### 確かめ方

1. 同じプログラムを ANE と CPU (`HWNPU_COREAI_UNITS=cpu`、`HWNPU_COREML_UNITS=cpu`) で動かし、位置ごとに比べる (ロジットの KL かコサイン)。詰め物は別に数える。
2. 原因を探す前に、参照の fp16 と比べる。HF の fp16 も同じだけずれるなら移植の誤りではない (Whisper の符号器: 無音の位置の注意の sink で、ANE の誤りではない)。
3. 最初の N 層だけ変換し (`hwnpu-dev convert -layers N`)、ずれの始まりを探す。
4. ANE と CPU のインタプリタの間で演算ごとに二分する (`internal/vision/detect` の `TestBisect`)。または部品を 1 つずつ CPU に移す。

CPU の `hwnpu-dev check` にはどれも出ない。

## プロンプトのプログラム

1 回の費用の大半は重みの読み出しで、64 行は 8 行の 1.06 倍。そこでプロンプトのプログラムは 1 回に多くの行を読み、ロジットは最後の行だけ計算する。

- 注意で分けたモデルはプロンプトを `pagedPrefillSeq` = 1 回 128 トークンで読む (`…-q128-last`)。分けないモデルは鍵の軸を 16384 以下に保つため 64。Intel は `LastRow` なしの 64。
- `llm.Options.LastRow` (LFM3、Gemma 4): 最後の行を one-hot の入力 `last` との積で取る (gather は CPU なので)。y は (1, 1, 語彙)。
- KV を共有する Gemma 4: 最初の共有の層から先は全部の層を 1 行で動かす (`attendOne`)。
- Core AI での数値は [LLM のエンジン](llm-engine.ja.md)。

## プロセスどうしのロック

2 つのプロセスが同時に ANE を使うと M1 が固まった (予測が返らず、プロセスを殺せず、約 20 分で戻った)。そこで:

- `llm.OpenDevice` は Core AI か Core ML のデバイスのとき、ユーザーのキャッシュの `hwnpu/neural-engine.lock` に排他の flock を取り、プロセスの終わりまで持つ。ファイルはいつもユーザーのキャッシュ (`~/Library/Caches/hwnpu`) にあり、`HWNPU_CACHE` で別のキャッシュを使うプロセスも同じロックを待つ (2026-11-26 まではキャッシュの下にあり、別のキャッシュのセッションが並んで ANE を使った)。2 つ目のプロセスは `waiting for the Neural Engine: process N (NAME) is using it …` と出す。プロバイダを直接開く道具は `llm.LockNPU` を取る。
- ロックを取ったあと `settle` は、前のプロセスのプログラムが ANE から消えるまで待つ (`mem.NPUWired` を 0.1 秒ごとに、最大 30 秒)。持ち主は見つけた hwnpu 以外の分 (`base N`) をファイルの 2 行目に書く。
- 理由: プロセスのプログラムは終わったあとも ANE に残り (忙しい機械で最大 7 秒)、その間に読み込むプロセスは失敗しうる (`Request cancelled`)。別のプロセスのコンパイルが動いているプログラムを失敗させることもある。
- ロックを飛ばす道はない (`HWNPU_NPU_LOCK` は 2026-11-22 になくした)。ほかのセッションが何時間もロックを持つことがある: ANE の仕事は順番を待つ。
- ロックを持つプロセスが起動したプロセスは、同じロックの下で動く (`HWNPU_NPU_LOCK_FD`: ロックのファイルの記述子を渡す。`tools/coreai/aicheck locked CMD`)。飛ばすのではなく、親が持ち続ける: 試行の列の途中でほかのセッションに ANE を取られないために使う。

## Neural Engine のメモリ

- ANE の重みは、プロセスの RSS にも footprint にも `aned` にも出ない。`com.apple.driver.AppleH11ANEInterface` の下のカーネルの wired メモリで、`mem.NPUWired` が purego 経由の `mach_memory_info` で読む (root 不要、ゾーンは名前で探す)。何もしないとき 144〜192 KiB。
- 機械全体の値なので、ロックを持って測る。
- 同じ重みの 2 本のプログラム (Q=8 と Q=128) は 2 回分持つ: LFM3-1.7B lut6 で 2.43 GiB (1.21 GiB × 2)。
- コンパイルしたばかりのプログラムは読み込んだ直後は ANE になく、最初の呼び出しで載る。`hwnpu-chat` は「the Neural Engine holds N GiB」と出し、重みの半分に満たないときは「so far」を添える。

## 採らなかったもの

- どのチップでも 2.8 GiB の予算: M2 以降でプロンプトのプログラムを失う。少なく読むのは M1 だけ。
- silu を `x · sigmoid(x)` で: ANE の `silu` と同じ値。
- `gelu` の exp の形 (Gemma 4): 変わらない。Anima の VAE の silu の exp の形: 絵は変わらず、VAE が 15〜20 % 遅い (Core ML。Core AI の書き出しは、ネイティブの形を `coreai-build` が落とすので exp の形にする: docs/design/image-apple.ja.md)。
- 1 回 256 トークンのプロンプト: 128 より速くなく、読み込みが重い。
- 注意の問い合わせを既定で分ける: Whisper の 90 MB のスコアで得がない。

## 未解決

- 2 つのプロセスで ANE が固まる理由。Intel と AMD は試しておらず、ロックは Apple だけ。
- システムの ANE のコンパイルのキャッシュの大きさと場所 (sudo が要る)。M1〜M4 の `hwnpu-dev probe cache` の結果は未記録。
- 16384 の上限で、どの形が CPU に落ちどれが残るか。
- 重み以外の ANE のメモリ (KV、途中の値) を分けて見られない。
- M1 Pro / Max / Ultra の上限 (M1 と同じとみなしている)。
- `silu` の書き直しは LFM3-VL / Audio / Omni / d1、その塔、TTS では測っていない。
