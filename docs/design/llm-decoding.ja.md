# デコード: 下書き、思考の上限、堂々めぐり

[English](llm-decoding.md)

`chat.Engine` が 1 ステップ 1 トークンより先に進む仕組み: プロンプトからの下書きと Qwen3.5 の MTP の
下書きによる投機的デコード、思考の上限、堂々めぐりの検出。どのバックエンドにも共通。AMD の確かめる版は
[amd-llm.md](amd-llm.ja.md)。キャッシュと分ける形は [llm-engine.md](llm-engine.ja.md)。

## フラグと既定

| 設定 | 既定 | 意味 |
|---|---|---|
| `--draft N` | 8 | 生成のプログラムの 1 回のトークン数。下書きは N − 1。0 か 1 でなし (Q=1) |
| `--mtp` | `auto` | チェックポイントに MTP の層があれば (Qwen3.5) それからも下書き。`off` はプロンプトだけ |
| `HWNPU_DEV=mtp.drafts` | 2 (`mtpDrafts`) | MTP の下書きを続けていくつ |
| `HWNPU_DEV=iron.drafts=0` | | AMD: 確かめる版を使わない |
| `--think` / `--no-think` | 考える (モデルの `no_think` があればそれ) | 答える前に考えさせる |
| `--think-budget N` | 1024 | 答えに移らせるまでの思考のトークン数。0 で無制限 |
| `--rep` | 1.05 | 答えのトークンへの繰り返しの罰 |
| `-n` | chat 0 (キャッシュが埋まるまで)、agent 2048 | 答えの長さの上限 |
| API の `reasoning_effort`、`chat_template_kwargs.enable_thinking` | | 要求ごとに `--think` と `no_think` より優先 (`Server.thinks`) |

ログと統計 (`chat.Stats`): `Drafted`、`Accepted`、`Calls` (`(a of d drafts accepted, c calls)`)、
`ThinkCut` (`thinking cut at N tokens`)、`ThinkLooped` (`thinking cut going round in circles`)、
`Looped` (`stopped repeating itself`)。

## 投機的デコード

理由: Neural Engine の 1 回の呼び出しの費用は 1 トークンでも 8 トークンでもあまり変わらない (M3、
LFM3-1.7B lut4、Core ML: Q=1 61.5 ms、Q=8 72.0 ms (+17%)、Q=64 103.2 ms)。Q=8 は 1 回に平均 0.15 個
当たれば元が取れる。エージェントは読んだものを書くものに写すので、答えがプロンプトを繰り返す。

### 生成は 1 つのプログラムで

- `--draft 8` では生成のプログラムを Q=8 にし、下書きのないステップもそれで動かす。読み込むのは従来
  どおり 2 本 (生成とプロンプトを読むもの)
- 理由: プログラムの切り替えは高い (M3、Core ML: Q=1 と Q=8 を交互に呼ぶと、空いた機械で 1 回 35 ms、
  スワップ下では 100 ms 超)。下書きの有無で切り替えると、下書きのない呼び出しが 2 倍になった

### プロンプトからの下書き (`LookupDraft`)

- 直近 n トークン (n = 4 から 1) の並びが前に出た最後の場所の続きを、最大 k 個
- 1-gram も出す: Q=8 では確かめるのが無料 (56 要求の再生で 3..2-gram 1.552 トークン/回、4..1-gram
  1.673、+7.6%)
- 下書きの長さは答えの上限、キャッシュの残り、思考の予算の残りで切る

### 採るのは一致したときだけ

- `Generate` は「本物 1 つ + 下書き k 個」を `speculate` に渡す。位置 i の下書きは、位置 i−1 のロジット
  からサンプリングした値と同じなら残す。最初に分かれた位置のサンプル、全部当たれば最後の行のサンプルが
  次の本物になる
- 貪欲法では 1 トークンずつと厳密に同じ出力。温度ありでも分布は変わらない: 残るトークンはいつもその
  位置でサンプリングした値そのもの。棄却サンプリングはしないので補正は要らないが、当たりは少ない。
  下書きが繰り返しを増やすことはない
- 残した下書きは 1 つずつ `take` (停止トークン、思考の予算の計数、`emit`、繰り返しの検出、上限) を通す

### ステップの一部だけを残す (`decode.Session.Speculate`)

- `Step` を `run` (入力を書いて動かす) と `keep(v')` (先頭 v' 行だけキャッシュに書く) に分けた。
  `accept` は各行のロジット (`row(i)`) を必要なときに読む
- 全注意のキャッシュ: 位置より先はマスクで見えないので、捨てる行は放置。リングは i < v' だけ書く。
  畳み込みの窓は `win_*_new` (W+Q 行) の v'..v'+W 行を取る。写しは要らない
- 丸ごと置き換える状態 (Qwen3.5 の GDN の `st_`): 出力の状態は全部の行の後のものなので切れない。2 通り:
  - `state-rows` (`llm.StateReplayer`、`qwen35.Config.ReplayState`、名前に `-sr`、下書きを確かめる
    プログラムだけ): プログラムが `st_rec_N_rows` (1, 値ヘッド, 行, dk+dv+2: 各行の k、v、β、減衰) も
    出し、ホストがステップ前の状態から残した行だけ delta rule を進める (fp32、ヘッドごとに並列)。
    呼び出し 1 回。0.8B で 1 層 66 KB
  - なければ残したトークンで回し直す (入力のバッファにステップ前の状態が残っている)。呼び出し 2 回
- AMD (IRON) は専用の確かめる版を持ち、行ごとの状態をデバイスの側で残す (`iron.Model.Keep`)。ホストでの
  戻しは要らない。[amd-llm.md](amd-llm.ja.md)

### 測った値 (プロンプトからの下書き)

M3 16 GB、Core AI、LFM3-1.7B lut6、`hwnpu-chat serve`、温度 0、思考なし、同じプロンプトを 3 回 (3 回の差は 1% 以内):

| | 散文 300 トークン (「自転車のギアの仕組み」) | 1159 トークンの Go のファイルを写し返す 600 トークン |
|---|---|---|
| `--draft 8` | 49.5 トークン/秒 (20.2 ms/token) | 285 トークン/秒 (3.5 ms/token) |
| `--draft 0` (Q=1) | 44.8 トークン/秒 (22.3 ms/token) | 44.8 トークン/秒 (22.3 ms/token) |

- Core AI では Q=8 のプログラムの 1 回の費用が Q=1 とほぼ同じなので、散文でも下書きで 1 割速く、プロンプトにある文を写すときは 6.4 倍。(Core ML では Q=8 の費用が大きく、エージェントの課題で 1.2〜1.5 倍、写すもののない思考では 1〜1.5 割遅かった)
- 当たるもの: 道具の呼び出しの XML、繰り返しの命令 (`go run main.go`)、前の文を言い直す要約。自由な
  散文はほとんど当たらない (「空はなぜ青いか」で 340 個中 28 個)

## Qwen3.5 の MTP の下書き

Qwen3.5 のチェックポイントは複数トークン予測の層 (`mtp.`) を 1 つ持つ。hwnpu はそれを下書きのモデルに
使う。

### 層 (`internal/llm/qwen35/mtp.go`、`-arch qwen35-mtp`)

- transformers には実装がないので vLLM の `qwen3_5_mtp.py` から移した。位置 t で、トークン t+1 の埋め込み
  と本体の最終の隠れ状態 h_t (最後の norm の後) をそれぞれ 0 中心の norm (`pre_fc_norm_embedding`、
  `pre_fc_norm_hidden`) に通し、埋め込みを先に連結して `fc` (2d → d)、全注意の層 `mtp.layers.0`、
  `mtp.norm`、本体の出力層 → トークン t+2 のロジット
- `llm.Model` としては 2 層: 層 0 を前段 (norm、連結、fc) にして、`-paged` が注意の前で分けられるように
  した (層 0 の注意はホストで回せない)。入力は `x` と `hid`。キャッシュつきでは自分の `h` も出し、2 つ目
  からの下書きは本体の h の代わりにそれを読む (vLLM と同じ)
- 本体の側: Arch の param `hidden-out` (名前に `-h`) が全部の行の最終の h を出す。
  `decode.Session.HiddenRows` が残した行の分を返す
- 照合: vLLM の forward をそのまま書いた fp64 の正解と 1.3e-7 (`TestMTPAgainstFP64`)、キャッシュつき、
  `Truncate`、分けた形 (`TestMTPCached`、`TestMTPPaged`)。連結の順を入れ替えると 8 件落ちる

### 下書き係 (`internal/chat/mtp.go`、`mtpDrafter`)

- 本体の各呼び出しの後に、残したトークンの h を受け取る (`Engine.recordHidden`)。下書きの前に、次の
  トークンが分かった位置を読ませ (Q=8、`LastRow`)、最後の行の argmax が 1 つ目、2 つ目からは 1 トークン
  ずつ。終わったら `decode.Session.Truncate` で本物の位置まで戻す (状態は全部位置ごとの KV なので印は
  要らない)
- 位置は `base` から: RoPE の注意は相対位置しか見ない。戻りや会話の入れ替えでは共通の先頭まで残す
  (`sync`)。512 位置より遅れたら (`mtpStart`) プロンプト全体を読まずにそこからやり直す
- プロンプトからの下書きが MTP の 1 つ目と合っていて長ければそちらを使う
- `TestMTPDrafts`: 出力は 1 トークンずつと同じ。1 つ目の下書きは読み直した MTP の層と同じ
- 変換 (`chat.Prepare`、`--draft` 2 以上、`--mtp auto`): 本体に `-h`、下書きを確かめるプログラムに
  `-sr`、MTP のプログラム `qwen35-mtp-<形式>-p8192-[dv2-]c262144-q8-last`

### 語彙の一部 (`draftVocab`、規則 `dv2`、Core AI だけ)

- MTP の出力層は本体の 248320 行で、MTP の 1 ステップ 13.6 ms のうち 11.4 ms (4B、M2)、本体の 1 ステップ
  ごとに 2 回。下書きは本体が確かめるので、語彙を絞っても答えは変わらず、外のトークンが下書きされない
  だけ (FR-Spec と同じ考え)。`llm.Options.HeadRows`、`llm.SelectRows`
- 規則: ID < 32768 に加え、かなを含むもの、漢字 1〜2 字、ASCII の記号と空白だけのもの。16 の倍数に
  埋める。約 7.4 万行 (30%): 日本語 97%、英語と Go 96%。低い ID だけでは英語 95% だが日本語は 65%
  (日本語のトークンは語彙全体に散っている)
- 行の一覧は書き出しの `draft-vocab.json`。`mtpDrafter.token` が添字をトークンに戻す。規則は名前に入る
- 効果 (4B、M2、Core AI): MTP の部品 2 が 0.68 → 0.26 GiB、MTP の 1 ステップ 13.6 → 6.6〜6.9 ms、答えは
  バイト単位で同じ。MTP の注意も短い塊にして (`AddSmaller`) MTP の 1 ステップ 6.5〜6.8 ms、生成 20.5〜21.9
  トークン/秒

M1 16 GB、Core ML、`--prefill off`、温度 0、トークン/秒 (採用 / 下書き)、`state-rows` つき:

|---|---|---|---|---|
| プロンプトだけ (`--mtp off`) | 32.1 (79/696) | 25.8 (11/323) | 23.5 | 19.3 |
| MTP 1 つ | 40.9 | 27.4 | 29.6 | 21.6 |
| **MTP 2 つ (既定)** | **43.8 (169/308)** | **30.3 (90/263)** | **32.4** | **20.1** |

## 思考の上限 (`chat.ThinkLimit`、`chat.Request.Think`)

- 思考の中 (テンプレートの開く印と閉じる印の間、または `Render` が思考の中で終わるプロンプトの続き) で
  `Budget` トークン生成しても閉じないとき、テンプレートの `End` (「もう時間がない」の一文と閉じる印。
  `Template.Think`。LFM3 は `</think>`、Gemma 4 は `<channel|>`) をモデルが生成したものとして流し込む
  (`step` を Q トークンずつ)。流したトークンも `emit` に渡るので、ストリームは閉じる印を見る
- 考えないモードでモデルが自分で `<think>` を開いたときも、開く印から同じ上限で数える
- 理由: OpenCode の題名づくりの要求 (587 トークン、道具なし) が 3440 トークン考えて 226 秒かかり、本題が
  後ろで待った (M3、LFM3-1.7B)
- モデルごとの既定: `--think` を与えなければ models.yaml の `no_think` (`chat.Model.NoThink` →
  `Engine.NoThink`)。Qwen3.5-0.8B と 2B は考えさせると堂々めぐりになる ([llm-qwen.md](llm-qwen.ja.md))
- `TestThinkBudget`: 予算の後に `End` が流れ、流したトークンが `emit` に届き、ロジットが最初から読んだ
  ときと 2e-3 以内で一致

## 堂々めぐりの検出 (`chat.repeats`、`internal/chat/repeat.go`)

理由: 小さなモデルは同じところを回る (LFM3-1.7B に「東京の23区」: 思考で一覧を書き直し、答えでも何千
トークンも続ける)。`-n 0` と文脈 262144 では何時間も続きうる。`--rep` は字面の繰り返しを弱めるだけ。

本当の答えも繰り返す (下書きの清書、同じ準備の行を持つテスト、JSON の鍵、表の行)。違いは回数: 清書は
2 回目、堂々めぐりは 3 回目以降が続く。「前に 1 回出た」の割合は重なる (堂々めぐり 0.50〜0.92、正常な
思考 0.58) が、「前に 2 回以上出た」で分かれる (正常: 行は最大 7/16、8 トークンの並びは最大 50/256)。

| 数え方 | 規則 |
|---|---|
| 行 | 単語 (字を含むトークン) が 2 つ以上の行を、トークンの並びのハッシュで数える。直近 16 行のうち 12 行が 3 回目以降なら繰り返し。単語のない行 (`}`、`---`、数だけの表の行) は数えない。数字は区別したまま (まとめると日付と天気の表で止まる) |
| 8 トークンの並び | 直近 256 位置のうち 230 位置で、そこで終わる並びが 3 回目以降なら繰り返し (改行のないループ、周期は問わない) |
| `looping` | 直近 64 トークンが周期 16 以下の 1 つの並び |

- 思考と答えは別に数える (`<think>`、`</think>` で数え直す): 思考で 2 回書いたものを答えでもう 1 回
  書いてよい
- 答えの中で見つけたら止める (`Looped`)。思考の中なら、予算に届いたときと同じく閉じて答えさせる
  (`ThinkLooped`)
- トークンの分類 (改行、字) は最初の生成でトークナイザーの語彙から作る。トークナイザーのないエンジンは
  並びだけで数える
- 確かめたこと: ログに残った正常な 24 の思考と答えでは一度も見つけず、23 区の堂々めぐりでは見つける。
  正常な答えを切らないことを優先して遅めにしてある (23 区の答えの 1 つは約 3700 トークンで止まった)
- テスト (`repeat_test.go`、`TestThinkLoop`): 20 の名前を少しずつ順を変えて回す行は 2 周より後に見つけ、
  40 行の清書、同じ準備の行を持つテスト 20 個、数字だけが違う 120 行は見つけない。改行のない周期 100 の
  並びは 200 トークンより後に見つける

## 採らなかったもの

- 棄却サンプリング (違う下書きも確率で残す): 一致だけを残せば補正なしで分布が保たれる
- 下書きの有無で Q=1 と Q=8 を切り替える: 切り替えが 35 ms 以上かかる
- 下書きに Q=4: 1 回が Q=8 より 2 ms (3%) 安いだけで、下書き 3 個は 7 個より 1 回あたり 1 割少ない
- 3..2-gram や最初の出現を取る推測: 1.552 / 1.550 トークン/回で、4..1 の 1.673 に劣る
- MTP の下書き 3 つ: 当たりが減り日本語で遅くなる。1 つごとに出力層を 1 回払う
- 低い ID + かな + 漢字 1 字の語彙 (`dv1`、43618 行): 説明、計算、``` を外し、採られた下書きが 82 → 67 に
  減って語彙全体より遅かった
- 答えの長さの既定の上限: 長い答えが切れる。代わりに繰り返しを見つける
- 堂々めぐりに `--rep 1.1`: 字面の繰り返しを弱めるだけ
- 「前に 1 回出た」で数える: 正常な答えと重なる
- AMD のプロンプトの塊の版で下書きを確かめる: 1 回にデコード 4.5 ステップ分の固定費がかかり、プロンプト
  からの下書きは 1 回 1.07〜1.3 個しか当たらない。代わりに専用の確かめる版 ([amd-llm.md](amd-llm.ja.md))
- Core AI の shim の入力の写しをなくす: 1 回 0.5 ms ほど (4B の 1 ステップの 4%)。呼び出し側のバッファの
  view はかえって遅かった

## 未解決

- AMD (本体の隠れ状態を出し、MTP の層の版が要る) と Intel での MTP の下書き
- 長いプロンプトの後の最初の MTP の下書きまでの時間 (最大 64 回)
- ロジットを fp16 のまま argmax して 248320 個の変換を省く
- エージェントの課題で温度 0 と 0.1 の下書きの比較。OpenCode の長い XML の往復での採用率
