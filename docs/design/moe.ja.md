# 専門家の混合 (MoE)

[English](moe.md)

hwnpu が専門家の混合 (MoE) のモデルをどう動かすか: Apple の gpt-oss-20b、Qwen3.6-35B-A3B、LFM2-8B-A1B と、AMD の NPU の gpt-oss-20b、Qwen3.6-35B-A3B。経路の選択と専門家をどこで回すか、専門家をメモリにどう置くか、今の値と、何がそれを決めているかを書く。

## モデルと動く場所

| モデル | 形 | Apple (Core AI) | AMD (IRON) | Intel |
|---|---|---|---|---|
| gpt-oss-20b (`gpt_oss`、21B、トークンあたり 3.6B) | 24 層、窓 (128) と全体の注意が交互、sink、YaRN。専門家 32 個から 4 個、チェックポイントは MXFP4 | 部品は Neural Engine、専門家は CPU でチェックポイントの MXFP4 のまま (`llm.HostRouted`、`experts.Host`) | 専門家は MXFP4 のまま (`mx4`)、経路は NPU。16 GB の機械は置き場 16 とホストの経路 | なし |
| Qwen3.6-35B-A3B (`qwen3_5_moe`、arch `qwen35moe`、35B、3B) | 40 層 = Gated DeltaNet 30 + 全注意 10、hidden 2048。専門家 256 個 × 中間 512 から 8 個と、sigmoid のゲートつきの共有の専門家 (512) 1 個。bf16 で 72 GB | gpt-oss と同じ形: 専門家は CPU で、派生のチェックポイントの MXFP4 | 専門家は q4。メモリに合わせて置き場 32 / 128 / 全部 | なし |
| LFM2-8B-A1B (`lfm2_moe`、8.3B、1.5B) | 専門家 32 個から 4 個 | 専門家は Neural Engine で、重みを持たないプログラム (`llm.Routed`)。M2 以降 | なし | なし |
| gpt-oss-120b | 36 層、専門家 128 個から 4 個 | — | 確かめただけで models.yaml にはない (採らなかったもの) | — |

- Neural Engine と Intel の NPU は経路の `gather` を回せない。Apple では部品の間でホストが専門家を選ぶ。Intel の形はない。
- models.yaml は機械のメモリで書き出しを選ぶ (`variants`):

| モデル | 16 GB | 24 GB | 48 GB |
|---|---|---|---|
| gpt-oss-20b、AMD | `--expert-places 16 --host-route` (8.3 GB) | 全部 (14.6 GB) | 全部 |
| gpt-oss-20b、Apple | 専門家を予算まで固定 (6.4 GB) | 全部固定 (12.2 GB) | 全部固定 |
| Qwen3.6-35B-A3B、AMD | `--expert-places 32` (8.2 GB) | `--expert-places 128` (17.2 GB) | 全部 (26.3 GB) |
| Qwen3.6-35B-A3B、Apple | 固定しない (2.7 GB とページキャッシュ) | 同じ | 同じ |

- 32 GB の AMD の機械は置き場 128 のまま: 全部 (26 GB) は余裕が少ない。
- hwnpu-chat (`internal/chat`) は MoE のモデルで下書きとキャッシュの tier を使わない (採らなかったもの)。

## 専門家の使われ方、芯、先読み (両方の会社)

- **数える**: `experts.Usage` が層ごとの選択を記録する。hwnpu-chat はモデルとアプリのキーごとにファイルを持つ: Mac は `~/Library/Caches/hwnpu/models/<モデル>/experts-usage/<キー>.bin`、Linux は `~/.cache/hwnpu/models/<モデル>/experts-usage/<キー>.bin` (`--experts-key`。測るときは `off`)。`HWNPU_DEV=moe.usage=FILE` も同じ形で書く。AMD の `iron.Model.CountExperts` は、プロンプトはホストの経路で数え、デコードは次のコマンドのスクラッチパッドに書かれた位置の語を読み戻す (費用は測れない)。
- **`tools/moeusage`**: `prompts.tsv` (110 プロンプト、19 分野、約 25 言語)、`collect.sh`、`analyze.py`、`place.py`。結果:

| | gpt-oss-20b (32 個から 4 個) | Qwen3.6 Mac (256 個から 8 個) | Qwen3.6 AMD | gpt-oss-120b (128 個から 4 個) |
|---|---|---|---|---|
| 分野の中で、よく使う半分 | 74〜90 % | 89〜95 % | — | — |
| 全分野を混ぜて、半分 | 81 % | 81 % | 上位 64 個で 59 %、128 個で 83 % | 上位 64 個で 88 % |
| ほかの分野で選んだ半分: コンピュータ、数学 | 59 %、63 % | 60 %、63 % | 45 %、48 % (上位 64 個) | 69 %、70 % (上位 64 個) |
| 芯 (どの分野でも均等な割合以上) | 141 個 (1.9 GB)、選択の 31〜41 % | 841 個 (1.4 GB)、21〜28 % | 901 個、24〜31 % | 515 個、29〜40 % |
| 使われない専門家 | なし | なし (10 回未満は 8 個) | 少しある (10 回未満は 78 個) | 5 個 (10 回未満は 39 個) |

- gpt-oss-20b の AMD の統計は Mac とほぼ同じ (芯 140 個と 141 個、131 個が共通): 注意と mx4 の専門家で選ばれ方が同じになる。models.yaml の `experts_core` は両方の会社で 1 つ。
- AMD では、置き場の半分を超える層の芯は外す (`internal/llm/iron/pool.go`): 置き場 32 では芯が置き場の大半を取り、コピーが 34.4 → 36.7 % に増えた。
- **次の層の予測**: 層 l の専門家に入った残差に層 l+1 の norm の重みと router を掛けると、層 l+1 の専門家を予測できる (Fate、MoE-CORE)。当たり: gpt-oss-20b は上位 4 個に 86〜87 %、8 個に 97〜98 %。Qwen3.6 は上位 4 個に 44〜48 %、8 個に 72〜82 %、16 個に 95 %。低いのは 256 個から 8 個を当てる問題の大きさのためで、専門家の分かれ方のためではない。

## Apple: 専門家を CPU で (gpt-oss-20b、Qwen3.6)

### 切り方

- `llm.PlanRouted` は MoE の層ごとにモデルを切る。Neural Engine の部品は token mixer、経路のロジット、(Qwen3.6 は) 共有の専門家を回す。部品の y は「残差 + 共有の専門家」で、ホストの専門家の出力 (`moe_o_N`) を次の部品が足す。
- ホストは上位 k 個を取り (`experts.Routing{softmax, Norm}`: 全体の softmax を選んだ分で正規化し直す)、選んだ専門家を `experts.Host` で回す。SwiGLU (`ActSiLU`) と bias なしの専門家も扱う。記録に経路と norm の名前 (`MXFP4.Router`、`Norm`、`NormOffset`: 0 中心の norm は 1 を足す) があり、先読みがどのモデルでも動く。
- 書式: gpt-oss の注意は `lut8r` (行ごとのスケールつきの lut8)、出力層は `lut6r`、router は fp16 (アーキテクチャの Revision 4)。Qwen3.6 は経路と共有の専門家のゲートが fp16、ほかは lut8、出力層は lut6r。
- 専門家はチェックポイントを写像して読む (`safetensors.File.Map`、コピーしない)。gpt-oss は 10.2 GB。

### MXFP4 のカーネル (`internal/mxfp4`、NEON)

- e2m1 は表で引く。活性の行は 32 個ごとに int8 にする。1 ベクトルは SDOT、同じ専門家の 8 行以上は SMMLA (`mm28NEON`、FEAT_I8MM、M2 以降)。
- 累算は `EOR v,v,v` でなく `MOVI` で 0 にする: M3 では EOR がレジスタの前の値を待ち、和が直列になる。MOVI でカーネルが倍に (1 ベクトルの行 65 → 32 µs)。
- `mxfp4.Rows` (`mvNEON`): 複数の行を 1 回の呼び出しで。1 コア 45.6〜47.3 GMAC/秒。メモリでなく NEON の命令数で決まる (2 ブロックに約 20 個)。`Dot` とビット単位で同じ。
- 符号化 (`mxfp4.Encode`): 32 値ごとの 2 の冪の scale は、OCP の規則 (最大値の指数 − 2) とその前後のうち二乗誤差の小さいもの。値は最も近い e2m1 (同じ距離は偶数)。正規分布の値で相対誤差 0.113。

### 生成: 1 トークンの専門家

- `Host.runRow`: 専門家を一片 (重み 128 × 2048 個) に分け、どのコアもどの一片でも取る。gate/up の最後の一片を終えたコアが活性化を計算し、その専門家の down を開ける。働き手を起こすのは 1 層 1 回。呼び出し側は仕事の中にいる働き手だけを待ち、後から起きた働き手は閉じた実行を見て寝直す。前は専門家 1 個を 1 コアに渡していて、効率コアや遅く起きたコアを層が待った (8 本の働き手の後ろの 4 本は起きるのに 85 µs〜3 ms、`TestWake`)。
- 活性化は `f32.GLU` (arm64 は NEON: LD2 で gate と up を分け、Cephes の expf)。値ごとの float64 の `math.Exp` ではない: gpt-oss の専門家の 2880 個が M2 で 22 µs かかり、その間 down が待っていた。バイアスは積に足し込み、専門家の出力は `f32.Axpy` で足す。`runRow` の配列は次のトークンに使い回す (`Host.rowBufs`): 1 層 217 KB の確保で、GC の消去と返却が専門家の CPU の 16 % だった。合成の gpt-oss-20b の 1 層、M2、層の間 1.5 ms (`TestHostRunGap`): 平均 1.51 → 1.39 ms、中央値 1.11 → 1.07、p99 6.7 → 5.9。続けて (`BenchmarkHostRun`) は約 2 % で揺れの範囲: 積が 425 MB の重みを読む。
- `mem.Probe`: 範囲の 2 ページだけを `mincore` に聞き (範囲はまるごと読まれ、まるごと使われる)、1 秒以内には聞き直さない (`hostLayer.fresh`)。割り付けたファイルの `mincore` は 1 ページ 0.25 µs で、専門家の CPU 時間の 47 % を占めていた。
- 1 層の専門家 8 個、全部メモリ (`TestHostTokenTimeQwen36`): 続けて 8 コアで 0.28 ms (1 コア 0.64)、1.2 ms の間のあと 0.79〜0.90 ms。間のあとの遅さは呼び出し側のスレッドが眠るため (`HWNPU_TEST_QWEN36_SPIN` で消える)。未解決を参照。

### メモリ: 固定 (`experts.Host.wiring`、`experts.Placement`)

| 専門家の大きさとメモリ | 既定 |
|---|---|
| 1/2 以下 | 全部固定 (mlock)。M4 32 GB で固定なしに対し 1 層 1.8 → 0.9 ms、13.5 → 18.0 トークン/秒 |
| 1/2 超、3/4 以下 (16 GB の gpt-oss-20b) | メモリの 1/4 (16 GiB で 4.3 GB) の予算まで専門家ごとに固定: 芯が先、次にアプリの統計。30 秒ごと (初回は 5 秒後) に入れ替え、`--idle` (5 分) 後は芯以外を外す |
| 3/4 超 (16 GiB の Qwen3.6、17.1 GB) | 固定しない。ページキャッシュに載る分だけ載り (6〜7 GB)、システムはそれを空きに数える |

- これを変える設定はない: `HWNPU_MOE_WIRE` は 2026-11-27 になくした (測定には `HWNPU_DEV=moe.prefault=wait` で、最初の実行の前に全部のページを固定して読み込める)。
- Qwen3.6 を固定してもページキャッシュの取り分が移るだけ: なし 10.6、2 GB 9.1、4.3 GB 8.6〜8.8 トークン/秒で、全部メモリにある層まで遅くなった (システムの空き 19 % 対 51 %)。
- **空きメモリに追う予算** (`placer.effective`、`mem.PressureNow`、5 秒ごと): 予算 = 空き + このプロセスが固定した分 − 25 % (システムの警告の後 5 分は 35 %)。危機 (Level 4) では芯だけ。空きの 2 % 以内の変化では動かさない。自分の固定を空きに数えるので落ち着く点がある。空きの割合だけで決めると振動した。
- **警告の後** (芯より多く固定しているとき、`placer.warned`): そのときの固定より 1 段 (予算の芯より上の 1/4) 下を上限にして 10 分保ち、その後 1 段ずつ戻す。戻した直後の警告で保つ時間を倍に (最長 80 分)。起動をまたいで `experts-usage/ceiling` に残す (`Placement.Ceiling`)。
- 読み込み中の ENOMEM はその場でやり直す。
- **入れ替えの方式**: 点数を半分にして直近の割合を足す。`place.py` で比べたほかの方式も平均の当たりは 72〜74 % で、変えていない。

### メモリに無い専門家を読む

- 割り付けたファイルを各コアのフォールトで読むと 16 KB ずつで 0.4〜0.6 GB/秒。同じ SSD は 1 MiB の `pread` 1 本で 2.6 GB/秒、4 本で 4.7 GB/秒。
- `Host.readIn` / `readChosen` / `experts.reader` (`reader.need`): 行 (またはプロンプトの塊) の専門家を回す前に、メモリに無い範囲を `pread` (1 MiB ずつ、読み手を複数) でまるごとページキャッシュに読み、写像から使う。`mem.Resident` の無い OS では `madvise(WILLNEED)` に戻る (0.5 GB/秒)。`HWNPU_DEV=moe.need=0` でフォールトに任せる。
- **先読み** (`experts.prefetcher`、既定で入): 予測は Neural Engine の部品の間に別の goroutine で回す。予測した専門家のうち固定されていないものに `madvise(WILLNEED)` をかけ、読み手が読む。数 `prefetchN` は 1 トークンが選ぶ数、最小 4 (gpt-oss 4、Qwen3.6 8)。ディスクから専門家を読んだ後の 10 秒は上位 2 個だけ (`prefetcher.auto`、`reader.short`)。`HWNPU_DEV=moe.prefetch=N` で数を固定、`0` で切る。
- 冷えた読み込みの計測 (`tools/moeusage/read_bench.py`、ページキャッシュを落とす): gpt-oss-20b の専門家 1 個 (13.2 MB) は写像のページフォールトで 13.9 ms、O_DIRECT で 3.0 ms、2 MiB 読みを 4 本で 2.6 ms。Qwen3.6 (6.3 MB) は 6.9 対 1.4 ms。ページキャッシュにあれば 0.04 ms。Mac の直接読みは未計測。
- M2 (`TestColdRead`、`mincore` でメモリに無い専門家を選ぶ、1 個 13.3 MB): フォールトで 0.5〜0.6 GB/秒 (1 専門家 20〜27 ms)、`madvise(WILLNEED)` してから触れて 1.7〜1.8 GB/秒 (7.1〜8.1 ms)、1 MB ずつ 4〜8 スレッドの `pread` で 2.7〜2.8 GB/秒 (4.7〜4.8 ms)。4.8 ms でも Neural Engine の部品の間 (約 1.5 ms) より長く、SSD から読む外れは先読みで隠しきれない。

### プロンプト

- **wave** (`decode.Session.Steps`、`decode.Program.RunMany`、`chain.tier.runMany`): 128 トークンのステップを全部 1 つの部品に通してから次の部品へ。段は注意の層で切る (`RunPart(i)`)。1 ステップずつ全部の部品に通すと、ステップごとに専門家をほぼ全部読む (Qwen3.6 で 1 ステップ 17 GB、2602 トークンで 190.9 GB)。wave は 1 回だけ読む (14.6 GB)。
  - 段の間でステップごとに持ち越すもの: `decode.Program.Carry(i)` (Qwen3.6 で 1 ステップ 2.6 MB)。wave は持ち越しが 64 MB までのステップ数 (25 ステップ、3200 トークン)。
  - 印 (プロンプトの保存の 512 トークンごと) は wave の中でも取れる。ステップと部品の間で `ctx` を見て、中断した wave は前の印に戻す。
  - ステップのマスクは fp16 のバイトで直接書く (`step.stepMasks`、3 → 0.1 ms)。
  - `TestPagedWave`: 合成モデルで 1 ステップずつとビット単位で同じ。長いプロンプトは丸めが違う (wave は最初から注意のキャッシュを最後の塊の大きさにする)。
- **複数のステップの行をまとめて** (`chain.moe.runMany`、`hostRows` 512、Core AI の先頭オフロード有効時は `prefillHostRows` 2048): 専門家は 1 回の呼び出しで 1 回読む。1 行 1 層: 128 行で 0.139 ms、512 行 0.089、1024 行 0.085。`Host.Run` は (専門家 × 行) 1024 個ずつの組で回すので、持つ量は 1 ステップ分 (12 MB) のまま。
- **Core AI でのプロンプトの Neural Engine オフロード** (`experts.Host.EnablePrefillNPU`、`HWNPU_DEV=moe.prefill=0` で切): 24 行以上 (`moe.prefill-min-rows`) が集まった熱い専門家を、重みを持たない 4 次元バッチ積のプログラム (`G=8, M=64` または大きい専門家は `G=4, M=128`、0.1〜0.2 秒でコンパイル) で Neural Engine に流し、少ない行の冷たい専門家を裏で CPU が同時に回す。MXFP4 は NEON のレジスタ内変換 (`mxfp4.DequantizeF16`、M1 1 コア 40.3 GB/s) で交互の入力配列 (`AllocInput`) に直接 fp16 で開き、1 トークンの生成に入った時点で入力配列を解放する (生成中の追加メモリ 0)。M1 実測 (1 層、CPU 8 コア NEON 対比、コサイン 0.99994): `gpt-oss-20b` 512 行で壁時計 222.4 → **160.1 ms (1.39 倍)**、CPU 時間 1691.6 → **484〜522 ms (3.2〜3.5 分の 1)**。`Qwen3.6` wave 2048 行で壁時計 275.2 → **222.4 ms (1.24 倍)**、CPU 時間 1940.5 → **618〜706 ms (2.8〜3.1 分の 1)**。512 行でも 65.6 → **61.7 ms**、CPU 時間 1.24 分の 1。
- LFM2-8B-A1B とそれ以前: `experts.BuildRows`、`chain.moe.runRows` が選ばれた専門家を呼び出しの全部の行に 1 回ずつ回す。

### Apple の Qwen3.6

- **派生のチェックポイント** (`hwnpu-dev mxfp4`、`qwen35.DeriveMXFP4`): bf16 の専門家 (72 GB のうち 64 GB) は 16 GB にもディスクにも入らない。各層の `gate_up_proj` (256, 1024, 2048) と `down_proj` (256, 2048, 512) を gpt-oss の形の MXFP4 (`*_blocks`、`*_scales`、gate と up の行を交互、gate が偶数行) で書く。専門家 17.1 GB、全体 22.0 GB (視覚の塔と MTP は落とす)。
  - Hugging Face から Range 要求で層ごとに読む (`HTTPSource`、4 本並び): 1 層 45〜70 秒、M3 で 39 分。層ごとのファイルなので続きから書ける。config.json の `hwnpu_mxfp4` は最後に書く。
  - hwnpu-chat (`llm.HostDerived`) は配布物を落とさず、キャッシュの `derived/Qwen/Qwen3.6-35B-A3B` に書く (`chat.DerivedDir`)。`hwnpu-dev convert` は専門家の MXFP4 が無いチェックポイントを、`hwnpu-dev mxfp4` を案内して断る。
  - 取得元のエントリにもなる (`chat.DerivedKind`、`converted/Qwen3.6-35B-A3B/any/Qwen3.6-35B-A3B/`。鍵は配布物のコミットと `derivedVersion`): 機械はそこから取り、自分では作らない。作った機械は書き戻す取得元に置く (`hwnpu-dev models package Qwen3.6-35B-A3B/coreai`、2026-11-22)。AMD は使わない (専門家は IRON の書き出しで NPU)
- **対応しない設定**は `ParseMoE` が断る: `mlp_only_layers`、`decoder_sparse_step` > 1、`norm_topk_prob` false、32 の倍数でない大きさ。
- **Neural Engine が内側の次元 1 の matmul を誤る**: Gated DeltaNet の出力 o = (QKᵀ ⊙ E) U + Γ Q S0 で、塊が 1 行だと `matmul (1×1)·(1×128)` になり、Neural Engine が誤る (値 40〜70 に対して 8 ほど)。1 トークンの生成が同じトークンを繰り返した。塊が 1 行のときは broadcast の mul にする (`deltaRuleChunks`)。密な Qwen3.5 の 1 トークンのプログラムも同じ変更 (Revision 2)。
- **畳み込みの窓の出力** (Revision 2): GDN の窓 `win_conv_N_new` はホストが使う 3 行だけを出す (1 トークンのプログラムは slice、128 トークンのプログラムは入力 `step_window` (1, 3, 131) との matmul。`PagedStepInputs` がステップの有効なトークンから作る)。64 MB 減る。この形はステップの途中までを残せない (下書きの一部だけの採用) ので、そのときは走らせ直す (`wholeWindow`)。密な Qwen3.5 は変えていない。
- 照合: `TestMoEAgainstFP64` (合成モデル、modeling_qwen3_5_moe.py から書いた float64 の参照と相対誤差 2.5e-6。共有のゲートの sigmoid を外す、共有の専門家を足さない、norm の前の値を渡す、を検出する)、`TestMoEPagedSteps`、`TestDeriveMXFP4` (MXFP4 を戻した重みとコサイン 0.99995 以上)、`TestMoEStepWindow`。実物の float32 の参照 `tools/ref/ref_qwen36_moe.py` (層の出力の最大 48.5: fp16 はあふれない)。KL は測っていない。
- 初回の起動: 変換と Core AI のコンパイルで約 10 分 (51 部品、2 つのプログラム)。2 回目からは 0.9 秒で読み込む。
- 16 GB での文脈: 180224 (KV 22 KiB/トークン)。

### Apple の gpt-oss-20b

- 部品: sink つきの注意、YaRN、bias つきの router。部品の間で上のカーネルが専門家を回す。
- 精度 (Neural Engine、float32 の transformers との KL、5 つの文): 注意が lut8 (16 行ごとに 1 つの表) 0.284、`lut8r` 0.069、fp16 0.033。射影の行の大きさは最大 6600 倍違うので、16 行の表では小さい行の段が足りない。`lut8r` は行ごとに最大値 (fp16、1 以下) で割り、bias の前に掛け戻す。出力層の `lut6r` は lut8 に対して平均 KL 約 +0.004、1 ステップ 10.2 → 8.1 ms。答えが最も良いのは `--format-for=self_attn=fp16`。

### Neural Engine の LFM2-8B-A1B

- 部品は MoE の層ごとに、fp16 の経路のロジットと専門家の入力 (`moe_x_N`、`moe_logits_N`) で終わる。ホストが上位 4 個を取り、選んだ専門家に重みを持たないプログラムを回す。int8 の重みは全部の層の専門家を持つそのプログラムの配列にある (7.22 GiB、1 回読み、`Share` するチェーンで共有)。
- 専門家のスケールは int16 の添字の `gather_nd` で引く: M2 と M3 は回り、M1 は回らない (`not_on: [M1]`、`chat` が M1 で断る)。
- `PlanRouted` に `Paged` を付けると注意でも切り (層なしの部品、`NoLayers`)、文脈 128000。
- メモリが足りないと macOS が専門家の配列を圧縮し、プロンプトが最大 3 倍かかる。アプリの `reserve_moe_memory` (`ai.LoadSettings`、hwnpu-chat の `--reserve-moe-memory=8GB` や `50%`) でその量まで固定する。既定は固定しない: 固定した配列は、使っていない間もモデルを読み込んでいる限り固定されたまま。16 GB の M2 の LFM2-8B-A1B (2026-11-27、プロンプト 2352 トークン、生成 300、3 回ずつ交互): なし 17.0〜17.1 s、11.9〜12.8 トークン/秒、4GB 16.5〜16.9 s、12.8〜13.4、全部 (7.23 GiB) 16.1〜16.3 s、12.9〜13.6。ほかのプロセスが 6 GB を使っているとき、なし 19.1〜19.3 s、5.9〜6.3 トークン/秒、全部 17.8〜18.0 s、11.6〜11.7。固定しなくても Neural Engine が実行中の配列 4〜5 GB を固定する (固定のメモリは最大 6.7〜7.1 GB、全部固定で 10.1 GB)。

## AMD: IRON (Ryzen AI 9 365)

NPU が読めるのは固定したバッファ (バンク) だけ。専門家の表の中の位置は呼び出しのときに決まる: コマンドのスクラッチパッドの語 (32 語まで) がシム DMA のアドレスに足される (`Affine`) ので、演算子は選ばれた専門家をコピーせずその場で読む。

### Qwen3.6 のデコード

- 1 層は 2 コマンドで、間に空のホストステップを置く (1 ステップ 81 コマンド):
  - **A**: mixer、残差、post-attention norm、経路の GEMV (256 行と共有のゲートの 1 行)、`MoERoute`。
  - **B**: 専門家。1 つの演算子 `MoEExperts` (gate/up と down を 1 つのプログラムで。gpt-oss の `MX4Experts` と同じ形で、活性は DRAM を回る)。表は経路が選ぶ専門家と、最後の項目として共有の専門家。silu × up × 経路の重みを gate/up の出口で (`moe_glu`)、残差を down の出口で足す。
- **`MoERoute`** (`kernels/moe_route.cc`、1 コア、ベクトル化、0.1 ms): 上位 8 個 (同値は番号の小さい方)、選んだ中の softmax (transformers と同じく bf16)、共有の sigmoid。コマンド B のスクラッチパッドの語 (`番号 × 専門家のバイト数`) を書く。どの語を書くかは、書き出しで IRON の lowering の結果 (`params.txt`、`Qwen35Moe.program_rows`) から埋めた表で決める。
  - 出力は feedback のバッファで、B の ctrl スクラッチパッドにする (manifest の `fed`、`Run.UseScratchpad`)。ホストはロジットを読まない。
  - feedback のバッファはデバイスのヒープ (`BufferInstructions`) に置く: ふつうの BO をスクラッチパッドにすると `ERT_CMD_STATE_ERROR`。コマンドの処理系はデバイスのアドレスで読むが、シムの DMA はプロセスの仮想アドレス (PASID) を使うので、ヒープのバッファの再配置には仮想アドレスを入れる (`buffer.dmaAddr`)。
- **Gated DeltaNet の演算子** (`tools/amd/iron_gdn.py`、`kernels/gdn.cc`): 8 列 × 2 コア、再帰は mlir-aie の `gated_delta_rule.cc` から。短い畳み込み (`gdn_conv`、履歴は状態の列ごとの先頭の組) とゲートつきの norm (`gdn_norm`、y/rms(y)·silu(z) を float32 で、norm の重みは `out_proj` に掛けておく) を演算子の中で。チェックポイントの枠を演算子が直接読み書きする (`gdn_operator(slots=)`)。q と k の silu はキーのヘッドごとに 1 回 (`gdn_gather_conv_v`)。in_proj (8704 行) と z (4096 行) は 1 つの表 (12800 行 = 200 列ブロック、8 列に 25 ずつ)。
- 注意の層: q、k、v、ゲートを 1 つの表 (9216 行) に。q と k の norm を 1 つの状態に書いて RoPE を 1 回に。残差は out_proj / o_proj の GEMV で足す (`into_linear`)。
- **`stepBarrier`**: 各デコードのステップの前に、デコードの ELF の空のインスタンスを別のハードウェアのコンテキストで流す (0.3 ms)。無いと、畳み込みを GDN に入れた形で、最後の層の B の後のコマンド 0 が止まる (`ERT_CMD_STATE_TIMEOUT`)。原因は分からない。同じコンテキストで流しても止まる。
- 書式: 専門家と出力層は q4 (q4nx)、mixer は q8。

### Qwen3.6 のプロンプト (256 トークンの塊)

- スクラッチパッドには 2048 個の位置が入らず、データで決まる番号でトークンを集める DMA もない。そこでプロンプトは:
  - **A**: mixer、残差 h (状態 `moe_h` に写す)、norm した hn、経路のロジット (C × 320)。
  - **ホストの route** (`moe_route`、選び出しの `topK`): トークンごとに上位 8 個、行を専門家ごとに並べ、専門家ごとの行数 (512 語: 256 個の数と埋め草の数)、本物の行だけを書く。
  - **B**: 共有の専門家 (q4 の Linear)、`MoEGroupGateUp`、`MoEGroupDown` (`tools/amd/iron_moep.py`、`kernels/moe_rows.cc`)。重みの流れは静的で、パスごとに全部の専門家の重みが 1 回ずつ流れ、コアはデータから読んだ専門家の行数だけ回る。埋め草の行は最後に置き、読み流して 0 を出す。
  - **ホストの combine** (`moeHostCombine`、トークンごとに CPU に分ける): out = h + 共有のゲート × 共有 + Σ 重み × 専門家の行 (float32 で足して bf16 に 1 回)。
- パスごとの専門家の行の上限 `MOE_CAP` = 256 (= 塊) で、塊は常に 1 パス。gate/up と down を列の 4 コアに配り、各コアは block の半分 (16 出力、q4nx の strip 1 つ) だけを持つ。それで 256 行の累算が 32 KB に入る。
- Go は manifest の `cap` を読むので、古い書き出しも動く。
- 塊が何回かのパスになるときは、後の B の前にホストが hn を書き戻す (`moeRoute.hn`)。IRON の領域の割り当てが B の出力を hn の上に置いていた。
- プロンプトの畳み込み: IRON の `CausalConv1d` と自分の状態。GDN の演算子は組の枠を飛ばす (`pairs=True`)。hwnpu が塊の前後で畳み込みの状態と GDN の組の間の履歴を写す (`internal/llm/iron/convpairs.go`、manifest の `conv_pairs`)。
- ホストの手順は manifest (`host`) に書かれ、Go がコマンドの間に回す (`internal/llm/iron/moe.go`)。

### AMD の gpt-oss-20b

- **mx4 の専門家** (`tools/amd/iron_gptoss_moe.py`、`kernels/moe_mx4.cc`): q8 と同じブロック (出力 32 × 入力 320)、e2m1 の 4 ビット、スケールは MXFP4 の指数のバイトのまま (カーネルで bf16 の指数の欄に入れる)、ブロックの bias。1 重み 4.3 ビット。符号 × max(m, 2m − 4, 4m − 16) で戻す。2880 = 9 × 320 なので入力は埋めない。gate と up の出力は 3072 に埋める。
- **sink** (`tools/amd/iron_sinks.py`、`kernels/mha_sinks.cc`): P×V のコアが最後の割り算の前に、行の和 l に 2^(sink·log2e − m·scale·log2e) を足す。softmax の状態を sink で始める形は誤った: 装置の exp2 は 0 より大きく下で最大 2 倍高い。IRON の MHA の P×V の worker のプログラムだけを差し替える。IRON のコンパイルのキャッシュは演算子の引数で引くので、`sink_form` を引数に足した。
- 残差を 3072 に埋める (norm の重み × sqrt(2880/3072)、eps × 2880/3072)。出力層の行は 201216 に埋め、hwnpu は先頭の 201088 個を読む。注意の射影は q8、出力層は q4 (GPTQ の符号は `--q4-codes` で)、router は bf16、埋め込みはホスト。窓の層は窓の中だけ読む。
- **デコードを常駐の 1 配列に** (`GptOssStep`、`tools/amd/iron_gptoss_layer.py`、`kernels/gptoss_layer.cc`): 層の演算がすべて 1 つの配列の段。1 コマンド = 前の層の専門家 (E) → q/k/v と RMSNorm、bias、RoPE (Q) → 注意 (A) → o_proj と bias と残差 (O) → router (R) → 経路 (T: 次のコマンドのスクラッチパッドの語を書く)。最後のコマンドは [E、出力層 (H)]。1 トークン 25 コマンド、PDI の読み込みは 1 回 (`unexpanded_loads`)、ステップのバリアなし (`no_step_barrier`。`HWNPU_DEV=iron.barrier=1/0` で逆に)。
  - 射影は 5504 バイトの q8x ブロック (mx4 のブロックと同じ大きさ)。プロンプトも同じ q8x の表を戻して使う (`Q8XDequant`) ので表は 1 つ。
  - 出力層は q4 の表をそのまま、5120 バイトずつ進む 5504 バイトの窓として読む。1 行の 2 つの部分和は hwnpu が足す (`logit_parts`)。
  - デコードの KV は 1 つの配列 (`cache.kv`)。hwnpu がプロンプトのキーと値の配列と行き来させる (`joinKV`、`splitKV`)。窓の層は 128 行の輪 (位置 % 128)、巻き戻しの後は `ringsTo` で入れ直す。`TestKVRingRewindOnDevice` で確かめる。
  - 指数関数は 1 つの `gl_exp32` (32 レーン、2^k·p(f)、bf16 の 2 リム) で softmax、glu、経路の重みに。
- **プロンプトの専門家** (`MX4GroupGateUp`、`MX4GroupDown`): 経路はホスト (`moeHostRouteMX4`)。ブロックを直接 bfp16ebs8 に組み (仮数 = 2·e2m1、指数 = E + 5。重みは正確、活性は 8 ビットの仮数に丸まる)、bfp16 の行列命令 `mac_8x8_8x8T` で掛ける。AIE2P の bf16 の `mmul<4,8,8>` は放送 mac の真似。
  - スロット: `SLOTS = 40`、`CAP = 56`。スロット e < 32 は専門家 e の最初の行、残りの 8 は行の多い専門家の続きの行 (位置は呼び出しごとの語、`slot<i>`)。重みの塊は 1 回だけコアに戻してスロットの行で使い回す。入らない塊は 2 パス。
- ホストはロジットを AVX2 で読み (`vecops.BF16ToF32`、`f32.Axpy`)、トップ k は 256 個ずつの塊を飛ばす (`vecops.MinMax`)。

### 専門家の置き場 (`--expert-places P`)

- 書き出しは層ごとにバンクに P 個の置き場と、Qwen3.6 ではその後ろに共有の専門家を持つ。置き場はバンクではゼロで、像のファイルでは穴 (疎なファイル)。全部の専門家の表は `experts.bin` (層ごとに全専門家の gate-up、続けて全専門家の down)。manifest の `experts_pool`。Qwen3.6 の演算子はどれも共有の専門家を番号 256 でなく「表の最後」として読む。
- 読み込み (`PlaceExperts`、hwnpu-chat が `experts.Placement` を渡す): 芯、アプリの統計、番号の順に置き場を埋める。hwnpu-chat が `experts_core` とアプリの統計を渡すのは名前で呼んだときだけ (`chat.LookupFor`)。書き出しのディレクトリで呼ぶと定義が無い。
- **デコード、デバイスの経路** (gpt-oss-20b の全部と置き場 24、Qwen3.6): コマンドを 1 つずつ出して待つ。fed のコマンドの前に、ホストが位置の語を読み戻し、置き場にない選ばれた専門家を最近使われていない置き場 (このトークンで選ばれていないもの、芯は最後) にコピーし、語を置き場の位置に書き直す (`route`、`placeChoices`)。カーネルは変えない。待つ費用は 1 トークン約 1.2 ms (gpt-oss、24 コマンド)。
- 点数: 使うたびに +1、1 トークンごとに × 0.995 (半減は約 140 トークン)。最初は統計の定常の点数を入れる。
- **デコード、ホストの経路** (`--host-route`、`internal/llm/iron/route.go`。gpt-oss の 16 GB の書き出しと 120b): 層のコマンドを注意で終える。ホストが残差 (`yo`) を読み、RMSNorm と router を CPU で (`router.bin`、転置した float32)、上位 4 個と softmax を取り、次のコマンドの位置の語と経路の重み (`moe_rw<l>`) を書く。続けて層 l+1 の上位 4 個を予測し、無いものを l+1 の置き場へ裏で読む (`guessNext`、`expertPool.inflight`)。デバイスの経路に対して (20b): コサインの中央値 0.99998、KL 0.0095。1 ステップ 50.3 → 51.9 ms。
- **プロンプト** (`poolPasses` / Qwen3.6 の `poolRowPasses`、`rowsPass`): 置き場にある専門家を最初のパスに、ない専門家は後のパスで要らない専門家の置き場へそのパスの前にコピーする。`TestPoolRowPasses` で確かめる。
- **コピー**: 4 つの goroutine がページキャッシュの写像から写して clflush (`SyncToDevice`)。`directReads` (専門家のファイルが物理メモリの半分以上。`HWNPU_DEV=iron.moe.direct=0/1`) のときは O_DIRECT で、goroutine ごとの中継のバッファを通して読む (バンクの写像は O_DIRECT を EFAULT で断る)。1 専門家を 8 つに分ける。測った費用: gpt-oss の 1 専門家 (14.3 MB) はページキャッシュから 1.1 ms、O_DIRECT で 2.6 ms (フォールトでは 9.4 ms)。Qwen3.6 の 1 専門家 (1.97 MB) は O_DIRECT で 0.4〜0.7 ms、キャッシュから 0.1〜0.3 ms。
- `HWNPU_DEV=iron.moe.check` は詰めた後と閉じる時に全部の置き場を `experts.bin` と比べる。置き場の書き出しのロジットは全部の書き出しとビット単位で同じ (重みは同じで、置く場所だけが違う)。

## 落とし穴

- **Neural Engine**: `matmul (1×1)·(1×N)` (内側の次元 1) を M3 の Core AI で誤る: broadcast の mul にする。
- **IRON の領域の割り当てはホストの手順の読み出しを使用に数えない**: ホストが読むバッファが後の演算に上書きされうる。ホストが読むのは、ホストの手順の直前の演算の出力か、状態に写したものだけにする。hn の上書き (NaN、後のパスの共有の専門家の破損) と、gpt-oss の hn が 2 層では正しく 24 層で崩れた件の原因。
- **シムのチャネルのタスクキューは 4 段**: チャネルごとに積むのは 3 本まで。続けて 2 回止めると SMU が戻らず (`aie2_smu_init: Access power failed`)、再起動が要った。`MoEExperts` は down の 9 本の流れを先に積んで止まった: `iron_moeprobe.AHEAD` = 2。
- DMA: 1 次元の大きさは 1023 語まで、記述子の繰り返しは 64 回まで、コマンドのスクラッチパッドは 32 語まで。スクラッチパッドの読み込みは runtime sequence の先頭に巻き上げられる (コマンドの途中でデバイスが書いた語は読まれない)。
- 層によって違う値を配列の鍵の引数にすると (gpt-oss の `kvn`)、別の配列になってコマンドごとに読み込み直す (1 層 1.80 → 4.27 ms)。照合は通るので時間を見る。
- コアのプログラムメモリは 16 KB、データメモリもあふれる。読み込むベクトルは 64 バイト境界に。実行時の添字の `vector.extract<8>` は違う値を返す。llvm-aie はある種のループや配置で落ちる。
- `--command-per-step` の書き出しでは Qwen3.6 のプロンプトのロジットが当てにならない (コサイン 0.32)。2 層に切り詰めたチェックポイントは、層 0 のほとんどのトークンが同じ 8 専門家を選び、全体のモデルと違う。
- 書き出しの `--check` は `qwen35moe --q4` で落ちる (ホストの参照の GEMM に q4 の表が渡る)。照合は `ironlm -record` と `iron_qwen35_check.py ref --stream` で。
- モデルの読み込み中に別のプロセスから `hwnpu status` を 0.5 秒ごとに呼んだ直後に、ファームウェアのメールボックスがタイムアウトして SMU が起動しなくなったことがある (原因とは確かめていない)。測るとき、ほかのプロセスが NPU を使うと 1 コマンドずつ待つデコードは大きく遅くなる。
- **M2 の MacBook Air で測る** (しないと設定の差が揺れに埋もれる):
  - ファンのない Air は 1〜2 回続けて回すと `thermal pressure` (`hwnpu status`) が heavy になり、同じ設定が 12.8 → 8.7 トークン/秒に落ちる。毎回 nominal に戻ってから (約 60 秒) さらに 45〜60 秒待つ。
  - `vm_stat` の Pageins を前後で比べる。Safari などのアプリを開いたままだと、生成中もシステム全体で 100〜450 MB/秒読み、1 回 7〜36 GB。
  - 設定は 1 回ずつ交互に回す (3 回ずつ)。1 つの設定を続けて回さない。
  - Core AI のコンパイル済みのキャッシュが消えると、最初の回はコンパイルし直す (約 40 秒)。比べるのは 2 回目から。
- AMD の固定の量は smaps の `/dev/accel/accel0` の写像の大きさ。`hwnpu status` は Linux では resident を出す。
- **Mac**: hwnpu-chat は考え中の文を標準エラーに出す: 標準エラーの「ready」の行から「[prompt」までを比べる。Core AI のキャッシュはプロセスの名前ごとで、名前を変えたテスト用のバイナリはそれぞれ 1.8 GB を足す。`--experts-key off` で測らないとアプリの統計が当たりを偏らせる。

## 採らなかったもの

AMD:
- 専門家を小刻みに入れ替える: gpt-oss の経路記録では、450 トークンごとの更新で当たり 81.8 % (1000 トークンごとに 0.83 GB 読み直す)、16 トークンごとに 8 個で 85.3 % (6.5 GB)、外れるたびで 89.0 % (140 GB)。当たりの増加が小さい一方、読み直しは 3〜8 倍で、既存の先読みがあれば外れの費用も小さい。
- 手元にない専門家を飛ばす、または選ばれにくくする (float32 の参照だけ): gpt-oss の上位 4 個の最下位を落とすと外れは 29 % 減るが、生成した答えの KL は 0.014、wikitext 調の文では 0.095。Qwen3.6 の上位 8 個から 1 個落とすと KL 0.0095。答えが変わり、NPU では未検証。
- 選んだ専門家を作業用の状態に写してから GEMV: バイトを 3 回動かし、`Copy` は最大でも読み 26 GB/s。呼び出しごとの位置でその場で読む形に替えた。
- down を「1 列 = 1 専門家」に: 和に加算 7 回が要り、`MoEDown` の 1.7 倍。転置した down を 1 行の GEMM で: GEMV より遅い。
- gpt-oss の専門家を q4nx に丸め直す: 重みの誤差 6.6 %、KL 2〜3 倍。mx4 のまま。
- gpt-oss の注意を q6 に: KL 2〜3 倍 (CPU)。gpt-oss を全部 GPTQ に: wiki-ja が悪くなる (0.027 → 0.066)。GPTQ の符号は出力層だけ。
- プロンプトの GEMM を本物の行だけで: `valid` は 256 行単位で速くならず、行ごとの GEMV は遅い。
- Qwen3.6 のプロンプトの専門家を前もって戻しておく (bfp16): 固定のメモリが増える。
- Qwen3.6 のプロンプトの gate/up を bf16 の `mmul` 8×8×4 で: 速くならない (`filter_even` / `filter_odd` での符号の並べ替えが 1 呼び出し約 29 万サイクル、行ごとのスケールと最小値で差が消える)。
- Qwen3.6 の B と次の層の A を 1 コマンドに (81 → 41 コマンド): 17.6 → 17.6 ms。
- GDN の状態の物を二重に: データメモリがあふれる。入力だけ二重でも効かない。
- gpt-oss を 1 トークン 1 コマンドに: デバイスが書いたスクラッチパッドの語はコマンドの中で読み直されない (コサイン 0.877)。`ERT_CMD_CHAIN`: 同じかやや遅い (19.3〜19.6 対 19.6〜19.7 トークン/秒)。
- gpt-oss: 専門家のコアのプログラムを小さく (IRON が ObjectFifo の深さで展開する)、KV への書き込みを GEMV / RoPE / `QGEMVQKV` から直接 (切り替えが 1 回増える)、norm の重みを表に畳む (q8 の誤差で最上位が変わる)、glu を tanh で (PDI が 6 KB 減るだけで bf16 の精度)、router の GEMV を `MoERoute` に (切り替えと同じくらいかかる)、`MX4Experts` を列 2 コアに (計算で 2.39 ms)、x を memtile に 1 回置く (`repeat_count`) や出力を 8 行の物に (効かない)、注意のスコアを bfp16 に (誤差 3.6 %)、bf16 だけの指数関数 (経路の重みが 1.3 % ずれる)、キャッシュを続けて読む形 (止まった)。
- 置き場 32 の Qwen3.6 に芯を置く: コピーが 34.4 → 36.7 % に増えた。置き場の半分を超える芯は外し、models.yaml の Qwen3.6 の芯は Mac 用。
- **gpt-oss-120b を models.yaml に**: NPU に 32 GiB を固定し、SSD の帯域で約 10 トークン/秒に留まる。このサイズは GPU 向き。80 TOPS を超える NPU とメモリが安くなってから考える。書き出しは `iron_export_lm.py gptoss CKPT OUT --max-seq-len 8192 --prefill-chunk 256 --expert-places 56`。
- `not_on` に NPU の会社を書く仕組み: 取り込んでいない (catalog とぶつかる)。Qwen3.6 が Apple でも動くので要らなくなった。

Apple:
- 経路の `gather` を Neural Engine で、Intel の形: どちらの NPU も回せない。
- Core AI の MX の型: GPU だけ (M3〜M5)。Neural Engine で MXFP4 を正確に引くと 1 専門家 49 ms。なので専門家は CPU。
- MoE のモデルの下書き: 専門家は行ごとに回るので、7 個の下書きは 8 行分の専門家 (LFM2-8B-A1B で 2.3 対 14.1 トークン/秒)。キャッシュの tier: tier ごとに専門家を全部持つ書き出しになる。
- メモリの 3/4 を超える専門家の固定 (16 GB の Qwen3.6): どの予算でも遅い。
- Qwen3.6 で 16 個の先読み (7.3 トークン/秒、外れが SSD の読みを食う)、gpt-oss で 8 個 (4 個より速くない、メモリが苦しいと遅い)、2 層前からの予測 (上位 4 個に 80〜85 %、読む量が増える)。
- 働き手を回し続ける (`mxfp4.Hold`、spinners): 0.55 → 1.0 ms で、Neural Engine の部品も同じだけ遅くなる。スレッドの QoS `USER_INTERACTIVE`: 効かない。
- SMMLA の閾値 (6 以外): 差なし。2 行 × 4 ベクトルの SMMLA: SDOT より遅い。
- 固定した専門家のほかの入れ替え方式: どれも平均の当たり 72〜74 %。
- gpt-oss の注意: ただの lut8 (KL 0.284)、int8 (Neural Engine で遅い)。`lut8r` の注意と lut6 の出力層の GPTQ の符号は既定にしない (どの文でも良くはならず、符号は配らない)。
- 生成で芯の専門家を定数の `lut4` で Neural Engine に常駐させ、外れだけ CPU と並べて回す (M1): 続けて呼べば CPU 時間は 1.18〜1.34 分の 1 になるが、部品の 1.2 ms の間が入ると Core AI の呼び出しの立ち上がりで壁時計が `gpt-oss` 1.52 → 3.79〜7.05 ms、`Qwen3.6` 0.33 → 2.66〜3.39 ms (CPU 時間も悪化) になり、コサインも 0.9916〜0.9934 に下がり、1.4〜1.9 GB の wired メモリと層ごとのプログラム数を食う。生成は CPU のままにする。
- プロンプトの専門家を Accelerate の `cblas_sgemm` (AMX) で回す (M1): 単一スレッド AMX で `gpt-oss` 512 行 596.7 ms (CPU 時間 600.4 ms) となり、上の Neural Engine オフロード (160.1 ms、CPU 時間 484〜522 ms) に速さでも CPU 時間でも劣る。
- 経路の下位の専門家を比率で切る (`HWNPU_DEV=moe.min-ratio=R`): 固定で 1 個落とすより KL は大幅に小さい (`R=0.12` で平均 KL 0.00077 対 0.034 / 0.0022、削減 6.6〜7.3 %) が、出力が変わるため既定では切らない。
