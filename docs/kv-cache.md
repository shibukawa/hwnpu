# KV キャッシュの省メモリ化と高速化: 手法の調査と Neural Engine への当てはめ

作成: 2026-10-29。対象は hwnpu の生成 (`cmd/hwnpu-generate`、`internal/llm/decode`) と LFM3-1.7B。実測は M3 (16 GB、macOS 27.0.1)。

## 1. 前提: 今の方式と、何が高いか

hwnpu の KV キャッシュは、ホストのバッファをプログラムの入出力として渡す (design.md 16.14)。Core ML の状態 (MLState) に置く方式も作って比べたが、速さは同じで CPU の使用率が下がるだけだった (16.15)。

| 項目 | 値 (LFM3-1.7B、lut4、2 分割) |
|---|---|
| 1 トークンあたりの KV | 注意層 1 層 2 KiB (4 ヘッド × 128 × K と V × fp16)、11 層で 22 KiB。8K で 176 MiB、256K で 5.5 GiB |
| 1 トークンの費用 | キャッシュの**容量** (使った量ではない) 1K トークンにつき約 5.4 ms。容量 256 で 16.8 ms、1K で 20.6 ms、4K で 37.6 ms。直線で延ばすと 32K で約 190 ms、256K で約 1.4 秒 (推定) |
| LFM3 の注意層 | 24 層のうち 11 層。6 層が全注意、5 層がスライディング注意 (窓 256)。残り 13 層は短い畳み込みで、状態は直前 6 行だけ |
| 文脈の上限 | モデルは 262144 (`max_position_embeddings`)。今の実装ではキャッシュの容量が入出力の合計の上限で、ANE に載るのは 16383 まで (1 次元の上限 16384) |

Neural Engine (Core ML) 側の制約で、手法の実現性が決まる。

- 形は固定。実行時に長さを変えられないので、「使った分だけ計算する」が素直にはできない。
- 動的な索引 (`gather`、`slice_update`、データ依存の分岐) は CPU に置かれる。キャッシュの行の選択や並べ替えはホストでやるか、one-hot の積で書く。
- 状態 (MLState) に書いた値は読み直してから使う。そのまま使うとコンパイルが `error code -14` で失敗する。
- 行列積の形には未解明の制約がある。GQA の K/V を `tile` で複製せずに (kv ヘッド, グループ) の行列でまとめて読む形は、同じ計算なのに全演算が CPU に置かれた (16.15)。
- **1 次元の長さは 16384 まで**。鍵の軸が 16385 以上になる注意は CPU に置かれる (16.16)。今の方式では、全注意の層のキャッシュは 16383 トークン (Q=1) が上限。これより長い文脈には塊分け (4 節 b) が要る。塊を別々の入力にして 1 つのプログラムの中で合わせる形は、64K まで全部 ANE に載ることを確かめた (16.21)。

## 2. 手法の一覧と評価

「何を減らすか」は、メモリ (キャッシュの大きさ)、容量の費用 (1 トークンあたりの計算で、今の実装では容量に比例する部分)、帯域 (読み出す量) の 3 つで見る。「学習」は、モデルの学習し直しや追加の学習が要るか。

| 手法 | 何を減らすか | 学習 | Neural Engine での実現性 | LFM3 への当てはめ |
|---|---|---|---|---|
| **GQA** (複数の Q ヘッドで K/V のグループを共有) | メモリ、帯域 | 要 (設計) | 動いている | LFM3 は 16 Q / 4 KV ヘッドで既に GQA。やることはない。ただし今の実装は K/V を `tile` で 16 ヘッド分に複製して注意を計算しており、その費用は 3 節で測る |
| **MQA** (全 Q ヘッドで 1 組の K/V) | メモリ、帯域 (GQA の 4 分の 1) | 要 | GQA と同じ | モデルの構造なので変えられない |
| **MLA** (K/V を低次元の潜在ベクトルに圧縮して保存。DeepSeek) | メモリ、帯域 | 要。GQA からの変換は TransMLA で後から可能だが追加学習が要る | 潜在ベクトルに対する行列積は普通の `matmul`。「吸収」(absorb) で復元せずに済むので ANE 向きの形になる見込み | 追加学習の仕組みが要り、Go の変換器の範囲外。将来の候補 |
| **KV 量子化** (KIVI: K は列ごと、V はトークンごとに 2 ビット。KVQuant: RoPE 前の K を列ごと、非一様、外れ値を分けて 3 ビットで perplexity 劣化 0.1 未満) | メモリ、帯域 | 不要 | **測った** (3 節): int8 の入力 (仕様の版 10、macOS 26 以降) をトークンごとの fp16 のスケールで戻す形は全演算 ANE に載る。メモリは半分、速さは fp16 より 1 割遅い (`cast` と `mul` が容量全体にかかる)。ANE の費用は帯域ではなく容量に対する計算なので、速くはならない | メモリだけが減る。LFM3 の fp16 のキャッシュは 8K で 176 MiB、256K で 5.5 GiB。100K 超を塊分け (4 節 b) と組み合わせて目指すときに使う |
| **スライディング窓** (直近 W トークンだけ見る層のキャッシュを W に固定する。llama.cpp の iSWA は SWA 層だけ別の小さなキャッシュを持つ) | メモリ、容量の費用 | 不要 (モデルが既にそう) | リングバッファ: ホストが `pos mod W` の行に書き、マスクで有効な行を示す。K には RoPE を掛けてから保存するので、行の順番は結果に効かない (softmax は鍵の順に依らない) | **実装済み** (design.md 16.16)。11 層のうち 5 層が窓 256 なので、長い容量が要るのは 6 層。容量 1K あたりの費用が 5.5 ms から 2.8 ms に下がり、4K で 27.7 ms (−26%)、8K で 38.5 ms。出力はリングなしと同一 |
| **退避・圧縮** (StreamingLLM: 先頭の数トークン (attention sink) と直近の窓を残す。H2O: 注意の累積が大きいトークンを残す。SnapKV: プロンプトの末尾の窓から見て重要な位置だけ残す) | メモリ、容量の費用 (容量を小さく固定できる) | 不要 | 残す行の選択はホストが行い、マスクで示す。ANE 側は何も変わらない。SnapKV に要る注意の重みは、プログラムの出力に足せば取れる | 固定の容量 (たとえば 4K) で終わりのない生成をするのに使える。精度の取引があるので選べる設定にする。StreamingLLM の「先頭を残す」は実装が簡単 |
| **PagedAttention** (キャッシュをページ単位で管理し、断片化と予約の無駄を減らす。vLLM) | メモリ (複数の系列を同時に扱うとき) | 不要 | ページ表による間接参照は `gather` で CPU 行き。形も固定にならない | 系列が 1 つで、バッファを事前に確保する今の方式では利点がない。「容量の段階」(後述) が粗い粒度で同じ役割をする |
| **FlashAttention / Flash-Decoding** (注意の計算を塊に分けて中間データの読み書きを減らす。Flash-Decoding は鍵の軸を塊に分けて並列に計算し、softmax の部分和 (log-sum-exp) で合流する) | 帯域、長い文脈の遅延 | 不要 | カーネルは Core ML のコンパイラが決めるので、hwnpu からは触れない。ただし Flash-Decoding の「鍵の軸を固定の塊に分けて部分和で合流する」形はプログラムの単位で再現でき、**使っている塊だけを動かせば費用が容量ではなく長さに比例する** | 容量の費用を減らす本命の 1 つ。塊ごとのプログラムが要るので Core ML の呼び出しが増える (1 回約 55 µs)。設計は 4 節 |
| **層をまたぐ共有** (CLA: 隣の層で K/V を共有。YOCO: 前半の層が作った K/V を後半が cross-attention で使う。Apple の on-device モデルは後半 37.5% の層の K/V 射影を外して前半のを使い、キャッシュを 37.5% 減らした) | メモリ、容量の費用 | 要 | 動くはず (共有先の入力を同じバッファに Bind するだけ) | モデルの構造なので変えられない。Apple が自社モデルでこれを選んでいることは、ANE では容量が高いという今回の観測と合う |
| **プロンプトのキャッシュ** (システムプロンプトなど共通の前置きの K/V を保存して再利用) | 読み込みの時間 | 不要 | ホストのバッファそのものを保存すればよい | 実装が最も簡単。チャットの往復で system プロンプトの prefill を省ける |
| **容量の段階** (1K、4K、8K の容量のプログラムを用意し、文脈が伸びたら大きいほうへキャッシュを移す) | 容量の費用 (短いうちは速い) | 不要 | **実装済み** (`hwnpu-convert -cache a,b,c`、`chain.Grow`、`decode.Session.Migrate`)。キャッシュの移し替えはホストのバッファのコピーで 0 秒。段階の読み込みは 6〜30 秒 (配置の検証をキャッシュして半分にした) で、裏で読み込むと生成が半分以下に落ちるので先に全部読み込む | 動いている段階は単独と同じ速さ (1024 で 19.2 ms)。重みは段階ごとに重複 (0.8 GiB ずつ) |
| **重みなしの注意プログラム** (層を「射影と MLP (重みあり、容量に依らない)」と「キャッシュに対する注意 (重みなし、容量ごと)」に分ける) | 容量の段階の重複 | 不要 | 分けた分だけ Core ML の呼び出しが増える (11 層 × 2〜3 回 × 55 µs ≈ 1〜2 ms)。重みなしのプログラムはコンパイルも読み込みも速いはず (未確認) | 容量の段階や塊分けと組み合わせる土台。未検証 |

## 3. 容量に比例する費用の内訳

費用がどこから来るかを `npuprobe kv` で切り分けた (M3、11 層 lut4、1 トークン、全部 ANE。レポートは `npuprobe-m3-kv.md` と `npuprobe-m3-kv-mha.md`)。

| 容量 | host (GQA、K/V を tile で 16 ヘッドに複製) | state (MLState) | host-mha (16 の Q ヘッドがそれぞれ K/V を持つ。複製なし、キャッシュ 4 倍) | host-int8 (キャッシュを int8 とトークンごとの fp16 スケールで渡し、`cast` と `mul` で戻す) |
|---|---|---|---|---|
| 1024 | 10.7 ms (KV 22 MiB) | 10.0 ms | 14.2 ms (KV 88 MiB) | 11.9 ms (11 MiB) |
| 4096 | 28.4 ms (88 MiB) | 26.8 ms | 36.6 ms (352 MiB) | 29.5 ms (45 MiB) |
| 8192 | 49.8 ms (176 MiB) | 49.3 ms | 63.5 ms (704 MiB) | 50.8 ms (89 MiB) |
| 1K あたりの傾き | 5.6 ms | 5.6 ms | 7.0 ms | 5.6 ms |

host の値は実行ごとに 46〜55 ms (8K) の幅で揺れる。int8 は同じ実行の host (10.8 / 27.6 / 46.5 ms) と比べて 1.1 / 1.9 / 4.3 ms 遅く、傾きは同じ (`npuprobe-m3-kv-int8.md`)。

- **入力のコピーではない**: MLState にしても速さは同じ (16.15)。
- **帯域でもない**: キャッシュのバイト数を 4 倍にしても (host-mha) 費用は 1.3 倍。8K で 704 MiB を読んで 63.5 ms なので、読み出しは少なくとも 11 GB/s は出ており、ANE の帯域 (重みで 65 GB/s) の壁には当たっていない。
- **`tile` による複製でもない**: 複製をなくした host-mha が速くならない。
- **量子化しても速くならない**: int8 のキャッシュ (host-int8) は全演算 ANE に載りメモリは半分だが、`cast` と `mul` が容量全体にかかる分だけ 1 割遅い。重みの lut4 が速いのは読むバイト数が減るからで、表引き形式は定数にしか使えず、キャッシュの費用はそもそも読み出しではない。
- 残るのは **容量全体に対する注意の計算そのもの**: 層ごとに 16 ヘッド × 容量 × 128 の内積を 2 回 (QK と PV)、問い合わせは 1 行。1K トークンで 1 層あたり約 4 MFLOP、0.5 ms なので約 8 GFLOP/s しか出ていない。ANE は行列同士の積は速いが、問い合わせが 1 行の行列ベクトル積は使い切れない (MODEL.md の「バッチ 1、幅 4096 までの全結合は CPU に置かれる」観測と同じ性質)。

結論: 容量の費用を減らすには、(a) 計算する容量を小さくする (リングバッファ、退避、容量の段階)、(b) 使っている塊だけ計算する (Flash-Decoding の形)、(c) 行列積の形を変えて ANE の効率を上げる (問い合わせの行を増やす: 投機的デコードの K 個の下書きや、GQA の 4 ヘッドを行にまとめる形。後者は今のところ CPU に落ちる (16.15))、の 3 方向になる。帯域やメモリを減らす手法 (量子化、MLA) は、ANE では速さに効かない。

## 4. 容量の費用を減らす設計 (案)

今の費用は「固定の容量のキャッシュ全体に対する ANE の計算」なので、減らすには (a) 容量そのものを小さくする、(b) 容量のうち使っている部分だけを計算する、の 2 通りがある。

**(a) 容量を小さくする**

1. スライディング注意の層 (5 層) を窓 256 のリングバッファにする。`llm.Cached` の約束に「層ごとに容量が違ってよい」を足し、`decode.Session` が層ごとに書き込み位置 (`pos mod W`) とマスクを作る。全注意の層 (6 層) だけが長い容量を持つ。
2. 退避 (StreamingLLM 型) を選べる設定にし、全注意の層の容量も上限を付けられるようにする。
3. 容量の段階を用意し、短いうちは小さい容量で動かす。キャッシュの移し替えはバッファのコピーで済む。

**(b) 使っている部分だけ計算する (Flash-Decoding の形)**

キャッシュを固定長 B (たとえば 1024) の塊に分け、塊 j に対する注意を「スコアの最大値 m_j、softmax の分母 l_j、分子 o_j」の 3 つを返す重みなしのプログラムにする。合流は m = max(m_j)、o = Σ o_j·exp(m_j − m)、l = Σ l_j·exp(m_j − m) で、これはホストで行える (1 トークンあたり 16 ヘッド × 128 の小さな計算)。塊のプログラムは 1 つをコンパイルして全部の塊に使い回せ、使っている塊だけを呼ぶので、費用は容量ではなく長さに比例する。

費用の見積もり: 11 層 × (使っている塊の数 + 2) 回の Core ML の呼び出し。8K の文脈 (8 塊) で 11 × 10 × 55 µs ≈ 6 ms の固定費が乗るので、今の 8K (約 60 ms の見込み) よりは速く、1K では今より遅い。塊の大きさで折り合いを決める。先に (a) をやり、その後で (b) を試す。

## 5. LFM3 での進め方

| 順 | 手法 | 見込み | 費用 |
|---|---|---|---|
| 1 | スライディング層のリングバッファ | **済**: 容量 1K あたり 5.5 → 2.8 ms、8K で 38.5 ms/token | 2026-10-30、design.md 16.16 |
| 2 | 容量の段階と移し替え | **実装済み** (design.md 16.20): `-cache 1024,4096,8192`、切り替えは 0 秒で出力は同一。端から端の利得はスワップのある機械では示せず、空いた機械で測り直す | 段階の読み込みは 6〜30 秒。裏で読み込むと生成が半分以下になるので、既定は先に全部読み込む |
| 3 | プロンプトのキャッシュ | チャットの 2 回目以降の prefill がなくなる | バッファの保存と復元だけ |
| 4 | StreamingLLM 型の退避 (設定) | 固定の容量で終わりのない生成 | マスクと書き込み位置の規則 |
| 5 | 塊分けの注意 (Flash-Decoding の形) | 16K を超える文脈。使っている塊だけ動かせば費用が長さに比例 | 実装済み (16.22): 16320 を超えるキャッシュは 16384 ずつの塊。LFM3-1.7B で 32K 138 ms/token、64K 363 ms/token、全部 ANE。使っている塊だけ動かす形は未着手 |
| 6 | KV の int8 | メモリが半分 (計測済み: ANE に載り、1 割遅い) | `decode` でホスト側の量子化 (KIVI の K は列ごと、V はトークンごと)。100K 超を塊分けと一緒に目指すときだけ |

学習し直しが要るもの (MQA、MLA、層をまたぐ共有) は、LFM3 では使えない。ただし新しいモデルを選ぶときの基準にはなる: Apple の on-device モデルのように層をまたぐ共有を持つモデルや、MLA のモデルは、ANE では容量の費用が小さくて済む。
