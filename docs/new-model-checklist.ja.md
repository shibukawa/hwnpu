## 方針: 速さより消費電力

hwnpu の目的は、NPU だけで動かして消費電力を下げること。手法を選ぶときは次の順に考える。

- **合計の時間が同じなら、NPU に載せる**。CPU や GPU に移して少し速くなる形 (短い文脈の注意を CPU で計算するなど) は採らない。GPU は使わない
- **読む重みのバイトを減らす**。1 トークンの電力の大半は重みの読み出しで、読む量を減らせば速さと電力の両方に効く (ビット数、プロンプト用のプログラムに要らない層を持たせない、MoE)
- **NPU の上での無駄を減らす**。読み込んだプログラムが NPU のメモリに収まらず載せ直しが起きる形、1 つの演算だけ CPU に落ちて NPU と CPU を往復する形は、速さが同じでも電力を使う
- 電力は `hwnpu-dev powerbench` で 1 トークンあたりの mJ を測る (Mac は sudo が要る)。測れないときは、読む重みのバイト、NPU が抱えるメモリ (`mem.NPUWired`)、CPU の使用率で代わりに比べる

数値の出典は [design.md](design.md) の 16 章 (カッコ内の番号)、[improvements.md](improvements.md)、[model-fit.md](model-fit.md)、[amd-npu-models.md](amd-npu-models.md)。構造を Go に移す作業そのものの手順と合格条件は `.claude/skills/port-architecture` にあるので、ここでは繰り返さない。

## 1. 机上の見積もり (移植する前に)

[model-fit.md](model-fit.md) の 2 節と 4 節の式と基準で、config.json だけから見積もる。

- **1 トークンの時間 (ANE)** ≈ 重みのバイト ÷ 65 GB/s + 長い容量に対して注意を計算する層の数 × 0.22 ms (`SDPAGrouped` の形) × 容量 / 1K + 3 ms
  - KV の共有は注意の計算の回数を減らさない (メモリだけ)。窓、短い畳み込み、Mamba2、GDN の層は容量に依らない
- **1 トークンの時間 (AMD)**: 生成は重みのバイトではなく演算の数で決まる (Qwen3.5-0.8B は bf16、q4、q6 とも 82〜86 ms、PLaMo 3 2B の q4 は 85 ms、Qwen3.6-35B-A3B の 40 層は 172 ms で、重みを読むだけなら約 33 ms)。層の数と、入れ済みのモデルの時間から見積もる (16.104、16.107、16.92)
- **重み**: lut4 0.5 B、lut6 0.75 B、lut8 1 B / 重み。M3 (16 GB) で常駐は 3 GiB までが目安。AMD は 4 ビット (q4nx 5 ビット + 注意 q8) で bf16 の 1/2〜1/5 の固定。M1 (16 GB) では、順に回す部分の重みのうち Neural Engine が抱える合計を 2.9 GiB 未満に: 超えると 1 回ごとに約 12 倍遅い (Qwen3.5-4B の lut6 は 2.97 GiB で 1.1 tok/s、lut4 は 1.99 GiB で 10.9。M2 と M4 は 3.62 GiB でも全速、16.109)
- **語彙**: 出力層は語彙 × 隠れ。linear は 262144 の軸でも ANE に載るが、その後の要素ごとの演算は CPU に落ちる。単調な演算 (ソフトキャップ) はホストに回す (Gemma 4、16.113)
- **使えない構造**: MoE のルーティング (`gather`)、学習済みの疎な注意、可変の形。MoE は AMD で動く (Qwen3.6-35B-A3B: 生成では経路の選択をデバイスで、プロンプトではホストで、16.89〜16.93、16.110)
- **チェックポイントが持つ下書き用の層** (Qwen3.5 の `mtp.`): 変換で捨てない。下書きにするとプロンプトからの推測より当たる (M1 の Qwen3.5-0.8B でコード 26.1 → 43.8 tok/s、16.109)
- **ライセンスと言語** (hwnpu-chat の目録に載せるか)

**合格**: 1K で 50 ms 以下、16K で 100 ms 以下の見込み。M3 で常駐 3 GiB 以内に入る形式がある。

## 2. 構造の正しさ (CPU)

`port-architecture` スキルの合格条件 (fp64 の参照と 1e-4、1 層ずつとまとめての一致、壊して検出、`hwnpu-dev check` の層ごとの照合) に加え、今までに後から見つかったもの:

| 確かめること | 道具 | 教訓 |
|---|---|---|
| 落としたチェックポイントが壊れていない | HF のファイルの `x-linked-etag` と `sha256sum` を比べる | ここでは大きな落としものにまばらなビットの反転があった (LFM3-Audio と Omni でそれぞれ 10 か所ほど、2〜6 バイト)。乱数の重みの照合や値の範囲では見えない。壊れた部分を取り直す (16.67) |
| **BOS を付けて**比べる | `tools/ref/ref_logits.py`、`hwnpu-dev check`、`ironlm -forced -bos` | LFM3 は BOS なしだと KL が 4 倍に見え、0 層目の活性が外れ値になる (amd-npu-models.md 13 節)。チャットの型で実際に付くトークンで測る |
| 実物の重みで照合する | `hwnpu-dev check`、`iron_plamo3_check.py`、AMD は `ironlm -forced` + `tools/ref/forced_logits.py` | 乱数の重みでは NPU と CPU の参照が食い違う (Gemma 4、PLaMo 3)。乱数の重みはロジットが平らで、bf16 の丸めと bfp16 の GEMM の差が層ごとに広がるため (16.107)。合否は実物の重みで |
| **大きさごとに**実物の重みで照合する | `hwnpu-dev check` | 同じ構造でも、大きさで config の通る道が変わる (Qwen3.5-0.8B は値のヘッドと鍵のヘッドが同じ数)。Qwen3.5-4B は 16.108 まで実物の重みで照合していなかった。目録に載せる大きさはどれも照合する |
| トークナイザーが HF と一致する | `tools/ref/tokenizer_golden.py` | 固定の文 + 数千の乱数の文で 0 件の食い違い。同点の扱い (PLaMo)、NFC と結合文字 (Qwen3.5)、byte fallback (Gemma 4) を逆にしたらテストが落ちることも確かめる |
| チャットの型が jinja2 と一字一句同じ | `tools/ref/template_golden.py` | 道具の呼び出し、考える部分の扱い、過去の考えの削除 |
| チャットの型の既定が大きさで違わないか | テンプレートと model card | Qwen3.5 は 0.8B / 2B が既定で考えず、4B は考える。小さいモデルに考えさせると予算まで回り続けたので、目録の `NoThink` で既定を合わせた (-think を書けば上書き) |
| 多モーダルの前処理 | `resize_golden.py`、`mel_golden.py`、`whisper_mel_golden.py` | PIL との ±1、librosa との 1e-4 |
| エンコーダ・デコーダ (音声) | `tools/ref/ref_whisper.py`、`hwnpu-dev check` (mel を `REF.x.bin` で入力) | エンコーダ、交差注意の K/V、デコーダを別々に照合する。30 秒を超える音声は窓の切り方まで HF に従う (クリップ全体で特徴を作り、タイムスタンプで次の窓へ進む)。30 秒で機械的に切ると、HF でも文が抜ける |
| 埋め込みモデル | `embed_golden.py` | HF との cosine 0.997 以上 |
| 画像生成 | `tools/ref/ref_anima.py`、`tools/ref/compare_image.py` | diffusers の fp32 と潜在の cosine、VAE の PSNR。float32 で 16 GB の Mac のメモリを超えるモデル (Qwen-Image-2.1 の 20B の DiT、8B の文の符号器) は、繰り返しの層の重みを各層の直前に読んで後で捨てて回す (`tools/ref/stream_weights.py`、`ref_qwenimage21.py --stream`): 512² の 1 枚 約 5 分、1024² は 30 分以上 (16.165) |
| **参照のパイプラインのマスクの掛け方** | `tools/ref/ref_chroma.py --mask keys` | diffusers の ChromaPipeline は文のマスクを float の 0/1 で渡し、SDPA はそれを点数に足すので、パディングが隠れない (Chroma は隠して学習された)。NPU の正しいマスクのほうが外れて見えた (最初の速度 0.9886)。参照でキーを隠すと 0.99985。差し替えは狙った所だけに: 同じ SDPA の差し替えを T5 より前に入れると、T5 の相対位置のバイアスのマスクまで変わった (Chroma1-HD 0.71)。NPU を疑う前に、参照のマスクの掛け方を読む (16.156、16.157) |
| float32 で Mac のメモリに入らない画像のモデル | `tools/ref/ref_chroma_lean.py` | Chroma の DiT は float32 で 36 GB、T5-XXL は 19 GB。diffusers のブロックをメタデバイスで作り、重みを shard から 1 ブロックずつ入れる (`load_state_dict(assign=True)`)。16 GB の M1 で 512² の DiT 1 回 98 秒。`--stats` でブロックごとの最大値 (fp16 の範囲)、`--dump --dump-call N` で N 回目の各ブロックの入力 (16.170) |
| Go の型なし定数 | 縮尺の式を読む | `T5FFScale/T5Scale` が型なしの整数どうしで `1/64 = 0` になり、T5 の FF が CPU でも消えていた。`float32(a)/b` と書く (16.170) |

## 3. Mac の Neural Engine に収まるか

**最初に確かめる**: Mac がないと何も決まらない項目。引き継ぎの文書 (`docs/handoff-*.md`) を書いて Mac で測る。

### 3.1 上限

| 上限 | 対処 | 節 |
|---|---|---|
| 1 パッケージ 1 GiB (1 部分の既定は 0.9 GiB) | 層で分ける (別のパッケージ。multifunction では越えられない) | 16.12–13 |
| 1 次元 16384 | 注意で分けた塊 (`-paged`)、ソフトキャップを (16, 16384) に畳む | 16.21, 16.25 |
| コンパイルのキャッシュ約 4 GiB (LRU)。**実効は約 3.5 GiB** | 2 本 (Q=8 と Q=64) の合計が超えるなら 1 本 (`-prefill auto`、境は 3.5 GiB)。Qwen3.5-2B の 3.56 GiB の 2 本は、起動のたびに 4〜5 分コンパイルし直しになった。段階 (`-tier`) は lut4 だけ | 16.41, 16.65, 16.71, 16.99 |
| 表は 16 行ごと | 形式の選び方は 5 節。行が 16 で割り切れない出力層 (Whisper の語彙 51866) は 0 の行で詰めて後で切る (`blocks.LinearPadded`)。詰めないと lut の変換が落ちる | 16.100 |

### 3.2 全部が NPU に載るか

`hwnpu-dev info -model PART.mlpackage` で各部分が `all on the NPU` か。今までに CPU に落ちたもの:

- `tile` で K/V を写す注意の形、問い合わせを行列にした形 → `SDPAGrouped` (16.25, 16.39)。順番だけで配置が変わる
- 最後の部分の `transpose` / `reshape` → 出力をトークン先に取る (`attn_ot_N`、PLaMo 3)。出力層の後の要素ごとの演算 (Gemma 4 のソフトキャップ) は、ホストのサンプリングで上位の値だけに掛ける (`-logits host`、`llm.LogitSoftcap`、16.113)
- 1 行の部品、単独のプログラムの部品 → 8 行にする、隣の群に入れる (Anima、16.85)
- `reduce_sum` → 行列積で和を取る (塊の注意、30 回中 30 回 ANE)
- 1 つの軸が 16384 を超えるテンソルを読む演算はどれも CPU。出力 y の identity も。PP-OCR の 18710 クラスで softmax、bias の add、y が CPU になった。softmax の手前の logit を出し、bias は linear に入れ、幅の大きな出力の linear は分けて (…, 分けた数, n / 分けた数) に積む。並びは同じ (`internal/onnx`、16.149)
- 4096 チャネルを超える深さ方向の畳み込み (Sana の GLUMBConv の 2 × 2880、5600) → 4096 以下に分ける (`maxDepthwise`、16.145)
- グループつきの int8 (`int8-g32`) は linear が CPU。行ごとの int8 にする (Sana の Gemma 2、16.145)

### 3.3 fp16 であふれないか

`hwnpu-dev check -f16` で層ごとの相対 RMS が 0.01 未満か。ただし 1 層ずつが通っても全体では崩れることがある (Whisper は 1 層ずつ 0.0003 以下、全体ではコサイン 0.9978)。次も見る:

- 全体の `-f16` と、**位置ごと**のコサイン。音声やプロンプトの位置と、詰め物の位置を分けて数える
- 外れて大きい活性 (massive activation、注意の吸い込み先) がどの層で生まれるか。HF の隠れ状態 (`REF.hidden.bin`) の層ごとの最大で探す (Whisper は層 21 から無音の位置に 300)
- **原因を追う前に、HF を fp16 で動かした値と比べる**。同じだけずれるなら移植の誤りではない (Whisper: HF の fp16 も 0.9978)
- ANE と Core ML の CPU で、層の数を変えたプログラム (`hwnpu-dev convert -layers N`) を HF の各層と比べると、ずれの始まる層がわかる (`internal/transcribe` の `TestEncoderOnDevice`)。Whisper は層 20 まで 0.9996 以上で、層 21 で無音の位置のどれが吸い込み先になるかが揺れた。CPU も ANE も、互いに同じだけ (コサイン 0.97) ずれ、音声の位置は崩れず、書き起こしは HF と同じ。行ごとの最大で割る LayerNorm に変えても同じだったので、あふれではない

効いた手当て:

- 正規化の入力を 1/64 にする (Gemma 4: KL 3.17 → 0.0004、PLaMo 3 も)。ただし値の小さな入力 (層 0 の入口の埋め込み) では二乗が fp16 の下に落ちて NaN になる (Qwen3-0.6B の埋め込みは最大 0.1、16.127)。層 0 は `-f16` で必ず見る
- 最後の層を head-scale で縮める (PLaMo-Embedding)、`-post-scale` (LFM3、1 層 1.4〜2.7 %)
- 残差を 1/32 で持ち、正規化は行ごとの最大で割ってから (Anima。固定の倍率だと非正規数になる)
- 残差の倍率は試して決めず、参照の各層の最大から決める: Qwen-Image-2.1 の DiT は 9000 (文の行)、文の符号器は層 6 から 13500 (最初のトークンの注意の吸い込み) なので 1/8 と 1/4 (`DitScale`、`TextScale`。float32 の参照が各層の最大を出す、16.165)
- 詰め物の行を最後のトークンで埋める (Gemma 4 の eps が fp16 で 0 になって NaN)
- ANE の `sigmoid` と `tanh` もずれる: x とその sigmoid の積で書いた SiLU が 80 個ある CNN (RTMDet の CSPNeXt) で、スコアが 0.35、箱が 98 px ずれた。CPU インタプリタの fp16 は重みの fp16 の分しかずれない。exp で書く (`onnx.Program.ExpSigmoid`、16.149)。どこでずれるかは、グラフの途中の値を 1 つずつ ANE と CPU インタプリタで比べて探す (`internal/vision/detect` の `TestBisect`)
- ANE の `softplus` と `silu` は不正確 (softplus がある入力で 0、silu は裾で 1.4 % ずれる)。exp と log で書いた `builder.softplus`、`builder.silu` を使う。fp16 の正規の最小値 (6e-5) を下回る積は ANE で桁を失うので、大きくしてから後で割る (Qwen3.5 の GDN の出力、16.88)。CPU の `hwnpu-dev check` ではこれは見えないので、ANE と Core ML の CPU (`HWNPU_COREML_UNITS=cpu`) で位置ごとの KL を比べる
- ANE の `gelu` も不正確。tanh 近似の GELU は `x / (1 + exp(-1.5958 (x + 0.044715 x³)))` と書く (Sana の Gemma 2: caption のコサイン 0.99962 → 0.99973、16.145)
- 後のすべての層が受け取る 1 行の計算 (拡散モデルの時刻の埋め込み: 正弦波 → 2 層 → 変調) は ANE で最大 1 % ずれ、DiT 1 回のコサインが 0.9998 → 0.983 になった。数 ms の計算なのでホストの float32 で (`time.safetensors`、Sana、16.145)
- 残差は収まっても線形注意の和 (VᵀK、分子、分母) は fp16 を超える (Sana の DiT 1.6e5、VAE の EfficientViT 4.5e7)。各ヘッドの q の行をその最大で割り (N / D は変わらない)、鍵を和の前に縮め (1/64、1/256)、分母の下を切る (16.145)
- linear の出力の 1 行が fp16 の上限に近い (SANA 1.5 の caption の `<bos>` の行で 3.8 万) と、ANE でだけ NaN になり、それを使う CFG の条件なしの側が崩れた。直後が正規化なら linear の重みとバイアスを 1/64 に (正規化は尺度によらない)。CPU インタプリタの fp16 では出ないので、部品を 1 つずつ CPU に移して探す (16.145)
- **行ごとの int8 の重みは大きな出力であふれる**: Neural Engine は int8 の符号のままの積和を取ってから行の尺度を掛けるとみられ、13000 の出力 (Qwen3-VL-8B の層 6 の down_proj、注意の吸い込みの行。残差の尺度の後で 3300) が途中で fp16 を超えて NaN になった。同じプログラムが Core ML の CPU では正しい。表の形式 (lut8) は重みを fp16 に戻してから積和を取るので正しい。そういう部品は CPU のインタプリタと層ごとに比べ、非有限の値を数えて探す (`internal/imagegen/qwenimage` の `TestTextLayersBisect`、16.165)
- **重みに畳んだ縮尺で積が fp16 の正規化の範囲を下回る**: 残差を 1/64 で持つために出力の射影の重みを縮めると、T5 の外れ値の行の小さなチャンネルが消えた (プロンプトの行のコサイン 0.36)。縮尺は射影の出力に掛け (出力が fp16 を超えるなら半分ずつ)、正規化した行は大きくして射影に入れ、出力で割る。Core ML は線形のすぐ隣の定数倍を重みに畳むので、効くのは縮尺が線形の隣にない形だけ (Chroma の DiT では効かなかった、16.170)
- **外れ値のチャンネルのある行の norm**: norm の前に行の最大値で割ると (`ScaledRMSNorm`)、他のチャンネルが非正規化数の近くになる。2 乗の平均は割った写しから取り、出力は x そのものに rsqrt / max を掛ける (`chroma/mil.t5Norm`)

### 3.4 合格

- 全部の部分が `all on the NPU`
- 2 回目と **3 回目**の起動が数秒 (コンパイルのキャッシュに残る)。分けた形 (`-paged`) で Gemma 4 は 98 s → 1.9 s。2 回目だけでは、追い出し合う 2 本を見逃す (16.99)
- プログラムがコンパイルのキャッシュを大きく超えるモデル (Qwen-Image-2.1: 17 GB) はこれを満たせない: 実行のたびにほとんどを読み直す (1 本 7〜32 秒、512² の 1 枚 4 分半のうち 4 分)。そのときは、ステップごとに回すものを最も少ないバイトに (DiT の画像のブロックを lut4、3.4 GB)、ほかの部分は 1 回の実行で 1 回だけ読み、プロンプトをまとめる (7.1)。読み込みの時間を記録する (16.165)
- 初回のコンパイルの時間を部分ごとに記録する。Qwen3.5 の 128 トークン/回 (GDN) は初回 13〜15 分かかった (未解決)
- M1 では、`HWNPU_PROFILE=1` の部分の時間が呼び出しごとにそろっている。順に回す部分の合計が約 2.9 GiB を超えると、同じ部分がばらつき、毎回 10 倍以上遅くなる (載せ直し)。M1 の `-prefill auto` は、2 本と MTP の層や塔のプログラムの合計が 2.8 GiB を超えると 1 本にする (16.118)。生成用 1 本だけで超えるモデル (Qwen3.5-4B の lut8、Gemma 4 E4B) は、ログに警告が出る (16.109、16.112)。順に回す部分の順が悪くても当たる: SANA 1.5 (3.0 GiB) は条件ごとに DiT の全部の群を回していて、1 ステップ 2.5〜3.2 秒、群ごとに回すと 1.6 秒 (16.160)
- 2.9 GiB を超えれば必ず載せ直すわけではない: Chroma の DiT (10 本、lut8 で 8.3 GiB) は 512² の 1 枚のステップの間ずっと Neural Engine に載ったまま (`mem.NPUWired` 8.29 GiB) で、DiT 1 回は組の和とほぼ同じ (6.4 秒と 6.1 秒)。1024² では `mem.NPUWired` が DiT を下回り (4.4〜6.9 GiB)、1 回 35 秒、同じ組で続ける CFG の 2 回目は 23 秒だったが、DiT を 6.9 GB にしても (MLP を lut6) 速くならず、重みの載せ直しではなかった。大きさごとに呼び出しの時間を測り、載せ直しの見立ては重みの量を変えて確かめてから手を打つ (16.170)
- **コンパイルのキャッシュはディスクが減ると消される**: プロセス名ごとのキャッシュ (`~/Library/Caches/<プロセス名>/com.apple.e5rt.e5bundlecache`) は上限が見えず 49 GB まで増えたが、ディスクの空きが約 15 GiB を切ると macOS が項目を消し、Chroma の 1024² の組が次の実行でコンパイルし直された (1 本 2〜19 分。初めは約 25 GB の上限とみたが誤り)。変換し直すと古いコンパイル済みモデルが `~/Library/Caches/hwnpu` に残る (実験の 2 日で 100 GB 以上)。項目の `.src` は使うパッケージを 1 つ指すが、ハードリンクしたパッケージ (Chroma の `LinkFrom`) は項目を共有する: 記録されたソースがない項目を消したら、使っているリンク先の書き出しの Neural Engine のコンパイル済みの束まで失い、DiT がコンパイルし直された。いまは当たったときに記録されたソースがなければ今のパッケージを記録し直すので、`cache.Prune` などの片付けで残る。ディスクを空け、2 回目の起動の読み込み時間を確かめる (Chroma の 1024² は 22 秒で全部キャッシュから)。テストのバイナリは自分の名前のキャッシュを作るので、コマンドの名前で作る (`go test -c -o DIR/hwnpu-image`) とコンパイル済みを共有できる (16.170)
- コンパイルの間は CPU を空ける: CPU の参照を並べて回すと、1024² のプログラムの配置の確認 (`MLComputePlan`) が上限を超えて読み込みが失敗した。独りでも時間の要るものがある: lut6 と lut8 の重みを混ぜた 1024² のシングルブロック 8 つの組は確認に 10 分を超えたので、上限を 30 分にした (`planTimeout`。このような組は読み込みに 19〜27 分、16.170)
- **シンボリックリンクにしたパッケージ**は、コンパイル済みモデルのキャッシュ (`cache.TreeDigest`) で空のツリーとしてハッシュされ、リンクしたパッケージが全部最初の 1 本のコンパイル済みモデルで走った (入力の形が違うと出る)。リンクを解いてから読むよう直した (16.170)
- 他のプロセスが Neural Engine でコンパイルしている間は、独りでは通るプログラムが失敗した ("Unable to compute the prediction")。失敗をプログラムのせいにする前に、ほかに使っているものがないか見る (16.170)
- **グラフを変えてもプログラムの名前が変わらないときは `llm.Arch.Revision` を上げる** (名前に `-rN` が付く)。上げないと hwnpu-chat は変更前に変換したプログラムを使い続ける (silu の書き換えで lfm3 / plamo3 が r1、ホストのソフトキャップで gemma4 が r1、Anima は `ExportVersion`、16.95、16.113)
- `hwnpu-dev check -package` の KL と argmax を記録 (形式ごと、5 節)
- `MLComputePlan` の待ちは 10 分まで (ほかのプロセスがコンパイルしている間、単独 13 秒の Gemma 2 の 1 本が 2 分を超えた)。ときどき返る "Failed to construct compute plan, internal failure" は 1 回やり直す (`internal/backend/coreml`、16.145)

### 3.5 Core AI (macOS 27)

同じ `.mlpackage` を Core AI でも動かす (`--backend coreai`)。`internal/coreai/ailower` が MIL を Core AI のバイトコードに下ろす。Core ML で 3.1〜3.4 を通った部品も、ここで通らないことがあるので、Core AI でも確かめる (16.169、16.182)。`hwnpu-image` と `hwnpu-audio` は Core AI だけで動く (macOS 27、16.190、16.191) ので、画像と音声のモデルは初めから Core AI のプログラム (`.aimodel`) に書き、Core ML の書き出しは `--cpu` が読むものだけ。M1 でも確かめる: MoGe-2 と Sana の VAE は M3 や Core ML で通ったのに、M1 の Core AI でコンパイラーに落ちた:

- **どの演算にも下ろし方が要る**。`aicheck lower OUT PKG` は下ろし方のない最初の演算で止まる (画像のモデルの ONNX のグラフは `max_pool`、続いて `conv_transpose` と replicate の `pad` で止まった)。新しく書くときは coreai-torch の書き方に合わせる: 小さな torch のモジュールを coreai-torch で変換し (`uv run --offline --prerelease=allow --python 3.13 --with coreai-torch==0.4.3 --with torch`、uv のキャッシュから)、プログラムを表示し、バイトコードを `tools/coreai/bcdump` で読む。演算の引数の順は coreai-core の `_coreai_ops_gen.py` にある
- **どの部品も、Core AI と Core ML の両方で CPU のインタプリタと比べる**: 乱数の入力で `aicheck run -cpu PKG...` と `aicheck run -cpu -coreml PKG...`。全部 Neural Engine に載った部品が Core AI でだけ誤ることがある: PP-OCR の検出器はコサイン 0.05 (Core ML 0.9999) で、RTMDet、RTMO、YuNet、DA3、MoGe-2 は正しかった
- **演算を `HWNPU_AILOWER_CUT=N aicheck run -cpu PKG` で探す** (先頭の N 個の演算で切ったプログラムを、その演算の milcpu の値とコサインで比べる。`AICHECK_WORST=1` で差の大きい要素を表示)。そのうえで、誤差の大きさだけでなく中身を見る。差の大きい要素だけで決めない: PP-OCR では、深さ方向の 3 × 3 と 1 × 1 の後の厳密な GELU の `x / sqrt 2` が誤っていた。最初は「最後の列だけ」と読んだ (差の大きい 12 個がそこに並んだ。値の大きい列だっただけ) が、全部の列とチャンネルがずれていた。割る前の値と結果をチャンネルごとに直線で当てはめると、正しい 0.7071 u に対して 1.42 u + d で、Neural Engine は割るところで掛けていた。この 3 つの演算だけのプログラムでは正しかったので、本物の部品で確かめる。Core AI の定数による `divide_v1` は、逆数との積に書くようにした (`HWNPU_AILOWER_DIVIDE=1` で割り算のまま下ろす。調べるとき用)
- **起動は両方のキャッシュが当たる状態で比べる**: それぞれを 1 回走らせた直後に、新しいプロセスで 3 回ずつ。画像を読むモデルはどちらも同じほどで起動する (1 コマンド 0.05〜0.9 秒)。ここでの最初の比較は、Core AI の 2 回目 (0.07〜0.45 秒) と、最後に走らせてから 1 時間たち、間にほかのモデルを動かした Core ML (1〜16 秒、コンパイルし直した) を並べていて、Core ML のキャッシュの外れを Core AI の速さと読み違えた。Core AI で変わるのは、キャッシュがディスクが減るまでプログラムを持ち続けること (Core ML は約 4 GiB、3.1)。初回のコンパイルはどちらも数秒から 22 秒
- **下ろし方の誤りと Neural Engine の誤りを `HWNPU_COREAI_UNITS=cpu` で分ける** (Core AI の CPU だけで動かす。`aicheck run -cpu` と `internal/backend/coreai` のテストで使える。Neural Engine を使わないので、ほかのプロセスがコンパイルしている間に新しい下ろし方を確かめるのにも使える)。PP-OCR の割り算は CPU でも GPU でも正しかった: 誤りは Neural Engine のもの。落とし穴が 1 つ: Core AI の CPU は、和が fp16 の範囲を超える `reduce_mean` があふれる (平均 −1.37 の 57600 要素が −inf。和を fp16 に戻してから 1 / n を掛けるため)。Neural Engine と GPU は正しい。また CPU のインタプリタは、実装してある範囲でしか参照にならない: `elu` は alpha 1 だけ
- **関数をいくつも持つプログラムは 1 つとしてコンパイルされる**: 大きさごとの書き出しを 1 本の `.aimodel` の関数にしたモデル (Sana の 512² と 1024²、16.189) は、コンパイラーが 1 つで失敗すると全部の関数が GPU に回る。切り詰める前に、大きさごとの Core ML のパッケージ (`hwnpu-image convert --backend coreml --size N`) の同じ部品を 1 つずつ `aicheck run` で見る。Sana の VAE の 1024² は、conv_in と `tile` で書いたチャンネルの繰り返しの和に 1 × 1 の畳み込みが続くところで失敗した ("empty reset layer candidates in SS cost model")。どの 2 つだけでも載る。繰り返しを 0 と 1 の重みの 1 × 1 の畳み込み (fp16 で厳密) にすると載った。本物の部品の最初に失敗する切り口を手がかりに、小さな書き換えを `aicheck probe` で試す
- **参照の精度を先に決める**。`runner` を通した CPU のインタプリタは `HWNPU_CPU_F16=1` がなければ fp32 で計算し、aicheck は fp16 に丸めて動かす。fp16 の丸めに頼るプログラム (MOSS-SoundEffect の snake の `(v + 1536) - 1536`) は丸めた参照とだけ合い、fp32 の参照では `--cpu` の経路が壊れていたことも隠れた (16.192)。定数やマスクを入力に取るプログラムは `AICHECK_CONST=mg=1536,m=1` で本物の値を与える
- **MOSS-SoundEffect の DAC で見つけた Core AI の Neural Engine の落とし穴 (16.192)**: `(v + c) - c` を c が入力でも `v` に畳む。カーネルが 1 より大きく 512 チャンネル以上の幅方向の畳み込みは、入力を別の演算が計算していると値が違う (高さ方向に: x を (1, C, T, 1)、重みを (co, ci, k, 1))。膨張のある畳み込みは長さによって値が違うか GPU に回る (フレームを膨張の幅の行に並べ、行方向に膨張なしで)。畳み込みの前の明示の `pad` も違った。チャンネルを分ける、明示の pad にする、は効かなかった。`sin` はそのまま Neural Engine で動き、fp16 の入力と同じ程度に正確
- `aicheck run` と `probe` は、コマンドと同じく Neural Engine のロックを取る (`llm.LockNPU`)。2 つのプロセスが同時に使うと Mac が固まったことがあり、ほかのプロセスのコンパイルは時間の計測も乱す

## 5. 量子化: 形式と校正の方法を選ぶ

**一番手間がかかり、一番効く段**。モデルによって 4 ビットの落ち方が 10 倍違う (AMD の q4 の KL: PLaMo 3 の訳文 0.009、LFM3 0.036、E4B 0.049、E2B 0.097)。次の順に決める。

### 5.1 測り方を揃える

- **KL(参照 ‖ 量子化)** の平均、中央値、95 %点、top-1 の一致。400 位置 (前の 256 トークンをプロンプトとして読ませ、その後を 1 つずつ)、**BOS あり**
- 文は 5 種: README (日英の混在。README と Go のコードは書き換わるので、2026-11-14 の版を `testdata/texts` に固定した (`readme.md`、`GPL-3`、`model.go`。校正に使う repo の文書と Go も同じ所)。`ironlm -forced` などにもこれを渡す)、GPL-3 (**校正に使わない**。合いすぎの検出用)、wiki40b-ja の評価分、wikitext-2 の試験分、Go のコード。置き場は `~/models/calib`
- 参照は fp32 の CPU (HF) か、同じ NPU の bf16。NPU の量子化の KL が CPU の見積もりと同じかを確かめる (LFM3 0.036 と 0.035、LFM3-VL も同じ傾向)。違えば NPU の計算 (丸め、bfp16) を疑う
- Apple の Neural Engine の上: `hwnpu-dev generate -package P.parts.json -score REF,...` がキャッシュなしのプログラム (`hwnpu-dev convert -seq 128`) を参照 (`ref_logits.py` / `ref_gemma4.py`) のトークンで流し、全位置の KL (平均、中央値、最大)、最上位、コサインを出す。文の先頭の数トークンの KL が大きい (8〜13) ので、設定の比較は同じ文どうしで (16.114)
- 画像生成は KL の代わりに、参照の軌跡の上での速度の相対 RMS と、自由に走らせた最後の潜在の cosine (`tools/amd/anima_gptq.py`)
- 画像生成は参照の軌道に沿って: float32 の参照の DiT の各呼び出しの入力 (`ref_chroma_lean.py` の `dit_in` と `sigma`) を NPU の DiT に通し、速度を比べる (`chroma.TestCallsOnDevice`)。Chroma の int8 の DiT は σ = 1 で正しく (0.99997)、σ = 0.25 で Neural Engine では 14 % ずれた (CPU のインタプリタでは 1.5 %)。ステップとともに育つ誤差は、最初の呼び出しの確認では見えない (16.170)

### 5.2 部分ごとのビット数を CPU で掃く

部分 (注意の射影、MLP、出力の行列、畳み込み、塔) ごとに 4 / 8 / bf16 を切り替えて CPU で KL を測る (`q4_gptq.py --method rtn` の `--q8`、`--head`、`--fmt-*` で組み合わせる)。今までの結論:

- **注意の射影は 8 ビット**: 重みの 1 割余りなのに 4 ビットにすると誤差の大半 (E2B 0.097 → 0.229)。固定は +0.12 GB だけ
- MLP と出力の行列は 4 ビット。出力の行列は 4 ビットでもほとんど効かない
- 短い畳み込みは 8 ビット (4 ビットで +0.01)
- サンドイッチ正規化の層 (Gemma 4、PLaMo 3) は 4 ビットに弱い。ANE の表なら lut6 以上 (Gemma 4 の lut4 は KL 2.54、PLaMo 3 2B は 1.91)
- **同じ構造でも大きいほど少ないビットに耐える**: PLaMo 3 Translate 8B の lut4 は 20 文のうち 13 文が lut8 と一字一句同じで、残りも正しい言い換えだった (2B は崩れた。16.164)。大きさごとに形式を測り直し、小さい版の結論を大きい版に持ち込まない (`Formatter`)
- ANE の 8 ビットの DiT: 行ごとの int8 は Sana 600M の絵を保ったが SANA 1.5 では崩れ、lut8 は保った (16.160)。両方を試して絵で見る
- 多モーダルの文の部分、TTS、d1 の判定、埋め込みは lut8 (lut4 で崩れた)
- 蒸留した 8 ステップの DiT は 4 ビットに弱い (q4nx で潜在の cosine 0.777)。q8 が既定 (q6 は構図を保つ)
- ANE でも同じ: Chroma1-Flash の DiT の MLP を lut4 (一様、k-means-minmax の表) にすると絵が変わるか崩れた (潜在のコサイン 0.87、0.93。lut8 は 0.9965)。lut6 は絵を保つ (0.985) が 1024² で速くならなかった (16.170)
- **大きな DiT は 4 ビットで保つことがある**: Qwen-Image-2.1-Turbo (20B、蒸留の 8 ステップ) は k-means-minmax の表の lut4 で 6 枚 0.935〜0.981、構図も文字も同じ (lut6 は 0.987 で 40 % 遅い)。先に、ブロックの組 1 つの fp16 に対する相対 RMS 誤差を実の入力で測る (一様 4.9 %、k-means 12.6 %、k-means-minmax 3.2 %、lut6 1.2 %、lut8 0.5 %。一部の射影だけ lut8 にしても 4.1〜4.8 %: 誤差は全部の射影にあった)。大きなモデルでは 3.3 節の行ごとの int8 のあふれが int8 に不利 (16.165)
- **プロンプトに 1 回のパスは、ただで 1 段上の形式にできる**: ステップの間は持たないので、Neural Engine が持つ量は増えない (Qwen-Image-2.1 の DiT の文の行のパスを lut8 に: 0.965 → 0.980、ステップの時間は同じ)
- **大きな DiT は MLP を 6 ビット、注意の射影を 8 ビットに** (Qwen-Image-2.1 の 7B の DiT、`tools/ref/qwenimage_quant.py`、16.167): MLP の q6 は 1.21 GB 減らして絵を保つ (CPU で 5 つの種の自由走行のコサイン 0.9965〜0.9999、NPU で 6 枚 0.976〜0.9996、構図は同じ)。注意の q6 は同じほどの誤差で 0.54 GB しか減らない。q4nx はどこでも細部が動く (18〜29 dB)。ただしこの DiT は Anima よりずっと 4 ビットに強い (0.99 と 0.777)。教師強制の速度の誤差と、いくつかの種で決める: 1 つの種のコサインはばらつく (q8 でも 1 つの種で 0.9983、別の種で 0.9997)
- **すでに 4 ビットのチェックポイント (MXFP4、gpt-oss の専門家) はその形のまま持つ**: q4nx に丸め直すと重みの誤差が 6.6 % 増え、KL が 2〜3 倍 (README 0.052 → 0.135、wiki-ja 0.043 → 0.107)。最大値で決める q8 でも 0.55 %。値は q6 (2 × e2m1 で -12〜12、2 の冪のスケール) にも mx4 (e2m1 の 4 ビットをカーネルで戻す、1 重み 4.55 ビット、`iron_gptoss_moe.py`) にもそのまま入る。選ぶ前に、丸め直しをチェックポイントと比べる (16.179)
- **小さいモデル (2B 以下) の MLP は 4 ビットで崩れることがある**: Qwen3.5-0.8B は README 0.055 に対し GPL 0.34 (GPTQ でも 0.30)。AMD の q6 (6.5 ビット、`--mlp q6 --head q6`) で 0.044。GPL を必ず見る。4B は q4 で 0.042 なので q4 のまま

### 5.3 校正の方法を順に試す

同じ形式のまま、どの符号 (段) を選ぶかで精度を上げる。形式が変わらないので速さとメモリは同じ。

**採るかどうか**: 校正に使っていない GPL でも丸めより悪くならないこと。LFM3-Audio は GPL だけ GPTQ で変わらない (0.154 → 0.161) が、他の 4 文が半分以下なので採った。多モーダルのモデルの文の部分は学習し直してあることが多い (LFM3-VL / Audio / Omni) ので、元のモデルの符号を使い回さず、それぞれ校正する。悪くなる文があれば、減衰を上げる (0.3 で試した)、校正の文を足す。

**DiT の GPTQ は別の種の自由走行で判断する**: Qwen-Image-2.1 の MLP の q4 を、別の 4 つのプロンプトで校正した GPTQ にすると、校正にないプロンプトで教師強制の速度の誤差は 13〜15 % 下がったが、自由走行は 3 つの種のうち 2 つで丸めより悪く (0.9888 と 0.9964)、看板の文字が変わった。評価するプロンプトそのもので校正すると、そのプロンプトだけがよくなった。採らない (16.167)。

**校正の費用**: CPU の fp32 で 2B 級 25〜60 分、E4B 2.4 時間 (fp32 で 30 GB 以上使う。並べて流すと OOM になる)。Linux では `systemd-run --user` で流す (セッションと一緒に殺されない)。**16 GB の Mac** でも Gemma 4 E2B は埋め込みの表をファイルから読めば (`q4_gptq.py` の `lean`、約 9 GB) 校正できる: M1 の 4 スレッドで 87 分、後半はスワップで遅くなる。校正の文は `tools/amd/calib_data.py`、PyTorch は Homebrew (16.114)。

**校正の対象にない重み**: 変換器は形式の重みをすべて丸め、MODELS が名前を挙げない重みも量子化する。Gemma 4 の `per_layer` の射影 (41M) を lut6 にすると GPTQ の後で目立つ: `-format-for per_layer=lut8` (+0.01 GiB) で ANE の KL の中央値 0.13 → 0.08 (16.114)。q4 / q8 の一覧の外の小さな射影を探し、1 段上げておく。

**射影は全部校正する**: `q4_gptq.py` に `--q8 gptq` がないと、注意と畳み込みの射影は丸めのまま (LFM3 は 143 のうち 73 だけに符号。付けると 143 で英文の KL 0.255 → 0.247、16.95)。16 GB の Mac のために軽く読み込んだモデル (lean) は、先に transformers のロジットと合わせる (KL 0.003 以下、最上位が同じ): Gemma 4 の `layer_scalar` (バッファ) を最初は読み漏らし、答えが崩れた (16.114)。

**符号の引き当て**: 符号はチェックポイントの重みの形と bf16 の値のハッシュで引く (`iron_q4.weight_key` = `palette.WeightKey`)。書き出しが重みを並べ替えたり、つないだりすると当たらない。書き出しのログの「N weights took the chosen codes」で数を確かめる (LFM3-VL: 73 個。q8 の部分は既定で丸めるので含まない)。PLaMo 3 の `gate_up_proj` のように 1 つの重みのまま量子化するものは当たる。

### 5.4 形式の決め方

| 目安 | 判断 |
|---|---|
| KL 0.05 未満 (CPU の HF との比較) | port-architecture の目安。4 ビットを既定にしてよい |
| KL 0.05〜0.2 | 答えの質 (9 節) を見て決める。ANE の lut6 (LFM3 0.232) はここ |
| KL 1 以上 | 使えない (lut4 の LFM3 は事実の質問 4 問中 3 問を誤った) |
| `hwnpu-dev formats` で参照と同じ次のトークン 90% 以上、短い質問の正解が同じ数 | 小さい方にする (Qwen3.5-2B の lut6 は lut8 と 92%、12 問とも 10 問正解。16.115) |
| 同じく 85〜90%、または計算や事実を新たに誤る | 1 つ上の形式のまま (Qwen3.5-0.8B の lut6 は fp16 と 86% で 17 × 23 を誤った) |
| 同じく 80% 未満、または答えが同じ句の繰り返しになる | 使えない (Qwen3.5 の lut4 は 60〜76% で、12 問中 5〜6 問が繰り返し) |
| 音声と画像のエンコーダ | 文字の誤り率 (WER、CER) で決める。Whisper の lut6 は WER 4.43% → 4.87%、CER 3.60% → 3.94% で、lut8 のまま |

速さとの引き換えは、重みのバイトどおり (ANE の lut4 / lut6 / lut8 で 1.81 / 2.65 / 3.49 ms)。lut6 の遅さは `SDPAGrouped` で取り戻した (16.41)。

- 参照は fp16 にする。fp16 が 1 部分 (0.97 GiB) に収まらないモデル (Qwen3.5-2B は最後の層と語彙 248K の出力層で 1.04 GiB) は lut8 を参照にして (`hwnpu-dev formats -ref lut8`)、lut8 自体は CPU の HF との KL で確かめる
- perplexity は短い文では量子化した方が低いことがある (Qwen3.5 の lut6)。参照との一致で比べる
- hwnpu-dev probe の形式ごとの読みの速さは、モデルの部分の速さとは限らない: M1 の hwnpu-dev probe は int8 を 62 GB/s で読むが、Gemma 4 E2B の部分では約 48 GB/s で、int8 はバイトが多いぶん lut6 より遅かった (16.112)。速さで形式を選ぶ前に、実物の部分を `HWNPU_PROFILE=1` で測る
- 小さくした形式で 2 本 (8 トークン/回とプロンプト用) の合計がコンパイルのキャッシュ (約 3.5 GiB) に収まるようになると、`-prefill auto` が 1 本から 2 本に変わる (Qwen3.5-2B の lut6)。常駐のメモリと初回のコンパイルを測り直す
- 形式はモデルの大きさで変わってよい: 同じアーキテクチャでも `Formatter` (config の `Format()`) でチェックポイントごとに決める (LFM3 と VL、Qwen3.5 の 2B と 0.8B / 4B)
- **1 枚に 1 回だけ回して閉じる部分の形式** (拡散モデルの文の符号器、Chroma の approximator) は、DiT ほどバイトを削らなくてよい。1 枚に 1 回読むだけで、ステップの間は持たない。ただしバイトは読み込み、ディスク、コンパイルのキャッシュを使うので、fp16 に残すのは要る重みだけにする: Chroma の T5-XXL は lut8 でプロンプトの 1 行がコサイン 0.77、`wo` (外れ値のチャンネルを入力に持つ FF の出力の射影、重みの 22 %) だけ fp16 で 0.979、絵は全部 fp16 と同じ (それとの潜在のコサイン 0.996〜0.999)。9.5 GB が 5.5 GB、プロンプトごとに 12.7 秒が 9.5 秒 (`--text-format-for wo=fp16`、16.170)。Chroma の approximator は fp16 のまま (0.5 GB)

### 7.1 画像生成 (拡散モデル)

1 枚の時間はほぼ DiT を回す回数で決まる: ステップ数 × 1 ステップの回数 (分類器なしのガイダンス、CFG では 2) × 1 回の時間。Anima-Aesthetic の 1024² は 30 × 2 × 4.55 秒 = 280 秒のうち 273 秒で、テキストと VAE は数秒。まず回す回数を減らし、次に 1 回を速くする。残りの伸びしろは 1 回の演算量で見積もる: Anima の DiT は 1 回約 17 TFLOP (28 ブロック、1 ブロックに射影と MLP 481 GFLOP、注意 137 GFLOP)、4.55 秒で毎秒 3.8 TFLOP、NPU の公称は 50 TOPS。どの変更も、同じ雑音から CPU の float32 の参照と比べ (潜在のコサイン、画像の PSNR)、種を並べて構図を見る (9 節)。

| M1 で Neural Engine が抱えるメモリ (`mem.NPUWired`) | — | ✓ (512² で 8.29 GiB、1024² で 6.92。T5 は fp16 を 2 層ずつ) | ✓ (1024² で 4.7〜5.4 GiB。T5 と VAE は Flash の書き出しからリンク) |

| 3 つのプロンプト × 2 つの種を diffusers の fp32 と | ✗ (1 枚、CFG 4: 0.9982) | ✓ (Mac の 512²: `ref_chroma_lean.py` と潜在のコサイン 0.987〜0.997、PSNR 30〜38 dB、同じ絵。AMD は 1 枚: 0.9988) | ✗ (1 枚、CFG 3: 0.9957。Mac は参照の最初の 4 回を 1024² で DiT に通して 0.9998 以上) |
| Intel の NPU | ✗ | ✗ | ✗ |

AMD の欄は別の作業で進めている (Sana の DiT の q8、交差注意のキーと値、Anima の VAE の段、AMD での Sana の CFG のステップ)。入ったら直す。Mac の電力量と Intel が残る。

## 8. 長い文脈

- 注意で分ける (`-paged`): 費用が使った長さに比例。既定 262144。ただし分けると注意の層ごとに Neural Engine を 2 回呼ぶ。全層が注意のモデル (Qwen3-0.6B の 28 層) では分けない 1 本が 2〜4 倍速い (16.127、`llm.Unpaged`)。注意の層の数を見て、両方を測る
- 2 段の注意 (`-sparse`): 約 48K から。合言葉の試験 (128K、250K、文書の 10 / 50 / 90 % の 3 つ)
- 状態型の層 (GDN) は 1 トークンずつと Q=64 の塊の一致 (`TestCachedMatchesFull` の形)

## 9. 用途での確認と記録

KL だけで決めない。モデルの用途で bf16 (または fp16) と並べる:

| 用途 | 確かめ方 |
|---|---|
| チャット | 16.26 の 4 問 (富士山、17 × 23、『こころ』、信濃川)、hwnpu-chat agent の課題 (`go test` が通るか)。小さいモデルが事実を誤ったら、fp16 にも同じ問いをする。同じく誤るなら、量子化や移植ではなくモデルの限界 (Qwen3.5-0.8B、16.99) |
| 翻訳 | **訳文のトークンだけ**で KL と一致を測る (原文の側は予測しないので高く出る)。44 文で bf16 と一字一句同じ数。`hwnpu-dev formats` は問答の文で測るので、翻訳モデルのパープレキシティには意味がない (PLaMo 3 Translate で 2.8 万) |
| 画像の説明、TTS | 同じ画像と音声で答えを並べる。TTS はもう一度 ASR に通す |
| 音声の書き起こし | 英語は LibriSpeech の検証用 73 本 (`hf-internal-testing/librispeech_asr_dummy`、正解つき)、日本語は `say` の 4 つの声 × 12 文。HF fp32 と一字一句同じ本数と WER / CER (16.115)。30 秒を超える音声も |
| 埋め込み | HF との cosine |
| 物の検出、OCR | 物 (種類、スコア、箱) を ONNX Runtime と比べ、全アンカーのスコアと箱は重みだけ fp16 に丸めたグラフの差と比べる (`tools/ref/onnx_f16_weights.py`)。OCR は配布元の手順全体を参照として動かし (`tools/ref/ref_ppocr.py`)、一字一句同じ行を数える (`compare_ocr.py`)。ホストの部分 (箱、切り出し、幅) もネットワークと同じくらい文字を変える。幅全体に注意する認識器は、行の後ろの 0 が多いと読み方が変わる。配布元と同じように詰める (16.149) |

- `hwnpu-dev formats` は、分けない 1 本のプログラムの重みを 0.00 GiB と表示する

- design.md の 16 章に節を足す (数値、採ったもの、採らなかったものと理由)

## 10. 部品として組み合わせるための値

モデルは将来、音声認識 → LLM → TTS のようにつないで、1 つのプロセスの中で同時に動かす (design.md 16.94、設計案で未実装)。そのときの常駐の管理と、つなぐ相手との照らし合わせに使う値を、モデルを入れたときに測って記録しておく。

| 記録するもの | 測り方 | 使い道 |
|---|---|---|
| 部分ごと (段、塔、DiT、VAE など) の固定の大きさ | AMD: プロセスの `/dev/accel/accel0` の写像の大きさ (`smaps`)。Mac: 部分ごとの重みと `phys_footprint` | メモリの予算 |
| 部分ごとの読み込み直しの時間 (2 回目) | AMD は `Release` / `Reload`。Mac は ANE のキャッシュに当たったとき | 追い出してよいかの判断。音声の連鎖のように遅れが聞こえる部分は常駐 |
| 同時に動く部分と、順に動く部分 | 処理の流れから | 順に動く部分だけを段ごとに載せられる (Anima のテキスト → DiT → VAE) |
| AMD の一番長いコマンドの時間 | `hwnpu-chat` / `irongraph` のログ | その間ほかのモデルが待つ。2 s 未満 (4.1) よりさらに短いほど、ほかと並べやすい |
| Mac の部分の重みの合計と切り替えの時間 | `TestCallTimes` の交互の呼び出し | ANE のキャッシュ (約 4 GiB) を超えると追い出されて再コンパイルに分単位。切り替えは 1 回 15〜35 ms |
| 入口と出口のデータの種類と条件 | モデルカードと前処理 | テキスト (トークナイザーと言語)、構造化テキスト (スキーマに従えるか)、画像 (受ける大きさ)、音声 (サンプルレート、チャンネル)。つなぐ相手との照らし合わせ |
| 少しずつ流せるか、最初の出力までの時間 | 塊で入れて塊で出してみる | 音声の連鎖の遅れの見積もり |

- 別のモデルとは、テキスト (同じトークナイザーならトークン ID) で受け渡す。隠れ状態は、トークナイザーが同じでも別のモデルとは互換にならない。ベクトルで直結してよいのは、一緒に学習した組 (LFM3-Audio のテキストモデルと depthformer、塔と射影、Anima のテキストエンコーダとアダプタ) だけ
- 音声を音声のまま扱うモデル (Audio、Omni) は、入口と出口を音声にした 1 つの部品として記録する

**合格**: 上の表の値が design.md の節に書いてある。

## 11. どの NPU でも名前で動くようにする (models.yaml と準備)

手で書き出したものが動いた時点では、まだ終わりではない。models.yaml に入れ、名前、ファミリー、用途を渡せば、どの NPU でも手作業なしで準備されて動くところまでを、モデルを入れる作業に含める。

### 11.1 準備の順

コマンドは、モデルを次の順に探す。

1. **手元にある書き出し**: 前に変換したもので、`NAME.done` (最後に書く) があるもの。途中で切れたものは作り直す
2. **配布された書き出し** (将来): Hugging Face から、その NPU のサブフォルダだけを落とす ([prebuilt.md](prebuilt.md))。書き出しの形式が安定してからにする。今はない
3. **手元で変換**: 変換器が読むファイルだけを落とし、sha256 を確かめ、変換して `.done` を書く
   - Apple と Intel は、Go の変換器で変換する。手本は Mac と Intel の Anima (`anima.Prepare`) と、hwnpu-chat のモデル (`chat.Prepare`)
   - AMD は、IRON の書き出しの道具 (`tools/amd/iron_*.py`) を IRON の環境 (mlir-aie、Peano、Python) で動かす。環境が見つからなければ、何を入れればよいか (INSTALL_AMD.md) を出して止める。黙って落ちたり、手順を利用者に丸投げしたりしない。hwnpu-chat はこうしている (`chat.PrepareAMD`): models.yaml の `amd_export` に書き出しのモデルとオプション、書き出しのスクリプトは hwnpu に埋め込み (`tools/amd/embed.go`)、IRON の環境は `HWNPU_IRON_ENV` か PATH の python3
4. **使えない**: 足りないもの (形がない、道具がない) を出して止める

- 落とすのは、変換器が読むファイルだけにする。リポジトリをまるごと落とさない。fp32 と fp16 の両方を置いているリポジトリがある (Sana 600M はリポジトリが 16.5 GB で、要るのは 8.9 GB)
- 同じファミリーで同じファイルを持つモデルは、ファイルを 1 回だけ落として共有する。Sana の 4 つは、どれも同じ Gemma 2 のテキストエンコーダ (5.2 GB) を持っている
- この NPU で動かす形がないモデルは、動ける所 (CPU など) に落とし、そのことを出す。たとえば、Apple と Intel の YuNet は CPU で動かす。`--device npu` を明示されたときだけはエラーにする

### 11.2 models.yaml に書く値 (見積もりでなく測った値)

| 項目 | 中身 | 測り方 | 落とし穴 |
|---|---|---|---|
| `bytes` | ダウンロードの大きさ | 準備で落とすファイルの合計。HF の API (`/api/models/OWNER/NAME/tree/main?recursive=true` の `lfs.size`) から取る | GB は 10⁹。`du -h` は GiB を出す。Sana-Sprint 0.6B は 7.7 GB を 7.2、Anima は 5.9 GB を 5.5 と書いていた |
| `memory` | 動いている間の最大 | 1 回の生成 (読み込みから終わりまで) の間、0.1 秒ごとに測る。AMD はプロセスの `/dev/accel/accel0` の写像の `Size` (`smaps`) に、同じ時刻の RSS を足す。Mac は、1 回呼んでからの `phys_footprint` と `mem.NPUWired` | 読み込みの直後ではなく、全体の最大を取る。Sana は、Gemma 2 のテキストの段 (2.3 GiB) と VAE (先読みで 2 段が同時に載り、2.4 GiB) が最大になる。DiT は 0.37 GiB しか使わない |
| `machine` | ファミリーがこのモデルを勧める、機械のメモリの下限 | `memory` に、OS とほかのアプリの分の余裕を見る | 同じ大きさのモデルどうしで揃える。DA3METRIC-LARGE (1.4 GB) は 8 で、DA3MONO-LARGE (同じ 1.4 GB) は 24 になっていて揃っていない |
| `file` | 1 つのリポジトリに複数のモデルがあるとき、そのモデルのチェックポイントのファイル | リポジトリのファイルの一覧 | Anima は `split_files/diffusion_models/` に Turbo、Aesthetic、Base が並ぶ (`anima-turbo-v1.1.safetensors` など)。名前の頭が違うことがある (Base は `net.`) |
| `device` | ベンダーごとの置き場所 (npu か cpu) | NPU と CPU (onnxruntime、1 スレッド) で、1 回あたりのエネルギー (mJ) を比べる | 小さなモデルは、AMD では NPU が負ける (YuNet は NPU 137 mJ、CPU 10 mJ。演算の切り替えに 1 回約 250 µs かかる)。1 つのベンダーの結果をほかに当てはめない |

- **同意の要るライセンス**: 研究用や非商用のライセンス (Qwen Research、Anima の CircleStone Labs) は models.yaml に `license: {id, url, terms, accept: true}` と書く。名前で初めて使うときに端末で一度だけ聞き、答えを `~/.config/hwnpu/licenses.json` に残す。端末がなければ止まり、`--accept-license` か `HWNPU_ACCEPT_LICENSE=ID` を求める (`chat.AcceptLicense`、16.155)
- **NPU ごとに変わる値**: ダウンロードの大きさ、メモリ、置き場所は NPU によって変わる
  - Anima のメモリは、AMD では 3.5 GB、Mac 向けの値は 4.1 GB
  - ダウンロードも変わる。今の AMD はチェックポイントを落として手元で書き出すが、配布が始まれば書き出しを落とすだけになる
  - 違うときは、`device` と同じ形で、ベンダーの表を書く (`memory: {amd: 3.5, apple: 4.1}`)。1 つの値なら全部の NPU に当てる。表に書かないベンダーは、表の中で一番大きな値を取る。`hwnpu-chat list` と `hwnpu-image list` の DOWNLOAD と MEMORY の列は、この機械の NPU のベンダーの値
- **用途も、ファミリーと同じくメモリで選ぶ**: 用途の `picks` にも、ファミリーと同じ段を書く。用途 `depth` には DA3MONO-LARGE しか書いておらず、8 GB の機械でも 24 GB 向けのモデルが選ばれていた
- **確かめ方**:
  - `HWNPU_MEMORY=8`、`16`、`24` を付けて、`hwnpu-image list` (`hwnpu-chat list`) を出す。用途とファミリーの列で、同じモデルが選ばれているかを見る
  - 各 NPU で、`list` の大きさ、メモリ、どこで動くか (RUNS FROM) が正しいかを見る。CPU に落とすモデルは CPU と出ていなければならない

測るときのスクリプトの例 (AMD):

```bash
"$@" & pid=$!
while kill -0 $pid 2>/dev/null; do
  awk '/accel/{a=1;next} /^[0-9a-f]+-/{a=0} a&&/^Size:/{s+=$2} END{printf "%d ", s/1024}' /proc/$pid/smaps
  awk '/VmRSS/{print int($2/1024)}' /proc/$pid/status    # NPU と RSS (MiB)。足したものの最大を memory に
  sleep 0.1
done
```

### 11.3 AMD の書き出しを Go にできるか

- 全部を Go にするのは難しい。IRON はグラフを MLIR にし、mlir-aie と Peano (AIE のコアの LLVM) で xclbin と ELF にコンパイルする。Go だけでやるには、このコンパイラを作り直すことになる
- ただし、コンパイルの結果 (`graph.elf`、xclbin) が決まるのは形からで、重みは別の bank (`bank_*.bin`、`embed.bin`) に入る。形ごとのプログラムを配り、bank は Go がチェックポイントから書く形にすれば、利用者の機械に Python は要らない
  - そのためには、モデルごとの重みの並べ方 (q8 や q4 への量子化、タイルの並び、畳み込みの im2col の並び、YuNet のような畳み込みと正規化の融合) を Go に移す必要がある
- 配布 (11.1 節の 2) が入るまでは、手元の IRON で書き出す
- **重みが違っても形が同じなら、プログラムは同じ**。2026-11-10 に Sana の書き出しで確かめた
  - DiT のブロックの `graph.elf` は、Sana-Sprint 1.6B と SANA 1.5 1.6B でバイト単位まで同じ
  - caption と dit_out の `graph.elf` は、Sprint 0.6B と Sana 600M、Sprint 1.6B と SANA 1.5 1.6B で、それぞれ同じ
  - dit_in は 4 つとも違う。Sprint にはガイダンスの埋め込みがあり、形が違うため
- **「形」に入るもの**: どれか 1 つが変われば、新しいプログラムが要る
  - 構造の寸法 (層の数、幅、ヘッドの数)
  - 画像の大きさ (Sana の比率ごとの大きさ、DA3 と MoGe-2 の 9 つの大きさ、YuNet の大きさ)
  - LLM の文脈の長さと、プロンプトの塊の大きさ
  - 部分ごとの量子化の形式 (q4、q6、q8)
  - NPU の世代と列の数 (NPU1、NPU2)
  - hwnpu の書き出しの形式の版
- **既存の形で済むもの**: 同じベースのファインチューン、LoRA をマージしたもの、同じ構造の蒸留モデルを、配っている大きさと形式で使う場合。bank を書くだけでよい
- **利用者の機械に要るもの** (bank を Go で書く場合): 今の実行時と同じ。コンパイラは要らない
  - Linux: amdxdna (6.14 以降のカーネル)、NPU のファームウェア、memlock の上限、`/dev/accel` の権限
  - Windows: AMD の NPU ドライバ (`xrt_coreutil.dll`) と `xrtshim`
  - CPU に置くモデル: onnxruntime の共有ライブラリ
  - チェックポイントを読む部分は Go で書く。safetensors と ONNX はある。PyTorch の `.pt` (MoGe-2 の `model.pt`、zip の中の pickle) は、これから書く
- **コンパイルも Python なしにするには**: 新しい形を作る人と、配布を作る CI だけの話。それも今の IRON (Python) で作れるので、必須ではなく、優先度は低い
  - 残る依存: mlir-aie (`aiecc` の C++ 版、`aie-opt`、`aie-translate`、`bootgen`。wheel で 853 MB)、Peano (AIE の `clang`、`llc`、`ld.lld`。422 MB)、カーネルのソースと AIE API のヘッダ。xclbinutil は hwnpu-dev xclbin で代わる
  - Go に移す部分: IRON の演算ごとの設計 (ObjectFIFO、ワーカー、実行の手順から MLIR を作るところ) と、`iron_graph.export_graph`
